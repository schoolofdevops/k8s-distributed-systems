Deep Dive — Services under the hood: cluster IPs, Endpoints and kube-proxy

The lab treated the Service as a switchboard: you call one name, you reach one of the Pods. That is the right mental model, but a switchboard implies an operator sitting in the path routing calls, and that is not what happens. There is no process in the traffic path. A Service is a set of rules in the Linux kernel on every node, written by kube-proxy, and in this part you open a node and read the actual rules that carried your requests to the backend Pods.

This is not a rerun of the lesson. The lesson said "kube-proxy programs the dataplane." Here you find the exact chains, watch them load-balance with a probability trick, and watch them re-write themselves when you scale — all against the running fernwood Services.

Before you start

You need the distsys cluster with the M4 lab still in place: the fernwood namespace, both ReplicaSets, and the backend (ClusterIP) and frontend (NodePort) Services. Confirm your context and namespace with kubectl config get-contexts before you begin.

First: which kube-proxy mode is this cluster running?​

kube-proxy can program the dataplane in more than one way, and the rules you read depend on which. The two you meet in practice are iptables (the long-standing default) and IPVS (a kernel load-balancer built for very large services). You never assume — you check. The mode is in kube-proxy's ConfigMap:

kubectl -n kube-system get configmap kube-proxy -o yaml | grep 'mode:'

Expected output

    mode: iptables

An empty string here would also mean iptables (it is the default when unset). Confirm it from the other side — what kube-proxy itself logged at startup:

KPP=$(kubectl get pods -n kube-system -l k8s-app=kube-proxy -o jsonpath='{.items[0].metadata.name}')
kubectl logs -n kube-system $KPP | grep -i proxier

Expected output

I0803 17:41:53.055126       1 server_linux.go:170] "Using iptables Proxier"

So this cluster is iptables mode. Everything below reads iptables rules. (If you ever land on a cluster in IPVS mode, the equivalent inspection is ipvsadm -L -n inside a node, and the cluster IP shows up as an IPVS virtual server with the Pod IPs as real servers — same idea, different kernel subsystem.)

The path a packet takes: three iptables chains​

When a frontend Pod connects to backend:8080, DNS resolves the name to the Service's cluster IP, and the packet is sent to that IP. The cluster IP belongs to no Pod and no NIC — nothing would answer an ARP for it. It survives only because kube-proxy has installed rules that intercept packets destined for it and rewrite them. Three chains do the work, and you can follow them in order. First get the cluster IP:

kubectl get service backend -n fernwood -o jsonpath='{.spec.clusterIP}{"\n"}'

Expected output

10.96.171.26

Now read the rule that catches traffic to it, inside the worker node (kube-proxy wrote identical rules on every node):

BIP=$(kubectl get service backend -n fernwood -o jsonpath='{.spec.clusterIP}')
docker exec distsys-worker sh -c "iptables-save -t nat | grep '$BIP'"

Expected output

-A KUBE-SERVICES -d 10.96.171.26/32 -p tcp -m comment --comment "fernwood/backend:http cluster IP" -m tcp --dport 8080 -j KUBE-SVC-WXFLBA2TDUYBCFRO
-A KUBE-SVC-WXFLBA2TDUYBCFRO ! -s 192.168.0.0/16 -d 10.96.171.26/32 -p tcp -m comment --comment "fernwood/backend:http cluster IP" -m tcp --dport 8080 -j KUBE-MARK-MASQ

Read the first line: any packet destined for 10.96.171.26 on TCP 8080 jumps from the top-level KUBE-SERVICES chain to a per-Service chain, KUBE-SVC-WXFLBA2TDUYBCFRO. The comment even names it — fernwood/backend:http. The hash suffix is derived from the Service, so it is stable for this Service but will differ on your machine.

The load-balancing trick: weighted probabilities​

Follow that per-Service chain. This is where one of the two backend Pods gets chosen:

docker exec distsys-worker sh -c "iptables-save -t nat | grep KUBE-SVC-WXFLBA2TDUYBCFRO"

Expected output

:KUBE-SVC-WXFLBA2TDUYBCFRO - [0:0]
-A KUBE-SERVICES -d 10.96.171.26/32 -p tcp -m comment --comment "fernwood/backend:http cluster IP" -m tcp --dport 8080 -j KUBE-SVC-WXFLBA2TDUYBCFRO
-A KUBE-SVC-WXFLBA2TDUYBCFRO ! -s 192.168.0.0/16 -d 10.96.171.26/32 -p tcp -m comment --comment "fernwood/backend:http cluster IP" -m tcp --dport 8080 -j KUBE-MARK-MASQ
-A KUBE-SVC-WXFLBA2TDUYBCFRO -m comment --comment "fernwood/backend:http -> 192.168.40.80:8080" -m statistic --mode random --probability 0.50000000000 -j KUBE-SEP-IG2SQFKA7R5SB5RZ
-A KUBE-SVC-WXFLBA2TDUYBCFRO -m comment --comment "fernwood/backend:http -> 192.168.40.83:8080" -j KUBE-SEP-CF2KBIHWLJBYARIK

The two bottom lines are the load balancer, and the mechanism is delightfully blunt. The first endpoint rule carries -m statistic --mode random --probability 0.5 — iptables flips a weighted coin, and with probability 0.5 it jumps to the chain for 192.168.40.80. If that rule does not fire (the other half of the time), the packet falls through to the next line, which has no probability and always matches — 192.168.40.83. Two Pods, 50/50.

Why the probabilities are not all the same number

This is the trick worth understanding, because it looks wrong at first. With three endpoints the probabilities are not 0.33 / 0.33 / 0.33 — they are 0.33, then 0.5, then fall-through. Each rule's probability is 1 / (number of endpoints still remaining below it). The first of three fires 1/3 of the time; of the remaining 2/3, the next fires 1/2 (so 1/3 overall); the last takes whatever is left (1/3). It is a bouncer at a line of doors flipping a coin at each: the weights are chosen so every Pod ends up with an equal share, using only "match with probability p or fall through." You will see the exact 0.33 / 0.5 split in the scaling demo below.

The final hop: DNAT to a real Pod​

Each KUBE-SEP-* ("SEP" = Service EndPoint) chain does the actual rewrite — destination NAT from the virtual cluster IP to a real Pod IP:

docker exec distsys-worker sh -c "iptables-save -t nat | grep -E 'KUBE-SEP-IG2SQFKA7R5SB5RZ|KUBE-SEP-CF2KBIHWLJBYARIK' | grep DNAT"

Expected output

-A KUBE-SEP-CF2KBIHWLJBYARIK -p tcp -m comment --comment "fernwood/backend:http" -m tcp -j DNAT --to-destination 192.168.40.83:8080
-A KUBE-SEP-IG2SQFKA7R5SB5RZ -p tcp -m comment --comment "fernwood/backend:http" -m tcp -j DNAT --to-destination 192.168.40.80:8080

There it is, end to end: packet to 10.96.171.26:8080 → KUBE-SERVICES → KUBE-SVC-… picks an endpoint by coin flip → KUBE-SEP-… DNATs it to 192.168.40.80:8080 or 192.168.40.83:8080, a real backend Pod. No proxy process, no extra network hop — the node's kernel rewrote the destination in place. That is the whole Service, and it is why a cluster IP can be "stable" while the Pods behind it churn: the IP is just a match key in these rules, and kube-proxy edits the rules as the endpoints change.

Watch the rules rewrite themselves when you scale​

The endpoints are not static config — kube-proxy regenerates these chains every time the Service's membership changes. Prove it. Scale the backend to three and re-read the per-Service chain:

kubectl scale replicaset backend -n fernwood --replicas=3
kubectl wait --for=condition=Ready pod -l tier=backend -n fernwood --timeout=60s
docker exec distsys-worker sh -c "iptables-save -t nat | grep 'fernwood/backend' | grep probability"
note

This step greps by the Service's fernwood/backend comment, not its cluster IP — the probability rules route to Pod IPs, so the cluster IP only appears in the earlier KUBE-SERVICES jump rule you already read, not here.

Expected output

-A KUBE-SVC-WXFLBA2TDUYBCFRO -m comment --comment "fernwood/backend:http -> 192.168.40.80:8080" -m statistic --mode random --probability 0.33333333349 -j KUBE-SEP-IG2SQFKA7R5SB5RZ
-A KUBE-SVC-WXFLBA2TDUYBCFRO -m comment --comment "fernwood/backend:http -> 192.168.40.83:8080" -m statistic --mode random --probability 0.50000000000 -j KUBE-SEP-CF2KBIHWLJBYARIK

The first endpoint dropped to 0.333, the second is 0.5, and the third (not shown, no probability) takes the rest — exactly the 1/n-of-remaining weighting from the note above, now with n=3. You changed one number in a ReplicaSet and kube-proxy rewrote the load-balancer to match. Put it back to two so M5 inherits the state it expects:

kubectl scale replicaset backend -n fernwood --replicas=2

Expected output

replicaset.apps/backend scaled

NodePort is the same machinery with one more entry rule​

The frontend's NodePort did not need a new mechanism — just one more chain that catches traffic arriving on the node port and sends it into the same per-Service path. Find it:

docker exec distsys-worker sh -c "iptables-save -t nat | grep 'fernwood/frontend' | grep 30080"

Expected output

-A KUBE-NODEPORTS -p tcp -m comment --comment "fernwood/frontend:http" -m tcp --dport 30080 -j KUBE-EXT-UMMLX5N253GY6HLC

KUBE-NODEPORTS matches anything arriving on TCP 30080 (on any node) and routes it into the frontend Service's external chain, which lands in the same endpoint-selection logic you just traced for the backend. So "NodePort" is literally "ClusterIP, plus a rule that also accepts the node port." One dataplane, one set of endpoint chains, two ways in.

A note on DNS: why the short name resolved​

One loose end from the lab. The frontend reached the backend as just backend, not the full backend.fernwood.svc.cluster.local. That works because of the Pod's resolver config:

FPOD=$(kubectl get pods -l tier=frontend -n fernwood -o jsonpath='{.items[0].metadata.name}')
kubectl exec $FPOD -n fernwood -- cat /etc/resolv.conf

Expected output

search fernwood.svc.cluster.local svc.cluster.local cluster.local
nameserver 10.96.0.10
options ndots:5

The nameserver is CoreDNS (itself a ClusterIP Service in kube-system). The search line is the key: because a frontend Pod in fernwood has fernwood.svc.cluster.local as its first search domain, the bare name backend is tried as backend.fernwood.svc.cluster.local and resolves. A Pod in a different namespace has a different first search domain, so it would have to use backend.fernwood — the concrete reason the "same namespace, short name; cross-namespace, longer name" rule from the lesson holds.

Where you will use this​

  • "My Service isn't reachable." Now you have a real procedure instead of guessing. Check kubectl get endpoints <svc> first — empty means a selector/label mismatch (the lab's broken Service). If endpoints exist but traffic still fails, you can go into a node and confirm kube-proxy actually wrote the KUBE-SVC/KUBE-SEP chains, ruling the dataplane in or out.
  • Understanding load distribution. When traffic looks lopsided across Pods, remembering that balancing is per-connection random (not per-request, and not round-robin) explains a lot — long-lived connections stick to one Pod, so a few clients with keep-alive can skew the spread. That is a dataplane fact, not a bug.
  • Reading kube-proxy mode before you tune. Before anyone reaches for IPVS "for performance," the first question is which mode is even running and whether the service count justifies it. You now know how to check in one command instead of assuming.

You have now seen a Service from both ends: the stable name and IP you code against, and the kernel rules that make that name mean something. In M5 the ReplicaSets you exposed here get an owner — a Deployment — that can replace their Pods a few at a time while these very Service rules keep steering traffic only to the ones that are ready.
