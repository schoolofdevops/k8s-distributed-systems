Service discovery and networking

▶ M4 · Service discovery & networkingOpen fullscreen ↗

You now have three frontend Pods and two backend Pods, kept alive by ReplicaSets. That is a new problem, not just a solved one. In M3 you wired the frontend to the backend by the backend's raw Pod IP — you looked it up and pasted it in. That was already fragile with one backend Pod, because a Pod's IP changes every time it is recreated. Now there are two backend Pods with two IPs, and the ReplicaSet will replace either of them at any moment with a Pod that has a new IP. Wiring by Pod IP is now impossible. This part gives you the object that fixes it for good: the Service.

The analogy: a company switchboard number​

When you call a company, you dial one main number and reach the switchboard. You do not know or care which specific person picks up, which desk they sit at, or that the person who answered last week has since left and been replaced. You dial the same number, every time, and the switchboard routes you to whoever is on duty and free. New hires get added to the rota; leavers get removed; the number on the business card never changes.

A Service is that switchboard number for a set of Pods. It gives them one stable name and IP that never changes, and it routes each request to one of the Pods currently behind it. Pods are added as ReplicaSets scale up, removed as they scale down or die — and callers, who only ever know the Service name, notice none of it. The Service turns a shifting set of disposable Pods into one dependable address.

Two capabilities are bundled in that one object, and it is worth naming them separately:

  • Service discovery — a stable DNS name you can reach the group by, instead of an IP you have to look up. This is the direct descendant of Docker's embedded DNS from M1, where backend resolved to a container on a user-defined network. Kubernetes does the same thing at cluster scale.
  • Load balancing — each connection to the Service is spread across the healthy Pods behind it, so the work is shared and no single Pod is a bottleneck.

Service discovery: the name is the contract​

Here is the payoff that makes the whole app work with zero code changes. The Fernwood frontend has always looked for its backend at http://backend:8080 — that default was written in M1 and never touched since. In M1 that name resolved through Docker's DNS; in M2 through Compose; and now, if you create a Service named backend, that same name resolves through Kubernetes DNS to the Service's stable IP. The hostname is the contract, and it has held across three different runtimes. This is why Part C's lab names the backend Service backend and nothing else: so the name the app already expects is the name the cluster provides.

Every Service gets a DNS record of the form:

<service-name>.<namespace>.svc.cluster.local

So the backend Service in the fernwood namespace is backend.fernwood.svc.cluster.local. But a Pod in the same namespace can use just the short name backend, because every Pod's DNS search path is pre-loaded with its own namespace. You will see this directly in the lab — a frontend Pod's /etc/resolv.conf lists fernwood.svc.cluster.local as a search domain, which is exactly why the bare word backend resolves. The rule that follows: same namespace, short name works; across namespaces, you must use the longer name (backend.fernwood). That is the first practical reason the namespace from Part A shows up in day-to-day work.

The four Service types — and when you would actually reach for each​

Every Service is one of four types. They are layers: each adds a way to be reached from further out.

  • ClusterIP (the default). A stable virtual IP and DNS name reachable only from inside the cluster. This is the right choice for anything that only other Pods need to talk to — which is most things. The Fernwood backend is ClusterIP: the frontend calls it, nothing outside the cluster should. If you do not specify a type, you get this, and most of the time that is correct.
  • NodePort. Everything ClusterIP gives you, plus a fixed port (30000–32767) opened on every node, so traffic to any-node-ip:that-port reaches the Service. It is the simplest way to expose something outside the cluster, and it is what you use in the lab for the frontend because it works on plain KIND with no cloud. In production it is mostly a building block, not the front door — raw node IPs and high port numbers are not what you hand to users.
  • LoadBalancer. Everything NodePort gives you, plus it asks the cloud provider for an external load balancer with a real, routable IP in front of the nodes. On EKS/GKE/AKS this is how a service faces the internet. On plain KIND there is no cloud to fulfil it, so it would sit <pending> — which is exactly why this course fronts the app with Ingress in M7 instead, the pattern you actually use to expose many services behind one entry point.
  • ExternalName. The odd one out: no proxying, no selector, no Pods. It just maps a Service name to an external DNS name via a CNAME — a way to give something outside the cluster (a managed database, a third-party API) a stable in-cluster name so your Pods can call it as if it were local, and you can swap the real target later without touching the callers.
The short version for choosing

Internal-only traffic → ClusterIP. Need it reachable from outside on a dev/bare cluster → NodePort. Need a real external IP on a cloud → LoadBalancer (or, for many services behind one address, Ingress in M7). Pointing at something outside the cluster → ExternalName. When in doubt, it is ClusterIP — you can always put a NodePort, LoadBalancer, or Ingress in front of it later.

Under the hood: Endpoints, the cluster IP, and kube-proxy​

A Service is not a process and not a proxy server sitting in the path. It is a set of rules. Three pieces make it work, and seeing them turns the switchboard from magic into mechanism.

1. The selector picks the Pods; the result is stored as Endpoints. A Service has the same kind of label selector a ReplicaSet has. It continuously matches Pods and writes their IP:port pairs into a companion object — the Endpoints (and its newer, shardable form, EndpointSlices). This is the switchboard's "who is on duty right now" list, and the cluster keeps it current for you: scale the backend ReplicaSet up and a new IP appears in the Endpoints within a second; a Pod dies and its IP drops out. The Service and the Endpoints are two objects working together — the Service is the stable front, the Endpoints is the live membership.

2. The cluster IP is virtual — nothing owns it. The 10.96.x.x address a ClusterIP Service gets is not assigned to any Pod or node. No machine answers ARP for it. It exists only as a target in a set of rules on every node. That is why it is stable: it is not tied to any Pod's lifecycle, because it is not tied to any Pod at all.

3. kube-proxy programs the dataplane. The component that turns "traffic to the cluster IP" into "traffic to one of the endpoint Pods" is kube-proxy, running on every node. It watches Services and Endpoints and writes rules into the node's kernel — on this cluster, iptables rules (the other common mode is IPVS; the deep dive checks which one you are actually running and reads the real rules). When a frontend Pod opens 10.96.171.26:8080, those kernel rules rewrite the destination to one of the backend Pod IPs, chosen roughly evenly. There is no extra hop through a proxy process — the kernel does the redirect. This is the same job Docker's networking did quietly in M1, now done explicitly and at cluster scale.

What this replaces, and where you are going​

Put the three modules side by side. In M1, containers found each other by name over Docker's embedded DNS on one host. In M3, you dropped to raw Pod IPs and felt how fragile that is. In M4, the Service restores the name — backend resolves again — but now backed by load balancing over a self-healing set of Pods across the cluster, with the membership list maintained automatically. The app code never changed through any of it; the platform underneath it got stronger.

In the lab you create both Services, watch their Endpoints track the Pods, prove the frontend reaches the backend by name with zero config, and deliberately break a selector so a Service has no endpoints and learn to read that failure. Then the deep dive opens the node and shows you the actual kube-proxy rules doing the work.
