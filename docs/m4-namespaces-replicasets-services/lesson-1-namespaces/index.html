Namespaces and kubectl contexts

▶ M4 · Namespaces & kubectl contextsOpen fullscreen ↗

In M3 you put a single frontend Pod on the cluster. It landed in a namespace called default, because you never said otherwise. That was fine for one Pod. But a real cluster is shared. Your team's app, a QA copy, a colleague's experiment, the platform team's tooling, all sit on the same machines. If everything lands in one bucket, names collide. A kubectl delete meant for staging can wipe something in dev. And you cannot tell whose Pod is whose. This first part fixes that before you put anything real on the cluster.

The analogy: floors in an office building​

Imagine the cluster is one office building, and a Namespace is one floor of it. The building has shared foundations. The same power, the same lifts, the same street address. In cluster terms, that is the nodes, the network, and the control plane (the brain that runs Kubernetes). But each floor is its own workspace. Two teams can both have a meeting room called "Boardroom", because they are on different floors. The names only have to be unique within a floor. You can lock a floor so only certain people can badge in. And when facilities says "clear floor 7", they empty that floor without touching floor 8.

A Namespace is exactly that. It is a named partition (a labelled section) inside one cluster. Inside it, object names must be unique. You can scope access and quotas to it, that is, set limits on who can use it and how much. And you can clean it up as one unit. It is not a security wall by itself, and it is not a separate cluster. The floors still share the building. It is an organizing boundary, and on a shared cluster you want one.

Namespaced vs cluster-wide: not everything lives on a floor​

Most things you create go in a namespace: Pods, Services, ReplicaSets, ConfigMaps, Secrets. A few things belong to the whole building and cannot sit on one floor. Those are Nodes, PersistentVolumes, Namespaces themselves, and cluster-wide roles (M8). This split matters the first time you go looking for something and cannot find it. You may be on the wrong floor, or it may not be a floor-level object at all. You can see the split directly:

kubectl api-resources --namespaced=true  --no-headers | awk '{print $1}' | head
kubectl api-resources --namespaced=false --no-headers | awk '{print $1}' | head

pods, services, replicasets, configmaps come back as namespaced. namespaces, nodes, persistentvolumes, clusterroles come back as cluster-scoped. When you run kubectl get pods, you are always asking about one namespace, the current one, unless you say -n <name> or --all-namespaces.

Contexts: which cluster, which namespace, which user​

Soon you will have more than one cluster on your machine. This course's distsys, maybe a work cluster, maybe another experiment. A kubectl context is a saved pointer that answers three questions at once. Which cluster am I talking to? As which user? And in which namespace by default? Switching context is how you move between clusters without retyping connection details on every command.

kubectl config get-contexts

You will see the clusters kubectl knows about. A * marks the current one, and a NAMESPACE column shows each context's default namespace. The most common operational mistake in Kubernetes is running a command against the wrong context. You delete in production what you meant to delete in dev. So before any command that changes things, build this habit: a one-second check.

kubectl config current-context

Two ways to work in a namespace, and which to use​

There are two ways to target the fernwood namespace you are about to create. Know both, because they solve different problems.

  • Per-command flag -n fernwood. Explicit, one command at a time: kubectl get pods -n fernwood. Nothing is remembered. You use this to glance at another floor without moving your desk. Run kubectl get pods -n kube-system to look at the building's own services, then come straight back.
  • Set the context's default namespace. kubectl config set-context --current --namespace=fernwood makes every later command assume fernwood with no flag. You use this when you are going to work on that floor for a while, which is exactly what the lab does. It changes the saved context, so it sticks across terminals and survives a reboot. You are moving your desk to that floor, not just visiting.
Namespace and context are not the same thing

Setting a context's default namespace is a convenience stored in the context. It does not restrict you. You can always reach another namespace with -n. And the namespace is only one field of a context. The context also picks the cluster and the user. So changing your default namespace does not change which cluster you are on. Keep the two ideas separate. The context chooses the building and your desk's floor. The -n flag lets you walk to any other floor for a single errand.

Into the rest of the module​

You now have the organizing boundary. In the lab you create a fernwood namespace, make it your default, and clean M3's single Pod out of default, so there is only one "frontend" on the cluster to reason about. Everything you build from here lives on the fernwood floor: the ReplicaSets in Part B, the Services in Part C, and every later module's work. Next you meet the object that keeps your app alive and at the right size without you watching it: the ReplicaSet.
