Lab — Organize and connect Fernwood Goods with Namespaces, ReplicaSets and Services

This lab picks up the exact cluster you left running at the end of M3 — the distsys cluster with one bare frontend Pod on it — and turns that hand-placed single Pod into a properly organized, self-healing, load-balanced app. By the end you have a fernwood namespace holding a frontend ReplicaSet (3 replicas) and a backend ReplicaSet (2 replicas), exposed by two Services, with the frontend reaching the backend by name — no Pod IPs anywhere.

What you will end up with

A fernwood namespace set as your default; a frontend ReplicaSet (3 Pods) behind a NodePort Service; a backend ReplicaSet (2 Pods) behind a ClusterIP Service named backend; and the Fernwood Goods page rendering its full catalogue, fetched through the backend Service. The cluster stays up — M5 turns these ReplicaSets into Deployments.

Before you start​

You need the running distsys cluster from M3. Point kubectl at it and confirm, then work from the labs repo:

kubectl config use-context kind-distsys
kubectl config current-context
cd labs/distributed-app

Expected output

Switched to context "kind-distsys".
kind-distsys
note

If kubectl get nodes does not show distsys-control-plane and distsys-worker both Ready, your M3 cluster is not up. Recreate it by re-running the M3 lab from its Step 1 — but you should not need to; the cluster is long-lived.

Step 1 — Create the fernwood namespace and make it your default​

The manifest is a small object. Apply it, then list namespaces to see it:

cat k8s/namespace.yaml
kubectl apply -f k8s/namespace.yaml
kubectl get namespaces

Expected output

apiVersion: v1
kind: Namespace
metadata:
  name: fernwood
  labels:
    app: fernwood
namespace/fernwood created
NAME                 STATUS   AGE
calico-apiserver     Active   51m
calico-system        Active   51m
default              Active   52m
fernwood             Active   0s
kube-node-lease      Active   52m
kube-public          Active   52m
kube-system          Active   52m
local-path-storage   Active   51m
tigera-operator      Active   51m

fernwood is now Active. From here you will do all your work on this floor, so set it as the context's default namespace — this saves typing -n fernwood on every command for the rest of the module:

kubectl config set-context --current --namespace=fernwood
kubectl config view --minify | grep namespace:

Expected output

Context "kind-distsys" modified.
    namespace: fernwood
note

This changes your saved context, so it sticks across terminals and reboots. To glance at another namespace without moving, use -n <name> on a single command (e.g. kubectl get pods -n kube-system). To go back to default later, run the same set-context command with --namespace=default.

Step 2 — Remove M3's bare frontend Pod​

M3 left a single frontend Pod in the default namespace, wired to the backend by raw Pod IP. It did its teaching job there; leaving it would mean two different "frontends" on the cluster confusing every later module. Delete it — the ReplicaSet-managed frontend in fernwood replaces it:

kubectl delete pod frontend -n default --ignore-not-found
kubectl get pods -n default

Expected output

pod "frontend" deleted
No resources found in default namespace.
note

--ignore-not-found makes this safe to re-run — if the Pod is already gone (you ran this lab before, or started from a cluster someone else already brought to this point), the delete is a silent no-op instead of an error, and you still end up with a clean default namespace.

default is now empty. Everything from here lives in fernwood.

Step 3 — Confirm the images are on the cluster nodes​

The frontend and backend images were loaded onto the nodes back in M2/M3. Images live at the node level, not per namespace, so they are still there — but re-run kind load to be certain (it is harmless if they are already present):

kind load docker-image fernwood-frontend:m2 --name distsys
kind load docker-image fernwood-backend:m2 --name distsys

Expected output

Image: "fernwood-frontend:m2" with ID "sha256:b614262e0581..." not yet present on node "distsys-control-plane", loading...
Image: "fernwood-frontend:m2" with ID "sha256:b614262e0581..." not yet present on node "distsys-worker", loading...
Image: "fernwood-backend:m2" with ID "sha256:957bbb660814..." not yet present on node "distsys-control-plane", loading...
Image: "fernwood-backend:m2" with ID "sha256:957bbb660814..." not yet present on node "distsys-worker", loading...
note

If you do not have these images, build them from labs/distributed-app: docker build -t fernwood-frontend:m2 ./frontend and docker build -t fernwood-backend:m2 ./backend, then re-run the two kind load commands. The image IDs will differ from the ones above.

Step 4 — Deploy the frontend ReplicaSet​

Look at the spec first — the three parts from the lesson, replicas/selector/template, with the template's labels matching the selector:

cat k8s/frontend-replicaset.yaml

Expected output (the parts that matter)

apiVersion: apps/v1
kind: ReplicaSet
metadata:
  name: frontend
  namespace: fernwood
spec:
  replicas: 3
  selector:
    matchLabels:
      app: fernwood
      tier: frontend
  template:
    metadata:
      labels:
        app: fernwood
        tier: frontend
    spec:
      containers:
        - name: frontend
          image: fernwood-frontend:m2
          imagePullPolicy: IfNotPresent
          env:
            - name: BACKEND_URL
              value: "http://backend:8080"

Apply it and wait for all three Pods to become Ready:

kubectl apply -f k8s/frontend-replicaset.yaml
kubectl wait --for=condition=Ready pod -l tier=frontend --timeout=90s
kubectl get replicaset frontend

Expected output

replicaset.apps/frontend created
pod/frontend-6psxk condition met
pod/frontend-xq68q condition met
pod/frontend-6mqg5 condition met
NAME       DESIRED   CURRENT   READY   AGE
frontend   3         3         3       10s

DESIRED 3 · CURRENT 3 · READY 3 — the ReplicaSet stamped out three Pods from the template. See them, with the labels the selector matches on:

kubectl get pods -l tier=frontend --show-labels

Expected output

NAME             READY   STATUS    RESTARTS   AGE   LABELS
frontend-6mqg5   1/1     Running   0          20s   app=fernwood,tier=frontend
frontend-6psxk   1/1     Running   0          20s   app=fernwood,tier=frontend
frontend-xq68q   1/1     Running   0          20s   app=fernwood,tier=frontend

Every Pod carries app=fernwood,tier=frontend — that is what makes them "the frontend ReplicaSet's Pods," and in Step 9 it is what the frontend Service selects on. The -xxxxx suffixes are generated and will differ on your machine.

Step 5 — Deploy the backend ReplicaSet​

Same shape, two replicas, tier: backend. Deploy it:

kubectl apply -f k8s/backend-replicaset.yaml
kubectl wait --for=condition=Ready pod -l tier=backend --timeout=90s
kubectl get replicaset
kubectl get pods -o wide

Expected output

replicaset.apps/backend created
pod/backend-kqs5n condition met
pod/backend-trt59 condition met
NAME       DESIRED   CURRENT   READY   AGE
backend    2         2         2       9s
frontend   3         3         3       2m
NAME             READY   STATUS    RESTARTS   AGE    IP              NODE             NOMINATED NODE   READINESS GATES
backend-kqs5n    1/1     Running   0          9s     192.168.40.80   distsys-worker   <none>           <none>
backend-trt59    1/1     Running   0          9s     192.168.40.83   distsys-worker   <none>           <none>
frontend-6psxk   1/1     Running   0          2m     192.168.40.82   distsys-worker   <none>           <none>
frontend-cbg22   1/1     Running   0          2m     192.168.40.85   distsys-worker   <none>           <none>
frontend-xq68q   1/1     Running   0          2m     192.168.40.79   distsys-worker   <none>           <none>

Five Pods now: three frontend, two backend, each with its own Pod IP from Calico's 192.168.0.0/16 pool. Those IPs are the problem the Services solve — note them, and note that you are about to stop caring about them.

Step 6 — Watch self-healing​

This is the ReplicaSet's whole reason to exist. Pick one frontend Pod name from your own get pods output above, delete it, and list immediately — you catch the controller replacing it in the same moment:

kubectl delete pod frontend-6psxk --wait=false
kubectl get pods -l tier=frontend

Expected output

pod "frontend-6psxk" deleted
NAME             READY   STATUS        RESTARTS   AGE
frontend-4vxpp   1/1     Terminating   0          55s
frontend-6psxk   1/1     Running       0          75s
frontend-cbg22   0/1     Pending       0          0s
frontend-xq68q   1/1     Running       0          75s

Read that carefully: the Pod you deleted is Terminating, and a brand-new Pod (frontend-cbg22 here, 0/1 Pending for a heartbeat) has already been created to take its place. A second later it is Running, and the count is back to three:

kubectl get replicaset frontend

Expected output

NAME       DESIRED   CURRENT   READY   AGE
frontend   3         3         3       78s

You did nothing to heal it. The controller saw the count drop below replicas: 3 and closed the gap. Confirm it in the ReplicaSet's own events:

kubectl describe replicaset frontend | tail -6

Expected output

Events:
  Type    Reason            Age   From                   Message
  ----    ------            ----  ----                   -------
  Normal  SuccessfulCreate  75s   replicaset-controller  Created pod: frontend-6psxk
  Normal  SuccessfulCreate  75s   replicaset-controller  Created pod: frontend-xq68q
  Normal  SuccessfulCreate  74s   replicaset-controller  Created pod: frontend-6psxk
  Normal  SuccessfulCreate  39s   replicaset-controller  Created pod: frontend-4vxpp

SuccessfulCreate is the controller stamping a Pod from the template — the self-healing you would otherwise be doing by hand.

Step 7 — Scale up, then back down​

Scaling is the same loop, driven by you changing the desired count instead of a Pod vanishing. Take the frontend to five:

kubectl scale replicaset frontend --replicas=5
kubectl get pods -l tier=frontend

Expected output

replicaset.apps/frontend scaled
NAME             READY   STATUS    RESTARTS   AGE
frontend-6psxk   1/1     Running   0          90s
frontend-c59vw   1/1     Running   0          5s
frontend-cbg22   1/1     Running   0          15s
frontend-kwz7k   1/1     Running   0          5s
frontend-xq68q   1/1     Running   0          90s

Two new Pods (-c59vw, -kwz7k), five seconds old. Now back to three:

kubectl scale replicaset frontend --replicas=3
kubectl get pods -l tier=frontend

Expected output

replicaset.apps/frontend scaled
NAME             READY   STATUS        RESTARTS   AGE
frontend-6psxk   1/1     Running       0          93s
frontend-c59vw   1/1     Terminating   0          8s
frontend-cbg22   1/1     Running       0          18s
frontend-kwz7k   1/1     Terminating   0          8s
frontend-xq68q   1/1     Running       0          93s

The two most-recently-created Pods go Terminating. Give it a few seconds and kubectl get replicaset frontend reads 3 3 3 again. Same mechanism as self-healing — the controller just makes reality match the number you declared, whichever direction the gap opened.

Step 8 — Expose the backend with a ClusterIP Service​

The backend only needs to be reachable inside the cluster, by the frontend. That is exactly what ClusterIP is for. Crucially, name the Service backend — that is the hostname the frontend already looks for (BACKEND_URL=http://backend:8080), so this wires the two together with no code change.

cat k8s/backend-service.yaml
kubectl apply -f k8s/backend-service.yaml
kubectl get service backend

Expected output

apiVersion: v1
kind: Service
metadata:
  name: backend
  namespace: fernwood
spec:
  type: ClusterIP
  selector:
    app: fernwood
    tier: backend
  ports:
    - name: http
      port: 8080
      targetPort: 8080
service/backend created
NAME      TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)    AGE
backend   ClusterIP   10.96.171.26   <none>        8080/TCP   0s

The Service has a stable CLUSTER-IP (10.96.171.26 here — yours will differ, but it will start 10.96.) that no Pod owns. Look at what it points to — the Endpoints, built from the selector:

kubectl get endpoints backend

Expected output

NAME      ENDPOINTS                               AGE
backend   192.168.40.80:8080,192.168.40.83:8080   19s

Two endpoints — one per backend Pod, exactly the Pods carrying tier=backend. The Service found them by label, not by name or IP.

Step 9 — Expose the frontend with a NodePort Service​

The frontend needs to be reachable from outside the cluster (your browser). On plain KIND, NodePort is the straightforward way. It opens a fixed port on every node:

kubectl apply -f k8s/frontend-service.yaml
kubectl get service frontend
kubectl get endpoints frontend

Expected output

service/frontend created
NAME       TYPE       CLUSTER-IP     EXTERNAL-IP   PORT(S)        AGE
frontend   NodePort   10.96.78.254   <none>        80:30080/TCP   0s
NAME       ENDPOINTS                                                  AGE
frontend   192.168.40.79:3000,192.168.40.82:3000,192.168.40.85:3000   0s

80:30080/TCP means: the Service listens on port 80 inside the cluster, and port 30080 is open on every node for outside traffic. Three endpoints, one per frontend Pod.

Step 10 — Prove service discovery end to end​

This is the moment it all connects. First, prove the name resolves and the frontend can reach the backend by it — exec into a frontend Pod, ask the cluster's DNS, then call the backend by name:

FPOD=$(kubectl get pods -l tier=frontend -o jsonpath='{.items[0].metadata.name}')
kubectl exec $FPOD -- getent hosts backend
kubectl exec $FPOD -- wget -qO- http://backend:8080/api/health

Expected output

10.96.171.26      backend.fernwood.svc.cluster.local  backend.fernwood.svc.cluster.local backend
{"db":"unavailable","hostname":"backend-trt59","service":"backend","status":"ok"}

The short name backend resolved to the Service's cluster IP, and the request reached a real backend Pod (backend-trt59). db is unavailable because there is still no database — that is M6, and the backend degrades gracefully exactly as designed. Call it a few times and watch load balancing spread across both backend Pods:

for i in 1 2 3 4 5 6; do
  kubectl exec $FPOD -- wget -qO- http://backend:8080/api/health \
    | sed -E 's/.*"hostname":"([^"]+)".*/\1/'
done

Expected output

backend-trt59
backend-trt59
backend-kqs5n
backend-trt59
backend-trt59
backend-kqs5n

Both backend Pods answer — the Service is balancing across them. The split will not be exactly even over six calls; it is roughly 50/50 over many.

Now the whole app, through the front door. NodePort on plain KIND is reachable from inside a node but not always straight from your Mac/Windows host, so the reliable way to open it in your browser is a port-forward to the Service. Run this in one terminal:

kubectl port-forward service/frontend 8080:80

Expected output

Forwarding from 127.0.0.1:8080 -> 3000
Forwarding from [::1]:8080 -> 3000

In another terminal, fetch the page and confirm it rendered the catalogue through the backend Service:

curl -s http://localhost:8080/ | grep -oE "served by <code>[^<]+|Cedar Plant Stand|Linen Table Runner"

Expected output

served by <code>backend-trt59
Cedar Plant Stand
Linen Table Runner

Open http://localhost:8080 in a browser: the Fernwood Goods page shows a green "Backend reachable · served by backend-xxxxx" banner and the full six-item catalogue — fetched by the frontend from the backend Service, no Pod IP anywhere. That green banner is the M3 raw-IP wiring problem, solved. Press Ctrl-C in the port-forward terminal when done.

Why port-forward and not the node IP?

NodePort genuinely opens 30080 on every node — you can prove it with docker exec distsys-worker curl -s -o /dev/null -w '%{http_code}\n' http://localhost:30080/healthz, which returns 200 from inside the node. But KIND's nodes are containers on a Docker network your host cannot always route to directly, so port-forward is the dependable browser path on a laptop. On a real cluster you would reach the NodePort via a node's real IP — or, more likely, put an Ingress in front (M7).

Step 11 — Labels and selectors, made concrete (the mismatch demo)​

You have seen selectors work. Now see one fail, because that is the bug you will actually hit. Apply a Service whose selector asks for tier: api — a label no Pod carries:

cat k8s/broken/backend-service-mismatch.yaml
kubectl apply -f k8s/broken/backend-service-mismatch.yaml
kubectl get endpoints backend-broken

Expected output

service/backend-broken created
NAME             ENDPOINTS   AGE
backend-broken   <none>      2s

<none> endpoints. The Service was created happily — there is no error at apply time — but it selects zero Pods, so it routes to nothing. describe shows exactly why, contrasted with the working one:

kubectl describe service backend-broken | grep -E "Selector|Endpoints"
kubectl describe service backend        | grep -E "Selector|Endpoints"

Expected output

Selector:                 app=fernwood,tier=api
Endpoints:
Selector:                 app=fernwood,tier=backend
Endpoints:                192.168.40.83:8080,192.168.40.80:8080

The broken Service asks for tier=api; the Pods are tier=backend. A request to it fails outright — there is nothing behind the address:

kubectl exec $FPOD -- wget -qO- -T 4 http://backend-broken:8080/api/health; echo "exit=$?"

Expected output

wget: can't connect to remote host (10.96.137.91): Connection refused
exit=1

Connection refused — the Service has a cluster IP but no endpoints to route to. This one selector typo is the single most common Service bug in real clusters: everything looks deployed, but traffic goes nowhere because a label and a selector disagree. When a Service "isn't working," check its Endpoints first. Clean up the broken Service:

kubectl delete service backend-broken

Expected output

service "backend-broken" deleted

Teardown — leave it running for M5​

As in M3, do not delete the cluster. This module's ReplicaSets and Services are the new steady state that M5 builds on. Confirm what you are leaving running:

kubectl get all

Expected output

NAME                 READY   STATUS    RESTARTS   AGE
pod/backend-kqs5n    1/1     Running   0          5m
pod/backend-trt59    1/1     Running   0          5m
pod/frontend-6psxk   1/1     Running   0          5m
pod/frontend-cbg22   1/1     Running   0          4m
pod/frontend-xq68q   1/1     Running   0          5m

NAME               TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)        AGE
service/backend    ClusterIP   10.96.171.26   <none>        8080/TCP       3m
service/frontend   NodePort    10.96.78.254   <none>        80:30080/TCP   3m

NAME                       DESIRED   CURRENT   READY   AGE
replicaset.apps/backend    2         2         2       5m
replicaset.apps/frontend   3         3         3       5m

Two ReplicaSets, five Pods, two Services, all in the fernwood namespace. That is what M5 inherits.

Do not run kind delete cluster

The distsys cluster is shared through M8. Deleting it means redoing every earlier setup. If you ever must rebuild, it is kind delete cluster --name distsys and re-running from M3's lab — but you should not need to.

What you proved​

  • A Namespace partitions one cluster; you created fernwood, made it your default, and cleared M3's Pod out of default so there is one app to reason about.
  • A ReplicaSet keeps a declared number of Pods alive. You watched it self-heal (a deleted Pod replaced in the same second) and scale (three to five and back), all by the reconciliation loop closing the gap between replicas and reality.
  • Labels and selectors are how objects find each other. The ReplicaSet owns Pods by label; the Services select Pods by label; a mismatched selector silently routes to nothing.
  • A Service gives a shifting set of Pods one stable name and IP with load balancing. The backend ClusterIP restored the backend hostname the app has expected since M1; the frontend NodePort exposed the app outside the cluster. Service discovery worked end to end, with no Pod IPs anywhere.

In M5 you stop managing these ReplicaSets directly. A Deployment will own them for you and add what a bare ReplicaSet cannot do: roll out a new version with zero downtime and roll back a bad one.
