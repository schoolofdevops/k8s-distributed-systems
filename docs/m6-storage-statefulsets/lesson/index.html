Stateful Workloads — Storage & StatefulSets

▶ M6 — Stateful Workloads — Storage & StatefulSetsOpen fullscreen ↗

Everything you have put on the cluster so far throws its state away, and it does not miss it. The frontend holds nothing. The backend serves a fixed catalogue and reports the database as down without crashing. That was on purpose. It let you scale, roll out, roll back, and autoscale freely, because any Pod was as good as any other. Lose one, and you lose nothing.

A database is the opposite. Delete the Pod running Postgres the way M5 ran the frontend, and the orders table goes with it. Data that is gone has no rollback. This is the one tier you cannot treat as interchangeable. So Kubernetes needs extra parts to run it safely: a way to give a Pod storage that lives longer than the Pod, and a controller that gives each stateful replica (a copy of the workload) a fixed identity instead of a random one. Those parts are PersistentVolumes, PersistentVolumeClaims, StorageClasses, and the StatefulSet. This module adds all of them. By the end, the Fernwood Goods backend is talking to a real Postgres running inside the cluster. That was the last piece still missing.

Why containers do not solve state for free​

Back in M1 the advice was to push state to the edges. Keep your containers stateless, so anything written inside a container's own filesystem (its local disk) is throwaway, because that filesystem dies with the container. That advice told you what not to rely on. It did not tell you where the state actually goes. This module is the other half. You will build the durable place you push state to, and attach that place to a Pod.

Why does this need real machinery? Because a Pod and its storage live on very different clocks. A Pod is cattle. It gets created, moved onto another node, and destroyed whenever a controller decides. Storage has to be the opposite. It must outlive the Pod, survive a move onto a different node, and reattach to whatever Pod stands in for the old one. You cannot get that by writing to the container filesystem. And you should not get it by hand-pinning a Pod to one node and one disk. You get it by making storage a first-class object with its own lifecycle (its own life, separate from any Pod), requested by the Pod but not owned by it.

The analogy: renting a self-storage unit​

Imagine a self-storage facility. The kind with rows of numbered units you rent by the month.

You do not build a storage unit. You walk into the office and sign a short agreement. It says: I need a unit, about this big, that I can load and unload myself. You do not get to point at unit 214 and demand that one. You state what you need, and the office gives you a unit that matches. Behind the counter, the facility keeps a catalogue of plans. There are standard units, climate-controlled units, and a plan where they clear the unit the day your lease ends, versus one where they keep your things locked up if you stop paying. The plan is not a unit. It is the recipe the office follows to hand you a real unit when you ask.

Map that onto Kubernetes, and the whole object model falls out:

  • The rental agreement you sign is the PersistentVolumeClaim (PVC), a Pod's request for storage of a given size and access mode. It says what you need, not which exact thing.
  • The actual unit you are handed is the PersistentVolume (PV), a real piece of storage, bound to your claim (locked to it as a pair).
  • The catalogue of plans behind the counter is the StorageClass, the recipe that says how to make a unit and what happens to it when the lease ends. It is not storage. It is how storage gets made.
  • The office building you a unit the moment you sign, instead of you phoning ahead to reserve a specific pre-built one, is dynamic provisioning (storage made on demand).
  • The standard loading dock every moving company knows how to back a truck up to, so the facility can swap in any vendor's units without rebuilding the place, is the Container Storage Interface (CSI). That is the plugin contract between Kubernetes and real storage systems, be it a cloud disk, a NAS box, or a local path on the node.

Keep one part of this analogy in mind. You, the tenant, never name a specific unit. You sign for a unit that meets your terms, and the office binds one to you. This gap between the two sides (your claim on one side, the real volume on the other, and a class deciding how they meet) is exactly why the same Pod manifest runs without any changes on a laptop's local disk and on a cloud provider's block storage.

The object model, layer by layer​

Four objects, each doing one job. Here is how a Pod ends up with storage that lasts:

  • A StorageClass is a named recipe for making storage. It points at a provisioner (the thing that actually creates the volumes) and it sets policy. The most important one is the reclaim policy. Delete throws the volume away when its claim is deleted. Retain keeps it. It also sets the volume binding mode, which is when the PV gets created. A cluster has a default StorageClass, so a claim that names none still gets one.
  • A PersistentVolume (PV) is one real piece of storage in the cluster, a specific unit. An admin can create it ahead of time (this is static), but far more often it gets created on demand by a StorageClass's provisioner.
  • A PersistentVolumeClaim (PVC) is a request for storage. It asks for a size, an access mode (ReadWriteOnce means mounted read-write by one node at a time, which is the common case), and, if you want, a StorageClass. Kubernetes then binds the claim to a PV that fits it. Binds means it locks the two together as a pair. A Pod mounts the claim, never a PV directly, so the Pod spec stays portable (it can move between clusters without edits).
  • The CSI is the standard interface a storage vendor builds to, so Kubernetes can drive it without vendor-specific code in the core. In your KIND cluster it is rancher.io/local-path. In AWS it is ebs.csi.aws.com. Same contract, so the same PVC works against either one.

Access modes: who can mount, and how many at once​

One field on a PVC creates more confusion than any other. It is the access mode. It is not about file permissions. It is about how many nodes can mount the volume, and whether they can write to it.

  • ReadWriteOnce (RWO) means mounted read-write by a single node at a time. This is what block storage (a cloud disk, a local path) supports. It is the right and common choice for a database: one writer, no sharing. Do keep this in mind: it says "one node", not "one Pod". Several Pods on the same node can share an RWO volume, which surprises people many a times.
  • ReadOnlyMany (ROX) means mounted read-only by many nodes. Useful for shipping the same fixed content to many replicas.
  • ReadWriteMany (RWX) means mounted read-write by many nodes at once. Only shared filesystems (NFS, CephFS, and the like) support it. So if you ask for RWX against a block-storage class, it either fails, or it quietly never works.

Here is the trap. People assume RWX will work just because they can type it in the manifest. But the access mode is only a request. The storage underneath has to be able to honour it. A database wants RWO, and it should say so. Reaching for RWX to "let all the replicas share one volume" is how people corrupt a database, not how they scale it. And that is the whole reason a StatefulSet gives each replica its own RWO claim instead.

Dynamic provisioning is the payoff​

The old way was static. An admin pre-created a pile of PVs by hand, and your claim bound to whichever spare one fit. That is like the self-storage facility making you reserve a specific pre-built unit days in advance, with someone having to guess how many units of each size to build.

Dynamic provisioning removes all of that. Your PVC points at a StorageClass. The moment a Pod needs the claim, the StorageClass's provisioner creates a PV of exactly the right size and binds it. No admin, no pre-building, and no guessing. You will watch this happen in the lab. You apply a PVC, see it sit Pending, start a Pod that mounts it, and then watch a PV appear and bind within seconds.

That Pending pause is not a fault. It is the default binding mode, called WaitForFirstConsumer. The provisioner waits on purpose until a Pod is actually scheduled before it creates the volume. That way the volume lands on the same node the Pod will run on. You will want to recognise this on sight. A PVC sitting Pending with no Pod to consume it is the single most common "is my storage broken?" false alarm. The deep-dive spends real time on how to tell that apart from a claim that is genuinely stuck.

Why a StatefulSet, and not a Deployment​

You now have a durable volume. For a database, that is needed but it is not enough. M5's deep-dive showed exactly why. Run Postgres as a Deployment, and its replicas are treated as interchangeable. You get random Pod names, no stable network address, and if they shared a volume they would corrupt each other's data. A Deployment is built on one assumption: any replica can stand in for any other. A database breaks that assumption. (If that demo is not fresh in your mind, here is the short version: two "identical" Postgres replicas are really two different databases, and the Deployment has no way to keep them straight.)

A StatefulSet is the controller built for workloads where identity matters. It gives each replica three things a Deployment cannot:

  • A stable name. Replicas are db-0, db-1, db-2. These are ordinals (fixed numbers in order), not random suffixes. Delete db-0, and the StatefulSet recreates it as db-0 again, not as some new db-9f8c7. In the self-storage story, tenant number 0 always comes back to the same numbered spot.
  • Its own PersistentVolumeClaim, kept across restarts. A StatefulSet has a volumeClaimTemplates field. Instead of one shared volume, it stamps out a separate PVC for each replica (data-db-0, data-db-1, and so on). And here is the important part: it reattaches the same PVC to the same ordinal every time that Pod is recreated. The Pod is throwaway. Its claim on its unit is not. This is the exact mechanism that makes the data survive a Pod delete.
  • A stable network identity. Paired with a headless Service (a Service with clusterIP: None), each replica gets a fixed DNS name, like db-0.db.fernwood.svc.cluster.local, that survives reschedules. A client can reach one specific replica every time, which a load-balanced ClusterIP cannot do.

It also starts and stops replicas in order. db-0 is ready before db-1 begins. This matters for clustered databases that must bring up a primary (the main copy) before its followers. You will run a single replica in the lab, since this is a storage-and-identity lesson, not a replication one. But the ordering guarantee is part of why the StatefulSet exists.

Put the two ideas together, and you have the recipe for any stateful workload on Kubernetes. You take durable storage from a PVC, and a StatefulSet to tie that storage to a stable identity. The database is just the most familiar example.

Where this leaves you​

In the lab you will inspect the cluster's default StorageClass. You will create a PVC and watch dynamic provisioning bind a PV to it the instant a Pod consumes it. Then you will write a file, delete the Pod, and prove the file is still there when a new Pod mounts the same claim. That is durability separated from the Pod's life, made real. Next you will deploy Postgres as a StatefulSet with a volumeClaimTemplates and a headless Service, seed it with some data, delete db-0, and watch it come back with the same name and the same data still on disk. Finally you will point the Fernwood backend at that database's stable DNS name and see it report db: connected for the first time in the whole course. The app now runs entirely on Kubernetes, with nothing left in Docker. See you in the lab.
