Lab — Give Fernwood Goods a real database with persistent storage

This lab picks up the distsys cluster you left running at the end of M5 — the fernwood namespace with a frontend Deployment, a backend Deployment under an HPA, and their Services. There is still no database in the cluster. You will fix that here, in three moves: first prove how persistent storage works with a plain Pod and a PVC, then deploy Postgres as a StatefulSet with its own durable volume, and finally wire the backend to it so the app runs entirely on Kubernetes for the first time.

What you will end up with

A default StorageClass you have inspected; a proven durability demo (a file that outlived its Pod); a db StatefulSet running Postgres with a per-replica PVC and a headless Service; proof that deleting db-0 brings it back with the same name, same volume, and same data; and the Fernwood backend reporting db: connected against that Postgres. The cluster stays up — M7 adds Ingress next and does not touch storage.

Point-in-time output

Every Expected-output block below is captured from one real run. PV names (pvc-1821b19a-…), Pod UIDs, IP addresses, timestamps and ages will differ on your machine — match the shape (a Bound status, the name db-0, a row count), not the literal values.

Before you start​

Point kubectl at the cluster and work from the labs repo. Confirm you are starting from M5's state — the two Deployments, and no database yet:

kubectl config use-context kind-distsys
cd labs/distributed-app
kubectl get deploy,statefulset -n fernwood

Expected output

Switched to context "kind-distsys".
NAME                       READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/backend    2/2     2            2           66m
deployment.apps/frontend   3/3     3            3           66m
No resources found in statefulset.apps.

Two Deployments, zero StatefulSets. If your default namespace is not already fernwood, add -n fernwood to the commands below (M4 set it as the context default).

Part 1 — Persistent storage with a PVC, from first principles​

Before the database, get the storage primitives under your hands with a plain Pod. The point of Part 1 is one thing: data on a PVC outlives the Pod that wrote it.

Step 1 — Inspect the default StorageClass​

KIND ships a dynamic provisioner (local-path) and marks its StorageClass as the cluster default. Look at it, and confirm the provisioner Pod is running:

kubectl get storageclass
kubectl get pods -n local-path-storage

Expected output

NAME                 PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
standard (default)   rancher.io/local-path   Delete          WaitForFirstConsumer   false                  3h3m
NAME                                      READY   STATUS    RESTARTS   AGE
local-path-provisioner-7dc846544d-ffnkd   1/1     Running   0          3h3m

Three fields matter. standard (default) means a PVC that names no class gets this one. Delete is the reclaim policy — when a claim is deleted, its volume goes with it. WaitForFirstConsumer means the volume is not provisioned until a Pod actually needs it, which you are about to see directly.

Step 2 — Create a PVC and watch it wait​

The PVC manifest requests 1Gi, ReadWriteOnce, and deliberately names no StorageClass so it uses the default:

cat k8s/pvc-demo.yaml
kubectl apply -f k8s/pvc-demo.yaml
kubectl get pvc demo-pvc -n fernwood

Expected output

NAME       STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
demo-pvc   Pending                                      standard       <unset>                 0s

Pending, with no volume bound. That is not an error — the event spells out why:

kubectl describe pvc demo-pvc -n fernwood | sed -n '/Events:/,$p'

Expected output

Events:
  Type    Reason                Age   From                         Message
  ----    ------                ----  ----                         -------
  Normal  WaitForFirstConsumer  0s    persistentvolume-controller  waiting for first consumer to be created before binding

The provisioner is waiting for a Pod to consume the claim before it creates a volume, so the volume lands on the right node. No consumer yet, so it waits.

Step 3 — Mount it, and the claim binds​

Start a plain Pod that mounts demo-pvc at /data. The moment it schedules, the PVC binds and a PV is provisioned on demand:

kubectl apply -f k8s/pvc-demo-pod.yaml
kubectl wait --for=condition=Ready pod/pvc-writer -n fernwood --timeout=90s
kubectl get pvc demo-pvc -n fernwood
kubectl get pv | grep demo-pvc

Expected output

pod/pvc-writer condition met
NAME       STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   AGE
demo-pvc   Bound    pvc-1821b19a-f443-4001-8db9-0f4a4aec9a63   1Gi        RWO            standard       19s
pvc-1821b19a-f443-4001-8db9-0f4a4aec9a63   1Gi   RWO   Delete   Bound   fernwood/demo-pvc   standard   3s

Bound, to a PV that did not exist a moment ago — pvc-1821b19a-… was created by the provisioner in response to the Pod. That is dynamic provisioning in one step. Now write a file onto the volume:

kubectl exec -n fernwood pvc-writer -- sh -c \
  'echo "Fernwood inventory snapshot $(date -u +%FT%TZ)" > /data/ledger.txt; \
   echo "hostname=$(hostname)" >> /data/ledger.txt; cat /data/ledger.txt'

Expected output

Fernwood inventory snapshot 2026-08-03T20:45:57Z
hostname=pvc-writer

Step 4 — Delete the Pod, prove the data survives​

This is the whole point. Delete the Pod and confirm the PVC is untouched:

kubectl delete pod pvc-writer -n fernwood
kubectl get pvc demo-pvc -n fernwood

Expected output

pod "pvc-writer" deleted
NAME       STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   AGE
demo-pvc   Bound    pvc-1821b19a-f443-4001-8db9-0f4a4aec9a63   1Gi        RWO            standard       52s

The Pod is gone; the claim and its volume remain Bound. Recreate a fresh Pod pointing at the same claim and read the file back:

kubectl apply -f k8s/pvc-demo-pod.yaml
kubectl wait --for=condition=Ready pod/pvc-writer -n fernwood --timeout=90s
kubectl exec -n fernwood pvc-writer -- cat /data/ledger.txt

Expected output

pod/pvc-writer condition met
Fernwood inventory snapshot 2026-08-03T20:45:57Z
hostname=pvc-writer

The same file, written by a Pod that no longer exists, read by a new one. Storage decoupled from the Pod lifecycle — exactly what a container's own filesystem could never give you.

Step 5 — Tear down the Part 1 demo​

You have made the point; clean up the throwaway pieces. Because the default StorageClass reclaim policy is Delete, removing the PVC also removes its PV:

kubectl delete pod pvc-writer -n fernwood
kubectl delete pvc demo-pvc -n fernwood
kubectl get pv | grep demo-pvc || echo "demo-pvc PV reclaimed"

Expected output

pod "pvc-writer" deleted
persistentvolumeclaim "demo-pvc" deleted
demo-pvc PV reclaimed
The PV may show Released for a moment first

With the Delete policy the provisioner removes the PV asynchronously, so a very quick kubectl get pv right after the delete can catch it in Released before it disappears. Re-run it a second later and the PV is gone. Under Retain — which you will meet in the deep-dive — it would stay Released on purpose.

Part 2 — Postgres as a StatefulSet​

Now the real thing. Postgres needs a durable volume and a stable identity, so it goes on as a StatefulSet, not a Deployment.

Step 6 — Deploy the headless Service and the StatefulSet​

Two objects. The headless Service (clusterIP: None) gives each replica a stable DNS name; the StatefulSet declares a volumeClaimTemplates so each replica gets its own PVC. Look at the StatefulSet first:

cat k8s/db-statefulset.yaml
apiVersion: apps/v1
kind: StatefulSet
metadata:
  name: db
  namespace: fernwood
spec:
  serviceName: db
  replicas: 1
  selector:
    matchLabels: { app: fernwood, tier: db }
  template:
    metadata:
      labels: { app: fernwood, tier: db }
    spec:
      containers:
        - name: postgres
          image: postgres:16
          env:
            - { name: POSTGRES_DB, value: "fernwood" }
            - { name: POSTGRES_USER, value: "fernwood" }
            - { name: POSTGRES_PASSWORD, value: "fernwood" }
            - { name: PGDATA, value: "/var/lib/postgresql/data/pgdata" }
          volumeMounts:
            - { name: data, mountPath: /var/lib/postgresql/data }
          readinessProbe:
            exec: { command: ["pg_isready", "-U", "fernwood", "-d", "fernwood"] }
  volumeClaimTemplates:
    - metadata: { name: data }
      spec:
        accessModes: [ReadWriteOnce]
        resources: { requests: { storage: 1Gi } }

serviceName: db ties it to the headless Service; volumeClaimTemplates is the StatefulSet-only field that gives each replica its own claim. Apply both and watch it come up:

kubectl apply -f k8s/db-service.yaml
kubectl apply -f k8s/db-statefulset.yaml
kubectl rollout status statefulset/db -n fernwood --timeout=180s

Expected output

service/db created
statefulset.apps/db created
Waiting for 1 pods to be ready...
partitioned roll out complete: 1 new pods have been updated...

Step 7 — See the stable name, the per-replica PVC, and the headless Service​

kubectl get pods -n fernwood -l tier=db
kubectl get pvc data-db-0 -n fernwood
kubectl get svc db -n fernwood

Expected output

NAME   READY   STATUS    RESTARTS   AGE
db-0   1/1     Running   0          14s
NAME        STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   AGE
data-db-0   Bound    pvc-87d43e84-976a-4b3a-bcfb-cc56d80af443   1Gi        RWO            standard       14s
NAME   TYPE        CLUSTER-IP   EXTERNAL-IP   PORT(S)    AGE
db     ClusterIP   None         <none>        5432/TCP   14s

Three things to notice. The Pod is db-0 — an ordinal, not a random suffix. The PVC is data-db-0 — <template-name>-<pod-name>, created automatically by the StatefulSet, not by you. And the Service has CLUSTER-IP: None — headless, so DNS resolves straight to the Pod.

Step 8 — Seed data, then delete the Pod​

Put a real table into Postgres and note the Pod's identity and its bound PV:

kubectl exec -n fernwood db-0 -- psql -U fernwood -d fernwood -c \
  "CREATE TABLE IF NOT EXISTS orders (id serial PRIMARY KEY, item text, qty int);"
kubectl exec -n fernwood db-0 -- psql -U fernwood -d fernwood -c "DELETE FROM orders;"
kubectl exec -n fernwood db-0 -- psql -U fernwood -d fernwood -c \
  "INSERT INTO orders (item, qty) VALUES ('Cedar Plant Stand', 3), ('Soy Wax Candle', 12);"
kubectl exec -n fernwood db-0 -- psql -U fernwood -d fernwood -c "SELECT * FROM orders ORDER BY id;"
kubectl get pod db-0 -n fernwood -o jsonpath='{.metadata.name} uid={.metadata.uid}{"\n"}'
kubectl get pvc data-db-0 -n fernwood -o jsonpath='PVC data-db-0 -> PV {.spec.volumeName}{"\n"}'

Expected output

CREATE TABLE
DELETE 0
INSERT 0 2
 id |       item        | qty
----+-------------------+-----
  1 | Cedar Plant Stand |   3
  2 | Soy Wax Candle    |  12
(2 rows)
db-0 uid=d161bc7e-9437-4391-bcb0-dfc5d5533403
PVC data-db-0 -> PV pvc-87d43e84-976a-4b3a-bcfb-cc56d80af443
note

The DELETE FROM orders makes this step safe to re-run — without it, running Step 8 twice would insert the same two rows again. DELETE 0 the first time (nothing to delete yet) is expected; a re-run shows DELETE 2 before the fresh insert.

Note the Pod's UID and the PV name. Now delete the Pod — the StatefulSet will recreate it:

kubectl delete pod db-0 -n fernwood
kubectl wait --for=condition=Ready pod/db-0 -n fernwood --timeout=120s

Expected output

pod "db-0" deleted
pod/db-0 condition met

Step 9 — Prove: same name, new Pod, same volume, same data​

kubectl get pod db-0 -n fernwood -o jsonpath='{.metadata.name} uid={.metadata.uid}{"\n"}'
kubectl get pvc data-db-0 -n fernwood -o jsonpath='PVC data-db-0 -> PV {.spec.volumeName}{"\n"}'
kubectl exec -n fernwood db-0 -- psql -U fernwood -d fernwood -c "SELECT * FROM orders ORDER BY id;"

Expected output

db-0 uid=b00fe447-dda7-4090-8959-68819a90f6e0
PVC data-db-0 -> PV pvc-87d43e84-976a-4b3a-bcfb-cc56d80af443
 id |       item        | qty
----+-------------------+-----
  1 | Cedar Plant Stand |   3
  2 | Soy Wax Candle    |  12
(2 rows)

Read those three outputs together. The name is still db-0. The UID changed (d161bc7e… → b00fe447…) — this is a genuinely new Pod, not the old one resurrected. The PV is identical (pvc-87d43e84…) — the StatefulSet reattached the same claim. And the data is all there. That is the exact failure M5's Deployment anti-pattern demonstrated — new random name, lost data — turned into a non-event. A StatefulSet is what makes it a non-event.

note

Your UID and PV name will differ. If this is not the first time you have run Step 8 on this cluster, the id column will not be 1/2 either — serial keeps counting up even after a DELETE. What proves the point isn't the exact ids, it's that both rows and their content survived a Pod being destroyed and recreated.

Part 3 — Wire the backend to the database​

The database is running; the backend still does not know about it. The backend reads a DB_HOST environment variable (it has defaulted to db and reported the database unavailable all through M2–M5, because no such host existed in the cluster). Point it at the StatefulSet's stable per-Pod DNS name.

Step 10 — Confirm the stable DNS name resolves​

kubectl run dnscheck --image=busybox:1.36 -n fernwood --restart=Never --rm -it --quiet -- \
  nslookup db-0.db.fernwood.svc.cluster.local

Expected output

Name:	db-0.db.fernwood.svc.cluster.local
Address: 192.168.40.79

That name — <pod>.<service>.<namespace>.svc.cluster.local — is stable for the life of the StatefulSet, which an ephemeral Pod IP is not. That is why the backend points at it and not at an IP.

Step 11 — Roll the backend with DB_HOST set​

Through M5, the backend Deployment carried no database configuration at all — there was no database in the cluster to point at. Check that first:

kubectl get deploy backend -n fernwood -o jsonpath='{.spec.template.spec.containers[0].env}{"\n"}'

Expected output

Empty — no DB_HOST, nothing. Now apply the updated manifest, which adds a DB_HOST env var pointing at the stable StatefulSet DNS name from Step 10:

kubectl apply -f k8s/backend-deployment.yaml
kubectl rollout status deployment/backend -n fernwood --timeout=120s
kubectl get deploy backend -n fernwood -o jsonpath='{.spec.template.spec.containers[0].env}{"\n"}'

Expected output

deployment.apps/backend configured
deployment "backend" successfully rolled out
[{"name":"DB_HOST","value":"db-0.db.fernwood.svc.cluster.local"}]
note

If you already ran this lab once on this cluster, the first env check above will already show DB_HOST set — that's expected on a re-run, not a sign anything is wrong.

Step 12 — Confirm db: connected — the app is fully on Kubernetes​

Hit the backend health and catalogue endpoints from a throwaway busybox Pod (the backend image itself has no wget):

kubectl run curler --image=busybox:1.36 -n fernwood --restart=Never -- sleep 3600
kubectl wait --for=condition=Ready pod/curler -n fernwood --timeout=60s
kubectl exec -n fernwood curler -- wget -qO- http://backend:8080/api/health; echo
kubectl exec -n fernwood curler -- wget -qO- http://backend:8080/api/products | head -c 200; echo

Expected output

{"db":"connected","hostname":"backend-ff65b9c87-96gfz","service":"backend","status":"ok"}
{"count":6,"db":"connected","products":[{"id":1,"name":"Cedar Plant Stand","origin":"Oregon"},{"id":2,"name":"Soy Wax Candle","origin":"Vermont"},{"id":3,"name":"Walnut Cutting Board","origin":"Ohio"}

"db":"connected" — for the first time in the course, the Fernwood backend is talking to a real Postgres running inside Kubernetes. Sessions 1–2 ran the database in Docker; Sessions 3–5 put only the stateless tiers on the cluster. The app now runs end to end on Kubernetes with nothing left in Docker.

Teardown​

Leave the cluster, the Deployments, the db StatefulSet, and the backend wiring running — M7 builds on all of it. Remove only the throwaway sampler Pod:

kubectl delete pod curler -n fernwood

Expected output

pod "curler" deleted

Confirm the steady state M7 inherits — two Deployments, one StatefulSet, three Services (including the headless db), and the bound data-db-0 claim:

kubectl get deploy,statefulset,svc,pvc -n fernwood

Expected output

NAME                       READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/backend    2/2     2            2           81m
deployment.apps/frontend   3/3     3            3           81m
NAME                  READY   AGE
statefulset.apps/db   1/1     7m20s
NAME               TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)        AGE
service/backend    ClusterIP   10.96.171.26   <none>        8080/TCP       138m
service/db         ClusterIP   None           <none>        5432/TCP       7m20s
service/frontend   NodePort    10.96.78.254   <none>        80:30080/TCP   138m
NAME                              STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   AGE
persistentvolumeclaim/data-db-0   Bound    pvc-87d43e84-976a-4b3a-bcfb-cc56d80af443   1Gi        RWO            standard       7m20s

You have attached durable storage to a Pod, watched it survive the Pod's death, run a database as a StatefulSet with a stable identity, and connected the app to it. For the harder failures — a PVC stuck Pending, a PV stranded in Released, and migrating a volume to a new StorageClass without losing data — continue to the deep dive.
