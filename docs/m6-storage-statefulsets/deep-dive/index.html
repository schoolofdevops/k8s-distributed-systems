Deep Dive — Diagnosing stuck PVCs and migrating volumes

The core lab showed storage working. This page is about storage when it does not work, and about moving data once it does — the two things a QA or platform engineer actually spends time on. Part 1 is a diagnostic playbook for PVCs that will not bind, run against real broken manifests. Part 2 is a real volume migration: copying a live PVC's data onto a new StorageClass and cutting the workload over without losing a byte.

Everything here runs in a throwaway storage-lab namespace so it never touches the db StatefulSet you left running for M7.

kubectl create namespace storage-lab

Part 1 — When a PVC will not bind​

A PVC has exactly two interesting states: Pending (not yet bound to a volume) and Bound (has one). Almost every storage support ticket is a PVC stuck in Pending, and the whole diagnostic skill is reading why from two places: the claim's events, and the StorageClass it is asking for.

Your first two commands for any Pending PVC never change:

kubectl describe pvc <name> -n <ns>    # the Events section is the diagnosis
kubectl get events -n <ns> --sort-by=.lastTimestamp | grep -i volume

The three scenarios below are the ones you will actually hit.

Scenario A — a StorageClass that does not exist​

The most common genuinely-stuck PVC: a manifest copied from another cluster that referenced a class name this cluster does not have (gold, fast-ssd, a cloud-specific class). Apply the broken claim:

kubectl apply -f k8s/broken/pvc-missing-storageclass.yaml
kubectl get pvc stuck-missing-sc -n storage-lab

Expected output

persistentvolumeclaim/stuck-missing-sc created
NAME               STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   VOLUMEATTRIBUTESCLASS   AGE
stuck-missing-sc   Pending                                      gold           <unset>                 3s

Pending, StorageClass gold. The events say exactly what is wrong:

kubectl describe pvc stuck-missing-sc -n storage-lab | sed -n '/Events:/,$p'

Expected output

Events:
  Type     Reason              Age   From                         Message
  ----     ------              ----  ----                         -------
  Warning  ProvisioningFailed  3s    persistentvolume-controller  storageclass.storage.k8s.io "gold" not found

ProvisioningFailed … "gold" not found. No provisioner recognises the class, so no volume is ever made. The fix is to point the PVC at a class that exists (kubectl get sc to list them) — edit the manifest's storageClassName, or drop the field to use the default. This one is unambiguous, and the Warning severity (versus the Normal you will see next) is the tell that it is a real failure.

kubectl delete pvc stuck-missing-sc -n storage-lab

Scenario B — Pending that is not broken at all​

This is the false alarm that generates the most needless tickets. Create a perfectly valid PVC on the default class and leave nothing to consume it:

kubectl apply -f - <<'EOF'
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: pending-no-consumer, namespace: storage-lab }
spec:
  storageClassName: standard
  accessModes: [ReadWriteOnce]
  resources: { requests: { storage: 1Gi } }
EOF
kubectl get pvc pending-no-consumer -n storage-lab
kubectl describe pvc pending-no-consumer -n storage-lab | sed -n '/Events:/,$p'

Expected output

persistentvolumeclaim/pending-no-consumer created
NAME                  STATUS    VOLUME   CAPACITY   ACCESS MODES   STORAGECLASS   AGE
pending-no-consumer   Pending                                      standard       2s
Events:
  Type    Reason                Age   From                         Message
  ----    ------                ----  ----                         -------
  Normal  WaitForFirstConsumer  2s    persistentvolume-controller  waiting for first consumer to be created before binding

Look at two things. The reason is WaitForFirstConsumer, and the type is Normal, not Warning. This PVC is healthy — the StorageClass binds late on purpose, so the volume is placed on the node the consuming Pod lands on. The "fix" is not a fix: mount it, and it binds within seconds.

kubectl run consumer --image=busybox:1.36 -n storage-lab --restart=Never \
  --overrides='{"spec":{"containers":[{"name":"c","image":"busybox:1.36","command":["sh","-c","sleep 3600"],"volumeMounts":[{"name":"d","mountPath":"/data"}]}],"volumes":[{"name":"d","persistentVolumeClaim":{"claimName":"pending-no-consumer"}}]}}'
kubectl wait --for=condition=Ready pod/consumer -n storage-lab --timeout=90s
kubectl get pvc pending-no-consumer -n storage-lab

Expected output

pod/consumer condition met
NAME                  STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS   AGE
pending-no-consumer   Bound    pvc-858efe6b-9e78-4276-9c06-cf4bf7553475   1Gi        RWO            standard       11s

The discipline: read the event type before you escalate. Normal / WaitForFirstConsumer means wait for (or create) a consumer. Warning / ProvisioningFailed means the claim is genuinely stuck. Same Pending status, opposite responses.

kubectl delete pod consumer -n storage-lab
kubectl delete pvc pending-no-consumer -n storage-lab

Scenario C — a PV stranded in Released​

The Delete reclaim policy on the default class tidies up after you. Retain does the opposite, and it produces the other classic stuck state. First look at the second StorageClass this module ships — same provisioner, but reclaimPolicy: Retain:

kubectl apply -f k8s/storageclass-retain.yaml
kubectl get sc

Expected output

storageclass.storage.k8s.io/standard-retain created
NAME                 PROVISIONER             RECLAIMPOLICY   VOLUMEBINDINGMODE      ALLOWVOLUMEEXPANSION   AGE
standard (default)   rancher.io/local-path   Delete          WaitForFirstConsumer   false                  3h8m
standard-retain      rancher.io/local-path   Retain          WaitForFirstConsumer   false                  0s

Now create a claim on it, bind it with a Pod, then delete the workload and the claim — the "oops, I cleaned up my test namespace" a QA does every week:

kubectl apply -f - <<'EOF'
apiVersion: v1
kind: PersistentVolumeClaim
metadata: { name: retain-demo, namespace: storage-lab }
spec:
  storageClassName: standard-retain
  accessModes: [ReadWriteOnce]
  resources: { requests: { storage: 1Gi } }
EOF
kubectl run retainer --image=busybox:1.36 -n storage-lab --restart=Never \
  --overrides='{"spec":{"containers":[{"name":"c","image":"busybox:1.36","command":["sh","-c","echo important > /data/keep.txt; sleep 3600"],"volumeMounts":[{"name":"d","mountPath":"/data"}]}],"volumes":[{"name":"d","persistentVolumeClaim":{"claimName":"retain-demo"}}]}}'
kubectl wait --for=condition=Ready pod/retainer -n storage-lab --timeout=90s
PV=$(kubectl get pvc retain-demo -n storage-lab -o jsonpath='{.spec.volumeName}')
kubectl delete pod retainer -n storage-lab
kubectl delete pvc retain-demo -n storage-lab
kubectl get pv "$PV"

Expected output

persistentvolumeclaim "retain-demo" deleted
NAME                                       CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS     CLAIM                     STORAGECLASS      REASON   AGE
pvc-e175e700-2b22-4904-89e1-4affac4813dd   1Gi        RWO            Retain           Released   storage-lab/retain-demo   standard-retain            39s
note

The transition to Released isn't instant — if you run kubectl get pv immediately after the delete, you may still catch it as Bound for a moment. Re-run the command if so; it settles to Released within a few seconds. The same async-transition note applies here as it did for the durability demo earlier.

The claim is gone but the PV is not — it is Released, still holding your data, still stamped with the old claim's name. Think of the self-storage unit whose tenant moved out: the office kept the padlock on with the old name tag, so nobody new can be assigned the unit until someone removes that tag. The stale claimRef is that tag, and it is what blocks reuse:

kubectl get pv "$PV" -o jsonpath='status={.status.phase} reclaim={.spec.persistentVolumeReclaimPolicy} claimRef={.spec.claimRef.namespace}/{.spec.claimRef.name}{"\n"}'

Expected output

status=Released reclaim=Retain claimRef=storage-lab/retain-demo

To make the retained volume reusable, clear the claimRef. The PV flips to Available and a new PVC could bind to it (recovering the data); if you instead want the space back, delete the PV:

kubectl patch pv "$PV" --type=json -p='[{"op":"remove","path":"/spec/claimRef"}]'
kubectl get pv "$PV"

Expected output

persistentvolume/pvc-e175e700-2b22-4904-89e1-4affac4813dd patched
NAME                                       CAPACITY   ACCESS MODES   RECLAIM POLICY   STATUS      CLAIM   STORAGECLASS      REASON   AGE
pvc-e175e700-2b22-4904-89e1-4affac4813dd   1Gi        RWO            Retain           Available           standard-retain            53s

Available — the padlock's name tag is off. This is the real reason Retain exists: an accidental kubectl delete pvc does not vaporise the data, and you can recover it by rebinding. Clean up the demo PV before moving on:

kubectl delete pv "$PV"

The diagnosis at a glance​

SymptomEvent you will seeWhat it meansAction
PVC Pending, StorageClass namedWarning ProvisioningFailed … not foundThe class does not exist on this clusterPoint the PVC at a real class (kubectl get sc)
PVC Pending, no consumerNormal WaitForFirstConsumerHealthy — binds when a Pod mounts itCreate/schedule the consuming Pod; then wait
PV Released, not reused(none — check claimRef)Retain kept the volume after PVC deletionClear claimRef to reuse, or delete the PV

Part 2 — Migrating a volume to a new StorageClass​

A StorageClass is (almost) immutable, and a PVC's class cannot be edited in place. So "move this volume to a different class" — a faster disk, a different reclaim policy, a different provisioner during a platform migration — is never an edit. It is always: provision a new volume on the new class, copy the data, cut the workload over, retire the old volume. The copy step runs inside the cluster in a Pod that mounts both claims at once.

Step 1 — a source volume with real data​

Stand up the "before": a PVC on the default class with a workload writing to it, and record a checksum you will insist on matching after the move.

kubectl apply -f k8s/migration-source.yaml
kubectl wait --for=condition=Ready pod/app -n storage-lab --timeout=90s
kubectl exec -n storage-lab app -- sh -c '
  mkdir -p /data/catalogue
  printf "Cedar Plant Stand,Oregon,49.00\nSoy Wax Candle,Vermont,18.00\nWalnut Cutting Board,Ohio,65.00\n" > /data/catalogue/products.csv
  dd if=/dev/urandom of=/data/catalogue/blob.bin bs=1k count=256 2>/dev/null'
kubectl exec -n storage-lab app -- sh -c 'cd /data && find . -type f | sort | xargs md5sum'

Expected output

959ac6b03c881ae95efb36d699a25208  ./catalogue/blob.bin
1d88d965eaf4d310d84109f6bc4fd8af  ./catalogue/products.csv
note

blob.bin is built from /dev/urandom, so its checksum will be different on your machine — that's expected. products.csv is fixed text, so that checksum should match exactly. What matters for the migration proof later is that both checksums stay identical to what you see here, on your own run, before and after the move — not that they match the literal values printed on this page.

Step 2 — a target PVC on the new class​

The destination claim references standard-retain. Like any WaitForFirstConsumer claim it stays Pending until something mounts it:

kubectl apply -f k8s/migration-target.yaml
kubectl get pvc -n storage-lab

Expected output

NAME          STATUS    VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS      AGE
app-data      Bound     pvc-c6beff9b-5d83-4820-a76b-546713b24876   1Gi        RWO            standard          10s
app-data-v2   Pending                                                                        standard-retain   0s

Step 3 — copy with a two-volume Pod​

ReadWriteOnce means only one Pod can mount app-data at a time, so stop the source workload first, then run a migrator Pod that mounts the old claim read-only at /old and the new one at /new and copies across:

kubectl delete pod app -n storage-lab
kubectl apply -f k8s/migration-copy.yaml
kubectl wait --for=condition=Ready pod/migrator -n storage-lab --timeout=120s
kubectl logs migrator -n storage-lab | grep COPY_DONE
kubectl get pvc app-data-v2 -n storage-lab

Expected output

pod "app" deleted
pod/migrator condition met
COPY_DONE
NAME          STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS      AGE
app-data-v2   Bound    pvc-ccd7d4b5-ae4a-420a-b3a8-3fd0bfdc05b9   1Gi        RWO            standard-retain   51s

Mounting the target bound it — a new PV on standard-retain. Now the check that makes a migration trustworthy: the checksums on the new volume must match the source exactly.

kubectl exec -n storage-lab migrator -- sh -c 'cd /new && find . -type f | sort | xargs md5sum'

Expected output

959ac6b03c881ae95efb36d699a25208  ./catalogue/blob.bin
1d88d965eaf4d310d84109f6bc4fd8af  ./catalogue/products.csv

Identical to Step 1, byte for byte. cp -a preserved contents and metadata. Never cut a workload over on "the copy finished" — cut it over on "the checksums match".

Step 4 — cut over and retire the old volume​

Stop the migrator, bring the workload up on the new claim, verify it reads the migrated data, and only then delete the old PVC:

kubectl delete pod migrator -n storage-lab
kubectl apply -f k8s/migration-verify.yaml
kubectl wait --for=condition=Ready pod/data-verify -n storage-lab --timeout=90s
kubectl exec -n storage-lab data-verify -- sh -c 'cat /data/catalogue/products.csv; echo ---; cd /data && find . -type f | sort | xargs md5sum'

Expected output

Cedar Plant Stand,Oregon,49.00
Soy Wax Candle,Vermont,18.00
Walnut Cutting Board,Ohio,65.00
---
959ac6b03c881ae95efb36d699a25208  ./catalogue/blob.bin
1d88d965eaf4d310d84109f6bc4fd8af  ./catalogue/products.csv

The workload is now serving from app-data-v2 on the new StorageClass, with the same data. Retire the old volume:

kubectl delete pvc app-data -n storage-lab
kubectl get pvc -n storage-lab

Expected output

persistentvolumeclaim "app-data" deleted
NAME          STATUS   VOLUME                                     CAPACITY   ACCESS MODES   STORAGECLASS      AGE
app-data-v2   Bound    pvc-ccd7d4b5-ae4a-420a-b3a8-3fd0bfdc05b9   1Gi        RWO            standard-retain   101s

Migration complete: one volume left, on the new class, holding verified-identical data. Because app-data was on the Delete class, retiring the claim also removed its PV; nothing is stranded.

Doing this to the db StatefulSet

The same pattern moves a StatefulSet's volume, with one wrinkle: you cannot edit volumeClaimTemplates on a live StatefulSet. The real-world move is to scale the StatefulSet to zero, migrate data-db-0 with a two-volume Pod exactly as above, then recreate the StatefulSet with the new template so db-0 re-adopts the migrated claim. The mechanics you just practised are the whole job.

Where you will use this​

  • A PVC is stuck Pending in CI or a fresh namespace. Read the event type first: Normal / WaitForFirstConsumer is a healthy claim waiting for a Pod (do not escalate); Warning / ProvisioningFailed … not found is a real misconfigured class (fix the name). That one distinction closes most storage tickets.
  • Someone deleted a PVC and the "empty" cluster still shows the PV. A Released PV under Retain is data you can still recover — clear the claimRef and rebind, rather than assuming it is lost.
  • A platform team is moving you onto a new StorageClass (cheaper disks, a CSI driver swap, a different reclaim policy). The provision-new / copy / verify-by-checksum / cut-over / retire sequence is the safe path, and "verify by checksum before cut-over" is the step that keeps a migration from becoming an incident.

Teardown​

Everything in this deep-dive lived in the throwaway storage-lab namespace, plus one cluster-scoped standard-retain StorageClass. Remove both — the db StatefulSet in fernwood is untouched by this:

kubectl delete namespace storage-lab
kubectl delete storageclass standard-retain

Expected output

namespace "storage-lab" deleted
storageclass.storage.k8s.io "standard-retain" deleted
note

Deleting the namespace also removes every Pod and PVC inside it (data-verify, app-data-v2, and anything left from Scenarios A–C) — you don't need to delete them one at a time first. This also puts kubectl get storageclass back to showing only standard (default), matching the lab's Part 1.
