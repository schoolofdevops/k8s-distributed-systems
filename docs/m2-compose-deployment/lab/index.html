Lab — Deploy the 3-tier app with Docker Compose

In M1 you started the same app by hand: create a network, then five docker run commands in the right order, each with its own flags. It worked, but the topology only existed in your terminal history. In this lab you write that topology down once, in a compose.yaml file, and bring the whole stack up with a single command. You then use the two things Compose gives you that the manual run did not — a named volume so the database survives a restart, and a restart policy so a crashed container comes back — and you find the wall that neither of them can get past.

This is the same distributed-app spine from M1, grown in place: same code, same images, now declared as a stack. It lives at labs/distributed-app/ in the labs repo.

What you will end up with

One file, compose.yaml, describing three services — frontend, backend, db — on one Compose-managed network with a named volume for Postgres. docker compose up brings all three up in dependency order; http://localhost:3000 shows the Fernwood Goods catalogue; the database keeps its data across a full teardown; and a crashed backend is restarted automatically.

Before you start​

You need Docker running (Compose ships inside Docker Desktop and Rancher Desktop) and the labs/distributed-app/ source from the labs repository.

docker compose version
cd labs/distributed-app
ls

Expected output

Docker Compose version v5.1.4
backend
compose.yaml
frontend
README.md
note

Your Compose version will differ — any Compose v2 or later is fine (the command is docker compose, with a space, not the old docker-compose). What matters is that it returns a version and does not error.

The checked-out compose.yaml is already the finished file

The course ships each module's completed artifacts, so the compose.yaml you see in the listing above already reflects this lab's end state — it includes the restart policy you add in Step 7. That is expected, not a mistake. You build the file up from scratch as you work through the lab: Step 2's command writes the pre-restart version, and Step 7's command writes the final version. Each of those commands overwrites whatever is on disk, so the lab behaves the same whether or not you started from the shipped file.

Clear the M1 stack first​

If you came straight from M1, its three containers (frontend, backend, db) are still running from the manual docker run commands, still holding host ports 3000 and 8080, and still attached to the appnet network you created. Compose is about to declare and own that same topology, so the hand-run version has to step aside — otherwise docker compose up in Step 3 fails with port is already allocated. Tear the M1 stack down with M1's own teardown commands:

docker rm -f frontend backend db
docker network rm appnet

Expected output

frontend
backend
db
appnet
note

If you never ran M1, or already tore it down, these commands print No such container / No such network instead — harmless. Either way you now have a clean host for Compose to build on.

Step 1 — Analyze the stack before you write it​

Before writing any YAML, be clear about what you are declaring. The app is three services, and each line of the Compose file falls out of this table:

ServiceImageListens onDepends onNeeds to persist?
frontendbuilt from ./frontend3000backendno (stateless)
backendbuilt from ./backend8080dbno (stateless)
dbpostgres:165432—yes — its data

Two of the three tiers are stateless: kill one, start another, no data is lost. The db tier is the one that holds truth, so it is the one — and the only one — that needs a volume. That single distinction drives the whole file.

The dependency direction matters too: the backend cannot answer a real query until Postgres is accepting connections, and the frontend has nothing to show until the backend is up. You will encode that order so Compose starts them correctly instead of you sequencing five commands by hand.

Step 2 — Write the Compose file​

Write compose.yaml in labs/distributed-app/ with the three services, one network, and one named volume. Run the command below exactly as shown — the heredoc writes the whole file in one shot, so you get a correct file whether or not the shipped copy is already there (it overwrites it with the pre-restart version you need for Steps 3–6):

cat > compose.yaml <<'EOF'
name: fernwood

services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: fernwood
      POSTGRES_PASSWORD: fernwood
      POSTGRES_DB: fernwood
    volumes:
      - db-data:/var/lib/postgresql/data
    networks:
      - appnet
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U fernwood -d fernwood"]
      interval: 5s
      timeout: 3s
      retries: 5

  backend:
    build: ./backend
    image: fernwood-backend:m2
    environment:
      DB_HOST: db
      DB_PORT: 5432
      DB_NAME: fernwood
      DB_USER: fernwood
      DB_PASSWORD: fernwood
    ports:
      - "8080:8080"
    depends_on:
      db:
        condition: service_healthy
    networks:
      - appnet

  frontend:
    build: ./frontend
    image: fernwood-frontend:m2
    environment:
      BACKEND_URL: http://backend:8080
    ports:
      - "3000:3000"
    depends_on:
      - backend
    networks:
      - appnet

networks:
  appnet:
    driver: bridge

volumes:
  db-data:
EOF

Read it against the table from Step 1 and notice what each block replaces from M1:

  • name: fernwood fixes the project name, so every resource Compose creates is prefixed predictably (fernwood_appnet, fernwood_db-data, fernwood-backend-1). Without it, Compose uses the directory name.
  • build: + image: tells Compose to build each image from its Dockerfile and tag it :m2 — the same per-session tag convention as M1's :m1. A learner who never ran M1 can still bring this up; Compose builds what it needs.
  • networks: [appnet] is the M1 --network appnet for every service, declared once. Compose creates the network for you. Service names (db, backend) are the DNS names the others use — exactly the names the app already expects (BACKEND_URL=http://backend:8080, DB_HOST=db).
  • volumes: [db-data:/var/lib/postgresql/data] is new. It mounts a named volume at the path Postgres writes to, so the data lives outside the container.
  • depends_on: { db: { condition: service_healthy } } with the db healthcheck encodes the dependency order. service_healthy waits for pg_isready to pass — not merely for the container to start. That difference (process up vs. database ready) is the whole reason the backend does not race ahead of a database that is still initialising.

Step 3 — Bring the whole stack up​

One command builds the images, creates the network and volume, and starts all three services in order:

docker compose up -d --build

Expected output (build detail abridged; the orchestration tail is the point)

 Image fernwood-backend:m2  Built
 Image fernwood-frontend:m2  Built
 Network fernwood_appnet  Creating
 Network fernwood_appnet  Created
 Volume fernwood_db-data  Creating
 Volume fernwood_db-data  Created
 Container fernwood-db-1  Creating
 Container fernwood-db-1  Created
 Container fernwood-backend-1  Creating
 Container fernwood-backend-1  Created
 Container fernwood-frontend-1  Creating
 Container fernwood-frontend-1  Created
 Container fernwood-db-1  Starting
 Container fernwood-db-1  Started
 Container fernwood-db-1  Waiting
 Container fernwood-db-1  Healthy
 Container fernwood-backend-1  Starting
 Container fernwood-backend-1  Started
 Container fernwood-frontend-1  Starting
 Container fernwood-frontend-1  Started

Read the tail carefully — it is the ordering you asked for, happening on its own. Compose started db, then waited on it (Waiting → Healthy) before it started backend, then started frontend. You wrote the dependencies; Compose sequenced them.

note

The -d runs the stack in the background (detached). Drop it and Compose streams every container's logs to your terminal until you press Ctrl-C — useful when something is misbehaving. The --build is only needed the first time, or after you change app code or a Dockerfile; on later ups Compose reuses the built images.

Step 4 — Verify all three tiers are healthy and talking​

List what Compose is managing:

docker compose ps

Expected output

NAME                  IMAGE                  COMMAND                  SERVICE    CREATED          STATUS                    PORTS
fernwood-backend-1    fernwood-backend:m2    "gunicorn --bind 0.0…"   backend    16 seconds ago   Up 8 seconds              0.0.0.0:8080->8080/tcp, [::]:8080->8080/tcp
fernwood-db-1         postgres:16            "docker-entrypoint.s…"   db         16 seconds ago   Up 15 seconds (healthy)   5432/tcp
fernwood-frontend-1   fernwood-frontend:m2   "docker-entrypoint.s…"   frontend   15 seconds ago   Up 8 seconds              0.0.0.0:3000->3000/tcp, [::]:3000->3000/tcp
note

The Up … durations and the container-creation times will differ on your machine. What matters: all three are Up, db shows (healthy), and only frontend and backend publish host ports — db exposes 5432 only inside the network, never to your host. If any service is missing or shows Exit, jump to Troubleshooting.

Name-based discovery works exactly as it did on the M1 network. Nothing here uses an IP address — the frontend calls the backend by the service name backend:

docker compose exec frontend wget -qO- http://backend:8080/api/health

Expected output

{"db":"connected","hostname":"d43aa84d510c","service":"backend","status":"ok"}

Two facts at once: the name backend resolved over fernwood_appnet, and the backend itself resolved db and connected to Postgres ("db":"connected"). The hostname is the backend container's own ID.

The full path works from your host. Hit the frontend and confirm it fetched the catalogue:

curl -s http://localhost:3000 | grep -oE 'Backend reachable.*db <strong>[a-z]*'

Expected output

Backend reachable · served by <code>d43aa84d510c</code> · db <strong>connected

Open http://localhost:3000 in a browser to see the whole page: the frontend's container ID, the green "Backend reachable" banner, and the six-item Fernwood Goods catalogue grid it fetched from the backend.

Step 5 — Prove the database survives a restart​

This is what the named volume buys you. Write a row into Postgres, tear the entire stack down, bring it back, and confirm the row is still there.

Write a row:

docker compose exec db psql -U fernwood -d fernwood \
  -c "CREATE TABLE IF NOT EXISTS notes (id serial PRIMARY KEY, msg text);"
docker compose exec db psql -U fernwood -d fernwood \
  -c "INSERT INTO notes (msg) VALUES ('written before restart');"
docker compose exec db psql -U fernwood -d fernwood -c "SELECT * FROM notes;"

Expected output

CREATE TABLE
INSERT 0 1
 id |          msg           
----+------------------------
  1 | written before restart
(1 row)

Now take the whole stack down. Plain down removes the containers and the network but keeps named volumes:

docker compose down
docker volume ls | grep fernwood

Expected output

 Container fernwood-frontend-1  Removing
 Container fernwood-frontend-1  Removed
 Container fernwood-backend-1  Removing
 Container fernwood-backend-1  Removed
 Container fernwood-db-1  Removing
 Container fernwood-db-1  Removed
 Network fernwood_appnet  Removing
 Network fernwood_appnet  Removed
local     fernwood_db-data

The containers are gone, but fernwood_db-data is still listed. Bring the stack back and read the table again:

docker compose up -d
sleep 6
docker compose exec db psql -U fernwood -d fernwood -c "SELECT * FROM notes;"

Expected output

 id |          msg           
----+------------------------
  1 | written before restart
(1 row)

The row survived a full teardown because it never lived in the container — it lived in the named volume, which down left alone. A brand-new db container came up and re-attached to the same data. This is the difference between a stateless tier (throw it away freely) and a stateful one (its data is the thing you must not lose).

down -v is the destructive version

docker compose down -v removes the named volume too. That is how you reset the database to empty — useful when you want a clean slate, and exactly what you must not run if you mean to keep the data. You choose at teardown; see the Teardown section.

Step 6 — Watch a crash with nothing watching it​

The app degrades gracefully — you saw that in M1 — but degrading is not recovering. Right now nothing is set to bring a dead container back. Prove it by crashing the backend from the inside, the way a real bug or an out-of-memory kill would take out its main process:

docker compose exec backend sh -c 'kill 1'

That sends SIGTERM to PID 1 (the gunicorn master), so the process exits and the container stops — a stand-in for a crash. Wait a few seconds and look:

docker compose ps -a

Expected output

NAME                  SERVICE    STATUS
fernwood-backend-1    backend    Exited (0) 4 seconds ago
fernwood-db-1         db         Up 17 seconds (healthy)
fernwood-frontend-1   frontend   Up 11 seconds

The backend is Exited and it stays that way — nothing is watching it. The frontend, meanwhile, does its M1 trick and degrades instead of erroring:

curl -s http://localhost:3000 | grep -oE 'Backend (reachable|unavailable)[^<]*'

Expected output

Backend unavailable — showing the app without a catalogue.

A useful page for your users, but the backend is down and will stay down until you notice and act. On a single host with no orchestrator, "notice and act" is a human on call. The next step gives Compose the one lever that removes the human from the simplest case.

Step 7 — Add a restart policy and watch it recover​

Add one line — restart: unless-stopped — to both the backend and frontend services (the two stateless tiers). Rewrite the whole file with the command below; it is the Step 2 file with that single line added to each of those two services:

cat > compose.yaml <<'EOF'
name: fernwood

services:
  db:
    image: postgres:16
    environment:
      POSTGRES_USER: fernwood
      POSTGRES_PASSWORD: fernwood
      POSTGRES_DB: fernwood
    volumes:
      - db-data:/var/lib/postgresql/data
    networks:
      - appnet
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U fernwood -d fernwood"]
      interval: 5s
      timeout: 3s
      retries: 5

  backend:
    build: ./backend
    image: fernwood-backend:m2
    environment:
      DB_HOST: db
      DB_PORT: 5432
      DB_NAME: fernwood
      DB_USER: fernwood
      DB_PASSWORD: fernwood
    ports:
      - "8080:8080"
    depends_on:
      db:
        condition: service_healthy
    networks:
      - appnet
    restart: unless-stopped

  frontend:
    build: ./frontend
    image: fernwood-frontend:m2
    environment:
      BACKEND_URL: http://backend:8080
    ports:
      - "3000:3000"
    depends_on:
      - backend
    networks:
      - appnet
    restart: unless-stopped

networks:
  appnet:
    driver: bridge

volumes:
  db-data:
EOF

Re-apply the file. Both backend and frontend changed, so Compose recreates both of them; db is untouched:

docker compose up -d

Expected output

 Container fernwood-db-1  Running
 Container fernwood-backend-1  Recreate
 Container fernwood-backend-1  Recreated
 Container fernwood-frontend-1  Recreate
 Container fernwood-frontend-1  Recreated
 Container fernwood-db-1  Waiting
 Container fernwood-db-1  Healthy
 Container fernwood-backend-1  Starting
 Container fernwood-backend-1  Started
 Container fernwood-frontend-1  Starting
 Container fernwood-frontend-1  Started

Now crash the backend exactly as before, wait a few seconds, and check the restart count:

docker compose exec backend sh -c 'kill 1'
sleep 6
docker inspect fernwood-backend-1 --format 'RestartCount={{.RestartCount}} Running={{.State.Running}}'
docker compose ps

Expected output

RestartCount=1 Running=true
NAME                  SERVICE    STATUS
fernwood-backend-1    backend    Up 5 seconds
fernwood-db-1         db         Up 40 seconds (healthy)
fernwood-frontend-1   frontend   Up 34 seconds

The backend crashed and came back on its own — RestartCount=1, Up 5 seconds, no human involved. Give it a moment and the frontend banner is green again. That is the whole value of a restart policy: the simplest failure — one container's process dies — now recovers automatically.

A restart policy answers a crash, not an operator

The policy fires when a process dies on its own. It deliberately does not fight you: if you run docker compose stop backend (or docker compose kill backend), that is you telling Docker to stop it, so it stays stopped and RestartCount does not move. unless-stopped means "keep it running unless a human stopped it." Restarting a crash is automatic; undoing your own stop is not.

This fixes the container-died case. It does not fix the host-died case. restart: unless-stopped is the Docker daemon on this machine restarting a container on this machine. If the machine itself goes down — kernel panic, power loss, the VM your Docker runs in is killed — the daemon that would do the restarting is gone too, and there is no second host for the work to move to. That ceiling is the whole reason Session 3 introduces Kubernetes; the Deep Dive makes it concrete.

Troubleshooting​

backend stuck Created / never starts, or up seems to hang

The backend waits for db to be healthy (condition: service_healthy). If Postgres is slow to initialise on first run, this is normal — give it up to ~30s. If it never becomes healthy, check the db logs with docker compose logs db; a corrupt or half-initialised volume is the usual cause. As a reset, docker compose down -v (this deletes the db data) and up again.

port is already allocated on 3000 or 8080

The most likely cause is the M1 seam: you came straight from M1 and its manually-run frontend/backend/db containers are still holding ports 3000/8080. Clear them with the M1 teardown from Clear the M1 stack first (docker rm -f frontend backend db and docker network rm appnet), then re-run docker compose up -d. If something else holds the port, find it with docker ps (or your OS's port tools) and stop it, or change the left side of the mapping in compose.yaml (e.g. "3001:3000") and use the new port — the right side (the container port) stays the same.

Health shows "db":"unavailable" even though db is up

The backend connects as user/db/password fernwood. If you edited the POSTGRES_* values on db but not the matching DB_* on backend (or vice versa), the credentials no longer match. Make the two blocks agree, then docker compose up -d to re-apply. Note the backend still returns HTTP 200 — this is graceful degradation working, not a crash.

Changes to compose.yaml don't seem to take effect

docker compose up -d re-reads the file and recreates only what changed. If you changed app code (not just the YAML), add --build so the image is rebuilt: docker compose up -d --build. Confirm what Compose will actually run with docker compose config, which prints the fully-resolved spec.

Teardown​

You have a real choice here, because this stack now holds data. Pick based on whether you want to keep the database between sessions.

Keep the data (removes containers and network, keeps the fernwood_db-data volume):

docker compose down

Wipe everything, including the database (use this for a clean slate):

docker compose down -v

Expected output (the -v form)

 Container fernwood-db-1  Removing
 Container fernwood-db-1  Removed
 Network fernwood_appnet  Removing
 Volume fernwood_db-data  Removing
 Network fernwood_appnet  Removed
 Volume fernwood_db-data  Removed

The built images (fernwood-frontend:m2, fernwood-backend:m2) stay in your local cache either way — you reuse them in the next session, so there is no need to delete them. Confirm nothing is left running with docker compose ps.

What you proved​

  • One compose.yaml replaces M1's create-network-then-five-docker run sequence: the whole 3-tier topology is declared once and brought up, in dependency order, by a single command.
  • Compose gives the stateful tier a named volume, so the database's data survives a full down/up — the stateless tiers need no such thing.
  • depends_on: condition: service_healthy waits for real readiness, not just container start, so the backend never races a database that is still initialising.
  • A restart policy recovers the simplest failure — a container whose process crashed — with no human in the loop, but only on this host.
  • That last point is the ceiling: nothing here reschedules work to another machine, does a zero-downtime rolling update, or survives the host itself dying. Those are the gaps Kubernetes exists to fill, and where Session 3 begins. The Deep Dive demonstrates the ceiling rather than just asserting it.
