End-to-End Application Deployment with Docker & Compose

▶ M2 · End-to-End Application Deployment with Docker & ComposeOpen fullscreen ↗

In M1 you got the three tiers of Fernwood Goods talking to each other over a Docker network. To do it you ran a sequence: create the network, start Postgres with three environment flags, start the backend with its port mapping, start the frontend with its port mapping. It worked. But think about what you are left with afterward. The knowledge of how the app is wired — which container talks to which, on what network, with which flags, in what order — lives only in your shell history and your head.

Now imagine the handover. A new QA joins the cohort on Monday and needs the app running to reproduce a bug. You send them the five commands. They miss the POSTGRES_DB=fernwood flag on one line, so the backend reports the database as unavailable, and they spend an hour convinced they have found a real defect. Or you come back to the project after three weeks on something else and cannot remember whether the backend port was 8080 or 8000. The manual sequence is fine the first time and a problem every time after. This module fixes that by writing the whole topology — how every container connects to every other — down in one file that anyone can run and no one has to remember.

The analogy: a prompt book, not shouting from the wings​

In live theatre, the stage manager runs the show from a single master document called the prompt book. It lists every actor, every prop, and every cue: who enters, carrying what, on which line, in what order. Every performance runs from that one book. The show is repeatable because it is written down.

Imagine running the show without it — standing in the wings, pushing each actor on stage by hand at the moment you think is right, every single night. That is M1: you, in the wings, starting each container by hand in the order you hope is correct. Docker Compose is the prompt book. You write down the cast (the services), their props (images, ports, environment, volumes), and their cues (which service waits for which), and then you "call the show" with one command: docker compose up. The wiring is no longer in your memory; it is in a file, in version control, that runs the same way for everyone.

Keep this in mind. The value is not that Compose is easier to type, though it is. The value is that the topology becomes a file you keep. You can read it, review it, and see what changed, instead of a ritual you re-perform each time.

From "install on a server" to "declare a stack"​

Before containers, deploying this app meant preparing a host: install a specific Python, install Node, install and configure a Postgres server, set up a process manager to keep each service running, edit config files so each process knew where the others were, and hope the next server you set up matched. Every one of those steps was a chance for two servers to drift apart, that is, to slowly stop matching each other. The classic "works on my machine" problem comes from exactly this hand-built, one-off style of setting up servers.

Containers already closed most of that gap in M1: each tier ships as an image with its runtime and dependencies baked in, so it runs the same on any host with Docker. What containers alone did not give you is a way to describe the whole application — all the tiers together, plus the network and storage that connect them — as one unit. That is the gap Compose fills. You move from procedural ("run these commands in this order to assemble the app") to declarative ("here is the app I want; make it so"). You describe the desired end state; Compose figures out the steps to reach it. That same declarative shift is exactly how you will describe workloads to Kubernetes from Session 3 on. That is why it is worth getting comfortable with it here first, on a single host, where it is simple.

Read the app as a system first​

A Compose file is only as good as your understanding of the app it describes. So before any YAML, look at Fernwood Goods as a system of three services:

ServiceImageRolePortDepends onState
frontendbuilt from ./frontendRenders the UI, fetches catalogue3000backendstateless
backendbuilt from ./backendJSON API, reports DB status8080dbstateless
dbpostgres:16Holds the data5432—stateful

Three facts fall out of this table, and each one becomes a decision in the Compose file:

  • Images. Two tiers are built from local Dockerfiles (your code); one is an off-the-shelf image (postgres:16). Compose can both build the first kind and pull the second.
  • Dependencies. The arrows point one way: frontend → backend → db. Nothing points back. That ordering is what Compose needs to know so it starts db before backend before frontend.
  • State. Only db holds data you cannot afford to lose. The frontend and backend are interchangeable — kill one, start another, nothing is lost. The database is not: destroy its container carelessly and its data goes with it, unless you have deliberately put that data somewhere the container's lifecycle does not touch. That "somewhere" is a volume.

This is the analysis the second learning objective asks for, and it is not busywork. The difference between a stateless tier, that is one that holds no data of its own, and a stateful tier, one that does, is the single most important difference in this whole course. It is why the frontend becomes a Deployment in Session 5 and the database becomes a StatefulSet in Session 6. It starts here, as one column in a table.

What Docker Compose actually is​

Two things share the name "Compose", and it helps to keep them separate:

  1. A file format — compose.yaml, a declarative description of a multi-container application: its services, the networks that connect them, and the volumes that keep their data. This is the prompt book.
  2. A command-line tool — docker compose, which reads that file and makes reality match it. up creates everything the file describes; down removes it; ps, logs, and exec operate on the whole stack by service name.

Here is the shape of the file for our three services (you build it up for real in the lab):

name: fernwood

services:
  db:
    image: postgres:16
    volumes:
      - db-data:/var/lib/postgresql/data
    healthcheck:
      test: ["CMD-SHELL", "pg_isready -U fernwood -d fernwood"]

  backend:
    build: ./backend
    ports: ["8080:8080"]
    depends_on:
      db:
        condition: service_healthy

  frontend:
    build: ./frontend
    ports: ["3000:3000"]
    depends_on: [backend]

volumes:
  db-data:

Every M1 flag has a home here. --network appnet on five commands becomes one network all services share. -e POSTGRES_DB=fernwood becomes an environment: block. -p 8080:8080 becomes a ports: entry. --name backend becomes the service key backend, which is also its DNS name, the name other services use to reach it. And two things that had no equivalent in M1 appear: a volume for the database's data, and a depends_on that writes down the ordering you previously did by hand.

Why the file beats the five commands​

The gain is not only about saving keystrokes. Four solid properties come from declaring the stack instead of running it:

  • One source of truth. The wiring is in a file you can read, review in a pull request, and compare when it changes, not lost in your terminal history. The new QA on Monday runs docker compose up and gets the exact topology you intended, flags and all.
  • Idempotence, that is, running it twice is safe. docker compose up brings reality to the state you described and then stops. Run it again and Compose changes only what has drifted, that is, what no longer matches the file. It does not blindly recreate what is already correct. Change one line and re-run, and only the affected service is recreated. There is no "did I already start the database?" bookkeeping.
  • Ordering by declaration. depends_on with condition: service_healthy lets you say "start the backend only once the database is actually ready to accept connections," and Compose waits. That is stronger than "start the database first". It is the difference between the container being up and the database being ready, which are seconds apart on first boot and exactly the window a race condition (a bug that shows up only when two things happen in the wrong order) hides in.
  • Whole-stack operations. docker compose logs, ps, exec, down all understand the stack as a unit. You stop reasoning about individual containers and start reasoning about the application.

Volumes: giving the stateful tier a memory​

A container's own filesystem is disposable. When you remove the container, everything written inside it is gone. For the frontend and backend that is exactly what you want — they hold nothing worth keeping. For Postgres it is a disaster: the database is its data.

A named volume solves this by storing the data outside the container's lifecycle. You mount it at the path Postgres writes to (/var/lib/postgresql/data), and from then on the data lives in the volume, not the container. Remove and recreate the db container — during an image upgrade, say, or a config change — and the new container re-attaches to the same volume and finds all the data still there. In the lab you prove this directly: write a row, tear the whole stack down with docker compose down, bring it back, and read the row again. It survives, because down removes containers but leaves named volumes alone. Only the explicit down -v deletes the data.

This is your first hands-on look at persistence, that is, keeping data safe across restarts, as a real concern. It is deliberately simple here: one volume, one database, one host. Session 6 takes the same idea and gives it the machinery a real cluster needs: StorageClasses, PersistentVolumeClaims, and StatefulSets. The concept does not change; only the scale and the guarantees do.

The wall Compose runs into​

Compose is genuinely good at what it does, and for a single host it may be all you ever need. It is worth being just as clear about where it stops, because that boundary is the reason the rest of this course exists.

Everything Compose does happens on one machine. It has exactly one lever for failure, a restart policy, restart: unless-stopped, which tells the Docker daemon, the background Docker process on this host, to restart a container whose process crashed. In the lab you watch it work: crash the backend and it comes back on its own. But notice what is doing the restarting — the Docker daemon on this host. That gives you three hard limits, and none of them has a fix inside Compose:

  • No rescheduling. If the host itself dies — kernel panic, power loss, the VM is killed — the daemon that would restart your containers dies with it. There is no second machine for the work to move to, because Compose only knows about this one.
  • No rolling updates. To ship a new version you up again, and the container is replaced in place. There is no built-in way to bring up the new version, shift traffic gradually, and retire the old one with zero downtime.
  • No scaling past this one machine. You can ask Compose for more copies of a service, but they all land on this one machine and compete for its CPU, memory, and, as you will see, its ports.

The Deep Dive shows each of these rather than just naming them. They are not Compose's failings. They are simply the edge of what a single-host tool is for. Crossing that edge, that is, running the app across many machines, rescheduling it when one dies, updating it without downtime, is the job of an orchestrator, a system that runs your app across many machines and keeps it healthy. That is where Session 3 picks up with Kubernetes.

What you will do in the lab​

You will write compose.yaml for all three tiers, bring the stack up with one command, and verify the tiers discover and reach each other by service name — the same name-based discovery from M1, now declared instead of typed. You will prove the named volume by surviving a full teardown, then crash the backend to see it stay dead, add a restart policy, and watch it recover. By the end you will have a single file that stands up the whole application, and a clear, hands-on sense of the ceiling that single file cannot break through.
