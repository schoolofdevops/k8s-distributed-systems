Deep Dive — Where a single Docker host stops

The lab left you with a working conclusion: a restart policy recovers a crashed container. That is true, and it is the correct first tool. This Part 2 pushes on it until it breaks — because the exact shape of how it breaks is the specification Kubernetes is built against, and you will understand Session 3 far better if you have watched the ceiling with your own eyes rather than been told about it.

Everything below runs against the same stack from the lab, but the restart counters need to start from a known zero. The lab already crashed the backend at least once, so its RestartCount is no longer 0 — reset the stack to a clean baseline (this also wipes the db volume, which none of the sections below need) and let it come back up healthy:

cd labs/distributed-app
docker compose down -v
docker compose up -d --build

Give it a few seconds — the backend waits on the db's healthcheck — then confirm the backend is running with a zero restart counter before you continue:

docker inspect fernwood-backend-1 --format 'RestartCount={{.RestartCount}} Running={{.State.Running}}'

Expected output

RestartCount=0 Running=true

1. A restart policy is a supervisor, and it has a memory​

In the lab you crashed the backend once and it came back. Watch what happens when the same process keeps dying — this is the failure mode that matters in production, where a bad config or a poisoned input can send a container into a loop, not just down once. Crash it three times in a row and read the restart counter each time:

for i in 1 2 3; do
  docker compose exec backend sh -c 'kill 1'
  sleep 5
  echo "after crash $i: $(docker inspect fernwood-backend-1 --format 'RestartCount={{.RestartCount}} Running={{.State.Running}}')"
done

Expected output

after crash 1: RestartCount=1 Running=true
after crash 2: RestartCount=2 Running=true
after crash 3: RestartCount=3 Running=true

The daemon restarts the container every time and keeps a running RestartCount. This is real supervision: the Docker daemon is watching the container's main process and reacting to its exit. Two things are worth naming precisely, because they are exactly what an orchestrator does differently:

  • The counter only goes up; it never resets on its own while the container keeps failing. Docker also applies an increasing delay between restarts (a backoff) so a container that dies instantly in a loop does not peg the CPU. But there is no notion of "this container has restarted 200 times, it is clearly broken, stop trying and tell someone." Docker will restart it forever.
  • The supervisor is the local daemon. Its entire universe is this one host. It can restart a process; it cannot conclude that the process is unschedulable here and place it elsewhere.

Kubernetes keeps the same idea — a controller watching and restarting — but adds the two things Docker does not: a CrashLoopBackOff state that surfaces "this is failing repeatedly" as first-class status, and a scheduler that can place the workload on a different node. Hold that comparison; it is the spine of the next several sessions.

2. stop is not a crash — and that distinction is deliberate​

It is easy to assume restart: unless-stopped means "always keep this running." It does not, and the gap is important the first time an on-call engineer stops a container on purpose and is confused that it does not fight them. Read the restart counter, stop the backend deliberately, and read the counter again:

docker inspect fernwood-backend-1 --format 'RestartCount before stop={{.RestartCount}}'
docker compose stop backend
sleep 5
docker compose ps -a
docker inspect fernwood-backend-1 --format 'RestartCount after stop={{.RestartCount}}'

Expected output

RestartCount before stop=3
NAME                  SERVICE    STATUS
fernwood-backend-1    backend    Exited (0) 5 seconds ago
fernwood-db-1         db         Up 48 seconds (healthy)
fernwood-frontend-1   frontend   Up 42 seconds
RestartCount after stop=3

The container is Exited and the counter did not move — the policy left it alone. Docker distinguishes a process dying on its own (the restart policy fires) from an operator asking for it to stop (it does not). unless-stopped literally means "restart it unless a human stopped it," and the daemon records that intent. Bring it back deliberately:

docker compose start backend

Why this matters: a restart policy is not a health guarantee, it is a crash responder. It has no opinion about whether your app is correct — only about whether its main process is running. A container that boots, answers "yes I am alive," and serves wrong data forever is, to a restart policy, perfectly healthy. Kubernetes separates these into distinct probes (liveness vs. readiness), which is why Session 3 spends real time on them; here, notice only that Compose has the one crude lever and no finer control.

3. The scale ceiling: one host, one port​

The most concrete single-host limit is one you can hit in a single command. Ask Compose to run three copies of the backend:

docker compose up -d --scale backend=3

Expected output

 Container fernwood-backend-1  Running
 Container fernwood-backend-2  Created
 Container fernwood-backend-3  Created
 Container fernwood-backend-3  Starting
Error response from daemon: failed to set up container networking: driver failed programming external connectivity on endpoint fernwood-backend-3 (2deccd0f4fd42…): Bind for 0.0.0.0:8080 failed: port is already allocated

Look at the result:

docker compose ps -a

Expected output

NAME                  SERVICE    STATUS
fernwood-backend-1    backend    Up 15 seconds
fernwood-backend-2    backend    Created
fernwood-backend-3    backend    Created
fernwood-db-1         db         Up 39 seconds (healthy)
fernwood-frontend-1   frontend   Up 33 seconds

Compose was willing to create three backend containers, but only one could start. The other two are stuck in Created — they exist but cannot run, because the first one already published host port 8080, and a host port can be bound by exactly one process. This is not a Compose bug; it is physics of a single machine. You published 8080:8080 so the backend is reachable from your host, and there is only one 8080 on this host.

You could work around it here — drop the published port and let something in front load-balance, or map each replica to a different host port — but every workaround runs into the same underlying fact: these copies all share one machine's ports, CPU, and memory. "Scale" on a single host means "until this box is full," and after that there is nowhere to go. Scale it back before moving on:

docker compose up -d --scale backend=1

The thing a cluster adds is precisely what is missing here: N copies spread across M machines, each with its own port space, sitting behind one stable address. That is a Service in front of a Deployment, and it is Sessions 4 and 5.

4. The ceiling you cannot demo: the host itself​

The three limits above have a common root you cannot safely reproduce on your laptop — killing the machine — so reason it through instead. Every recovery mechanism you have used lives inside one host:

The restarting is done by the daemon. The daemon runs on the host. If the host dies, the daemon dies with it, and every container it was supervising is gone at the same instant — there is no surviving supervisor to notice, and no second machine to move the work onto. The named volume that made your database durable is on that host's disk too; if the disk goes, "durable" was only ever durable against a container being removed, not against the host being lost.

Contrast that with what an orchestrator is for:

The supervisor is no longer on any single node — it is the control plane, watching all of them. When a node dies, something outside that node observes it and places the lost work elsewhere. That is the one capability a single host can never have, no matter how good its restart policy is, because the supervisor and the thing it supervises share a fate.

This is not an argument that Compose is inadequate. For a single-host deployment — a dev environment, a CI runner, a small internal tool that can tolerate the host as a single point of failure — Compose is often exactly right, and reaching for Kubernetes would be over-engineering. The point is to know the boundary precisely, so you choose the orchestrator when the workload actually crosses it and not before.

Where you will use this​

  • In a design review, when someone proposes "we'll just run it with Compose and a restart policy": you can now say precisely what that does and does not buy — crash recovery yes, host-failure survival and rolling updates no — and make the single-host-SPOF trade-off explicit instead of discovering it during an outage.
  • On call, when a container is flapping: you understand that RestartCount climbing and a growing restart backoff is Docker doing its job, not the fix, and that the missing piece ("stop trying, this is broken, page someone") is exactly what a CrashLoopBackOff-style state gives you in the cluster.
  • When you hit port is already allocated scaling anything on one host, you will recognise it immediately as the single-port ceiling rather than a misconfiguration, and know that the real answer is a load balancer in front of replicas spread across hosts — the Service/Deployment pattern coming in Sessions 4 and 5.

Tear down when you are done (keep or wipe the data as you prefer — see the lab's Teardown):

docker compose down
