Distributed Systems in a Cloud Native Pattern

▶ M1 · Distributed Systems in a Cloud Native PatternOpen fullscreen ↗

You already ship software in containers. Over the next eight sessions you will take one ordinary 3-tier application (a web frontend, an API backend, and a database) and move it all the way from "three containers I start by hand" to "a self-healing, scalable service running on Kubernetes." This first part is the map for that journey. Before you touch a single docker command, you need a clear picture of what really changes when an application stops being one process and becomes several processes that talk over a network. Everything else in the course, every Service, every Deployment, every NetworkPolicy, is an answer to a problem this part names.

The product and journey you will build​

Your sample system is Fernwood Goods, a simple storefront:

  • frontend: shows the catalogue page
  • backend: provides products and health status
  • db: stores product data

In Session 1, this is one real stack on one machine. In later sessions, the same stack grows into Kubernetes without changing business logic.

What this module proves​

By the end of this module, you should be able to say this in one line:

If three app containers are on the same user-defined network and use names, they can find each other reliably without hardcoded IPs.

You will do this in three short steps:

  1. Build the two application images (fernwood-backend:m1, fernwood-frontend:m1).
  2. Create one app network (appnet) and start frontend, backend, and db on it.
  3. Prove the path works by name: frontend -> backend -> db.

Then you will test the same app on default Docker network modes and see exactly why appnet is the safe default for this app.

Why this matters at work​

Think about the last time a request failed in your system and the error pointed at the wrong place. The frontend logged a timeout, but the real problem was the database three hops away. Or a QA colleague filed a bug that only shows up when two services run on different machines, never on their laptop. That gap, between where a failure shows up and where it starts, is the built-in tax of a distributed system. If your team is moving a monolith (one big program) to microservices (many small services), you are not just reorganising code. You are signing up to pay that tax on every request, every test run, and every deploy. The goal of this part is to make that tax visible and predictable, so the rest of the course can teach you the tools that manage it.

From one process to many: what a distributed system is​

Analogy

A single-process application is like a home kitchen. The cook, the ingredients, and the stove are all in one room, and "passing the salt" is just reaching across the counter. A distributed system is like a restaurant with a separate kitchen, bar, and store room, connected by waiters. Nothing is on the same counter anymore. Every "pass the salt" is now a request that travels. It can be delayed, it can arrive twice, or it can find nobody home. The food is the same. The coordination is the whole new job.

A distributed system is a set of independent parts that run on separate machines (or separate containers) and work together only by passing messages over a network. The moment you split a monolith into a frontend, a backend, and a database, you cross a line that changes three everyday activities.

Debugging changes. In a monolith, a stack trace is the whole story. It points at the line that failed and the calls that led there, all in one place. Split the app and a single user action becomes a chain of network calls across processes. When it fails, the frontend's error (say, "upstream timeout") is only a symptom. The real cause sits in another process's logs, on another machine, maybe even at another time. So now you debug by correlating, that is, matching one request across several logs, instead of reading one trace. That is why request IDs, structured logs, and later distributed tracing (following one request as it hops from service to service) stop being nice-to-haves.

Testing changes. A monolith test can call a function and check the return value. Once there is a network in the middle, "the backend is slow," "the backend returned a 500 error," and "the backend is simply gone" are three different outcomes your frontend must handle. None of them happen when both run in the same process on a developer's laptop. The interesting bugs now live in the seams between services, not inside any one service. That is exactly why integration testing and contract testing (checking that two services keep the same request format and response format) matter more here than they did before.

Deployment changes. One process means one deploy. It is either up or down. Several processes get deployed on their own, and for real stretches of time they run at different versions. A new backend must not break the frontend that still speaks the old contract. So deciding who ships when, and keeping the pieces working together across a rollout, becomes an ongoing operations job, not a one-time release step.

Underneath those three, the same three technical concerns keep coming up. They are worth naming plainly, because the rest of the course is organised around them.

State: decide where the truth lives. In the home kitchen, there is one fridge and everyone trusts it. Split the system up and you must decide who owns each piece of truth, and how the others get a matching view of it. A stateless part keeps nothing saved between requests. Any copy can serve any request, because the answer does not depend on which copy you happened to reach. A stateful part owns data that must survive and stay correct. In our sample app the database owns the saved state (the durable state). The frontend and backend are stateless on purpose. Get this ownership wrong and the failure is very real. If you let the backend keep user data in its own memory and then run three copies of it, the same user gets three different answers, depending on which copy the load balancer picked. That habit, "push state to the edges, keep the middle stateless", is why, later, the frontend and backend become easily scaled Deployments while Postgres becomes a carefully managed StatefulSet.

Scalability: handle more by adding copies. There are two ways to handle more load, and they work quite differently. Vertical scaling gives one instance a bigger machine, that is, more CPU and more memory. It is simple, but it has a ceiling (the biggest machine you can buy) and a single point of failure (that one machine). Horizontal scaling adds more instances and spreads the load across them, with no hard ceiling and no single point of failure. Distributed systems are built to scale horizontally, but only the stateless tiers can. You can run ten copies of the stateless backend behind one address, and any of them can serve any request. You cannot just run ten copies of Postgres the same way. They each own data, and ten separate copies would drift apart at once. So statelessness is the precondition for horizontal scaling, which is why the two concerns above are really one concern seen twice.

Failure handling: partial failure is the normal case. In one process, either everything runs or the process crashes. There is no in-between. Across a network there is a third state, and it shows up in most real incidents: one part is down or slow while the rest keeps running. Take a failure your team will surely hit. The backend gets slow, so the frontend's calls start timing out. The frontend retries, which adds more load to the already-struggling backend, which makes it slower still. This is a retry storm, and it turns a small hiccup into a full outage. A solid distributed system treats a missing or slow dependency (a service it needs but cannot reach) as an expected thing, not a disaster. Our sample app is built to show exactly this. The frontend still renders a useful page and shows a clear "backend unavailable" banner when the backend is gone. The backend still answers and reports db: unavailable instead of returning a 500 error when Postgres cannot be reached. Graceful degradation, that is, dropping to a smaller but still useful service instead of failing outright, is a design choice you make on purpose. You will see it in the code you run today.

The cloud native system layers: containers and orchestration​

Analogy

A shipping container does not make cargo smaller. It gives every load a standard size and interface on the outside, so any crane, ship, or truck can carry it without knowing what is inside. An OCI image (a standard container format) does the same for software. Whatever language or libraries sit inside, the outside package is the same.

"Cloud native" is a way of building systems that uses this container pattern. Applications are packaged as images, run as throwaway instances, and are managed by software instead of by hand. Two layers make it work. Being clear about which layer does which job really matters, because the rest of the course lives on the seam between them.

  • Containers solve packaging and isolation for one instance on one machine. Docker gives you a repeatable image and an isolated process with its own filesystem and its own network namespace (its own private view of the network). Docker will start a container, stop it, and connect a handful of them on a single machine. That is where its job ends: one machine, with instances you start and wire up yourself. Docker has no opinion about what happens when that machine dies, or when you need forty copies across ten machines.
  • Orchestration solves running many instances across many machines, and keeping them running. Placing containers onto machines, restarting the ones that die, replacing whole machines, spreading copies so the service stays available, and wiring up service discovery and load balancing: that is Kubernetes' job, and it is why Sessions 3 to 8 exist. Docker gets our app connected on one machine. Kubernetes runs it as a service that survives machines coming and going.

Keep this boundary clear, because it is easy to blur. Docker packages and runs one container. Kubernetes decides where and how many containers run, and keeps that true over time. Sessions 1 and 2 live fully on Docker's side of the seam. Sessions 3 to 8 live on Kubernetes' side.

The wider ecosystem around these two layers is listed by the Cloud Native Computing Foundation (CNCF), hundreds of projects for networking, storage, observability, security, and delivery. You do not need to memorise every project. You need the map. Kubernetes sits at the centre as the shared control plane (the central brain that decides what runs). The tools your team already uses plug into it around the edges. Your CI/CD pipeline (the build-and-ship automation) builds an image and hands Kubernetes a new desired state. A service mesh manages the service-to-service traffic between the things Kubernetes runs. Your observability stack (metrics, logs, and traces) watches what Kubernetes is running and tells you when the partial failures above are happening. Each of these sits on top of, or beside, Kubernetes. None of them replace it. So when a new tool shows up in a design review, the useful question is "which layer is this, and how does it plug into the control plane?" This course gives you the control plane those tools attach to.

Portability: OCI images and the Kubernetes API​

Two standards are the reason "build once, run anywhere" is real and not just a slogan. They map cleanly onto the two layers above.

The OCI image is the portable unit of software. When you run docker build in this course, you produce an image in the Open Container Initiative (OCI) format. At heart that image is a manifest, a small document that lists a set of read-only filesystem layers plus the settings to run them (the command, the environment, the exposed ports). Each layer is named by a digest (a hash of its exact bytes), so the image is the same bytes wherever it is used. That is why containerd, CRI-O, Podman, and every Kubernetes node's runtime all understand it. They read the same manifest and stack the same layers. The image you build on your laptop in Session 1 is the byte-for-byte same artifact Kubernetes pulls and runs in Session 3. Nothing is rebuilt or translated. That is the portability guarantee, and it is why we build the images now and reuse them without any changes.

The Kubernetes API is the portable unit of intent. Instead of a script that says "do these steps on this machine," you write a declarative object, that is, "I want three copies of this image, reachable under this name," and you hand it to the API. This is the key difference between imperative and declarative. An imperative script spells out how, and it is tied to the exact machine, order, and starting state it was written for, so it breaks the moment any of those differ. A declarative object states what you want to be true. Any conformant cluster, on any cloud, or on your laptop under KIND, then reconciles reality toward that same desired state (keeps checking and adjusting until reality matches) in the same way. Move to a new cluster and your manifests come with you without any changes, while a pile of setup scripts would have to be rewritten. You will start writing these objects in Session 3. For now, keep in mind that the image and the desired-state object are the two things that make your work portable.

What you do with this map next​

You now have the map. A distributed system trades one process's simplicity for independent parts that must coordinate over a network. That changes how you debug, test, and deploy, and it forces you to plan for state, scaling, and partial failure. The cloud native world answers this with two layers, containers and orchestration, and two portability standards, the OCI image and the Kubernetes API. The rest of the course turns that map into working infrastructure.

The very first thing that map asks for is simple and immediate. If the pieces coordinate over a network, they first have to find and reach each other. That is a networking problem, and on a single machine it is Docker's to solve. Part 2 picks up right there: how Docker gives a container a network, and how to make our three tiers find each other by name. The lab right after puts it into practice. See you there.
