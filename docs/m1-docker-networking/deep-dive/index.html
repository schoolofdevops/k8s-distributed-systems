Deep Dive — what a Docker network driver actually does

The lab proved that containers on appnet find each other by name and that the default bridge cannot do the same. That is the behaviour. This page is the machinery under it: the Linux bridge and veth pairs a driver builds, the iptables NAT rules it programs, the resolver it plants at 127.0.0.11 to answer names, and why none of it can cross to a second host without a fundamentally different driver. You reach for this layer the moment "the app works but a container cannot reach X" lands on you — when the symptom is a network path, the fix is almost never in the application code, and knowing what the driver actually built is the difference between guessing and reading the wiring.

Where this picks up

This page inspects the live wiring of the M1 app, so it needs the three tiers running on appnet. The block below rebuilds that state from scratch and is safe to re-run — it force-removes any existing containers first, so running it fresh or right after the lab gives the same result. Several inspection commands use nicolaka/netshoot on the host network stack (the standard way to see Docker's bridges and iptables from inside the daemon's world — necessary on macOS/Windows where the daemon runs in a VM); the first use pulls the image automatically.

cd labs/distributed-app
docker network create appnet 2>/dev/null || true
docker rm -f db backend frontend 2>/dev/null || true
docker run -d --name db --network appnet \
  -e POSTGRES_USER=fernwood -e POSTGRES_PASSWORD=fernwood -e POSTGRES_DB=fernwood postgres:16
docker run -d --name backend --network appnet -p 8080:8080 fernwood-backend:m1
docker run -d --name frontend --network appnet -p 3000:3000 fernwood-frontend:m1

1 — A "network" is a Linux bridge with veth patch cables​

Analogy

Picture a network switch bolted into a wiring closet. The switch is a box that forwards frames between whatever is plugged into it; each device reaches it by a patch cable with a plug on each end. The Docker bridge driver builds exactly this in software: the "switch" is a Linux bridge device, and each container is plugged in with a veth pair — a virtual cable whose two ends are a linked pair of interfaces, one inside the container's network namespace (its eth0), the other on the bridge.

When you ran docker network create appnet, the driver created a Linux bridge on the host named br-<first 12 chars of the network ID>. Find the network ID, then find its bridge:

docker network inspect appnet --format 'id={{.Id}} subnet={{range .IPAM.Config}}{{.Subnet}}{{end}}'
docker run --rm --net host --privileged nicolaka/netshoot ip -br link show type bridge

Expected output (the network ID, then the host bridges — extra br-… lines from other Docker projects on this machine are omitted here)

id=50d8325d9c7af3e6b6b4dc28d054409b18af21961b10924921e34cb5787d78b9 subnet=172.27.0.0/16
docker0          DOWN           86:e6:06:91:ab:63 <NO-CARRIER,BROADCAST,MULTICAST,UP> 
br-50d8325d9c7a  UP             86:3d:1c:78:66:26 <BROADCAST,MULTICAST,UP,LOWER_UP>

The br-… device whose name matches the start of the network ID is appnet. (The MAC addresses above are this host's; yours will differ.) The default network is the separately-named docker0 bridge — two different switches, which is the whole reason containers on one cannot see containers on the other. Now look at the patch cables plugged into that bridge — one veth end per running container:

docker run --rm --net host --privileged nicolaka/netshoot bridge link

Expected output (veth lines for every bridge on the host — other Docker/KIND projects' veths are omitted here; find yours by master br-<your network ID>)

157: vethc53c126@eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 master br-50d8325d9c7a state forwarding priority 32 cost 2 
158: veth3bab7aa@eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 master br-50d8325d9c7a state forwarding priority 32 cost 2 
159: veth425ecf4@eth0: <BROADCAST,MULTICAST,UP,LOWER_UP> mtu 1500 master br-50d8325d9c7a state forwarding priority 32 cost 2
note

On a machine running other Docker projects or a KIND cluster, this list is longer — every bridge's veths show up here, not just appnet's. Filter for the three lines whose master matches your appnet bridge (br-<your network ID> from the previous step).

Three veth… lines, one per running container, all with master br-50d8325d9c7a — they are the host ends of the cables into appnet's bridge. Each veth… line is one end of a cable; its partner is the eth0 your container sees. The container's own view is just an ordinary interface with an address from the network's subnet:

docker exec backend ip -br addr show eth0

Expected output

eth0@if158       UP             172.27.0.3/16

The @if158 is this interface's link to its veth partner (peer index 158) back on the host — the same 158: veth3bab7aa@eth0 you saw plugged into the bridge above. The address is from appnet's subnet. At work this is the first thing to check when a container "has no network": a container whose eth0 is missing or whose veth never landed on the expected bridge was attached to the wrong network (or none), and no amount of application-level retry will fix a cable that was plugged into the wrong switch.

2 — NAT: the iptables rules the driver programs for you​

Analogy

A container's 172.x address is an internal office extension — useful inside the building, meaningless to the outside world. Reaching the internet, or being reached from your laptop, needs a receptionist who rewrites addresses at the door. That receptionist is NAT, and the driver programs it as iptables rules the instant you create a network or publish a port.

Two translations matter. Outbound: traffic leaving a container for the internet gets its source address rewritten to the host's (a MASQUERADE rule scoped to the network's subnet). Inbound: a published port like -p 8080:8080 installs a DNAT rule that rewrites traffic arriving on the host port to the container's address and port. See the inbound rules the driver wrote for your published ports:

docker run --rm --net host --privileged nicolaka/netshoot iptables -t nat -S DOCKER

Expected output (DNAT lines for every published port on the host — other Docker/KIND projects' port mappings are omitted here; find yours by the --to-destination matching your appnet subnet)

-N DOCKER
-A DOCKER ! -i br-50d8325d9c7a -p tcp -m tcp --dport 8080 -j DNAT --to-destination 172.27.0.3:8080
-A DOCKER ! -i br-50d8325d9c7a -p tcp -m tcp --dport 3000 -j DNAT --to-destination 172.27.0.4:3000

The DNAT lines mapping host 3000/8080 to a container address are what make curl localhost:3000 from your host reach the frontend. Now the outbound side — the masquerade rule for the app's subnet:

docker run --rm --net host --privileged nicolaka/netshoot iptables -t nat -S POSTROUTING

Expected output (the appnet rule first, then docker0; masquerade rules for other Docker projects' subnets on this machine are omitted)

-P POSTROUTING ACCEPT
-A POSTROUTING -s 172.27.0.0/16 ! -o br-50d8325d9c7a -j MASQUERADE
-A POSTROUTING -s 172.17.0.0/16 ! -o docker0 -j MASQUERADE

This is why "published the port but still connection-refused" is almost always a host firewall or a missing/duplicated DNAT rule, not the app. When a port mapping silently does nothing, reading these rules tells you whether the driver ever programmed the translation — a check no docker logs will give you.

3 — Name resolution: the resolver planted at 127.0.0.11​

The lab used name-based discovery. Here is the mechanism behind it. Every container on a user-defined network gets a /etc/resolv.conf that points not at your host's DNS but at a loopback address Docker owns inside the container:

docker exec backend cat /etc/resolv.conf

Expected output

# Generated by Docker Engine.
# This file can be edited; Docker Engine will not make further changes once it
# has been modified.

nameserver 127.0.0.11
options ndots:0

# Based on host file: '/etc/resolv.conf' (internal resolver)
# ExtServers: [host(192.168.5.3)]
# Overrides: []
# Option ndots from: internal

The ExtServers: [host(192.168.5.3)] comment names the host resolver Docker forwards public names to (its address will differ on your machine). That nameserver 127.0.0.11 is Docker's embedded DNS resolver, running inside the container's own network namespace. It answers queries for container names from the daemon's internal record of what is attached to the network, and forwards everything else (public names) to the host's real resolvers. The 127.0.0.11 address is intercepted by an iptables rule in the container's namespace and redirected to the daemon's resolver — which is why it works even though nothing appears to be listening there in the usual sense. Confirm it resolves a peer by name through exactly that server:

docker exec frontend nslookup backend 127.0.0.11

Expected output

Server:		127.0.0.11
Address:	127.0.0.11:53

Non-authoritative answer:
Name:	backend
Address: 172.27.0.3

The practical payoff: when name resolution fails inside a container, check this file first. A container on the default bridge (or one you forgot to attach to appnet) gets a resolv.conf pointing at the host's DNS with no 127.0.0.11, so peer names return NXDOMAIN — the exact failure from Step 6 of the lab, now explained by a file you can read in one command.

4 — Why one bridge cannot span two hosts (and what does)​

Everything so far lives on a single machine: one bridge, one host's iptables, one daemon's DNS. A Linux bridge is a layer-2 switch, and a switch only connects things plugged into that same physical box. Put the backend on host A and the database on host B and the bridge driver has nothing to join them — the two bridges are unaware of each other. This is not a limitation you tune around; it is the ceiling of single-host networking, and it is precisely the gap Kubernetes' cluster networking exists to close.

Analogy

The lesson's office-floor phone directory works because everyone is in one building. Connecting two buildings so extensions dial across as if on one floor needs a tunnel between them: you take each internal call, wrap it in an envelope addressed building-to-building, ship it over the public road, and unwrap it on arrival. That envelope-around-a-frame is what an overlay network does with VXLAN — it encapsulates each container Ethernet frame inside a UDP packet routed over the ordinary host network (the "underlay"), so two hosts' bridges behave like one L2 segment.

You cannot stand up a true multi-host overlay on a single laptop, but the driver that does it is already registered in your Docker — the plugin list names it alongside bridge, host, and null:

docker info --format 'network drivers: {{.Plugins.Network}}'

Expected output

network drivers: [bridge host ipvlan macvlan null overlay]

overlay is Docker Swarm's answer to this. Kubernetes solves the same problem with a pluggable layer called the CNI (Container Network Interface) — Calico, in this course, installed in Session 3. Different implementation, identical purpose: give every container across every node one flat address space so a Pod on node A reaches a Pod on node B by address without you thinking about tunnels. When you see "why do we need a CNI plugin at all?" in Session 3, this is the answer — the single-host bridge you dissected here simply does not reach across machines.

Where you will use this
  • A Docker network is a Linux bridge, and each container is joined by a veth pair. Use it when: a container reports no connectivity — check that its eth0 exists and its veth landed on the expected br-… bridge before you touch the app; a cable on the wrong switch is not an application bug.
  • Published ports and outbound internet access are iptables DNAT/MASQUERADE rules the driver writes. Use it when: a port mapping is "connected but refused" or silently dead — read iptables -t nat -S to confirm the translation was actually programmed, rather than re-checking the app that is working fine.
  • Name resolution is an embedded resolver at 127.0.0.11, present only on user-defined networks. Use it when: a peer name returns NXDOMAIN — cat /etc/resolv.conf inside the container tells you in one command whether it is on the right network, no packet capture required.
  • A single-host bridge cannot cross machines; overlay/VXLAN and Kubernetes' CNI exist for that. Use it when: someone asks why Kubernetes needs Calico or "why not just use a Docker bridge on the cluster" — you can explain the L2 ceiling instead of hand-waving.

Teardown​

This page only re-seeded the same three app containers and network the lab used, and ran throwaway --rm inspection containers (already gone). Remove the app containers and network the same way the lab did; the next session rebuilds the stack with Compose, so nothing here needs to persist:

docker rm -f frontend backend db
docker network rm appnet

Expected output

frontend
backend
db
appnet

Keep the fernwood-frontend:m1 and fernwood-backend:m1 images — later sessions reuse them. If you want the disk back from the inspection tool, docker rmi nicolaka/netshoot is optional and safe.
