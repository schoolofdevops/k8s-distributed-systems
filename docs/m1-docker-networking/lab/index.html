Lab — Connect the 3-tier app over a Docker network

In this lab you build the two application images, put all three tiers on one user-defined bridge network, and prove they find and reach each other by name — the frontend calls backend, the backend reaches db, none of it wired by IP address. You also see, by contrast, why the default bridge network cannot do this. This is the first increment of the distributed-app spine you will grow for the rest of the course — it lives at labs/distributed-app/ in the labs repo.

What you will end up with

Three containers — frontend, backend, db — attached to a network called appnet. Open http://localhost:3000 and the frontend shows its own container ID, a "Backend reachable" banner, and the product catalogue it fetched from backend, which in turn reports db: connected.

Lab map (compact)​

You will use three Docker network modes in this lab. Keep this matrix handy and map each command to it:

ModeHow you set itWhy you use it here
bridgedocker network create ... + --network <name>Gives name-based discovery for app services
host--network hostPuts container in the host stack for direct host-level networking
none--network noneHard isolation test where there is no outbound connectivity
container--network container:<peer>Shares one existing container namespace for peer debugging

The main lab flow is:

  1. Build and tag the two app images (backend, frontend).
  2. See Docker's built-in network list and then create appnet.
  3. Start all three tiers on appnet and prove discovery.
  4. Validate that default bridge and explicit host/none settings behave exactly differently.
  5. Use peer networking (--network container) to debug a container that cannot run shell commands.

What to capture while you run this lab​

Keep these two visuals as references while you run the lab:

  • Frontend output (http://localhost:3000) — product grid + green banner when backend is reachable.

  • Backend health output (/api/health) — DB status and hostname response after health check.

Use these placeholders as visual references: your real output should match the sections and flow.

Use this map before each step so the mental model stays close to the command you are running.

Before you start​

You need Docker running and the labs/distributed-app/ source from the labs repository (this repo).

docker version --format '{{.Server.Version}}'
cd labs/distributed-app
ls

Expected output

29.5.2
backend
frontend
README.md
note

The Server version will differ on your machine — any recent Docker (24+) is fine. What matters is that the command returns a version and does not error with "Cannot connect to the Docker daemon".

Step 1 — Build the frontend and backend images​

Each tier has its own Dockerfile. Build both, tagging them with :m1 so the tag is meaningful as the app grows. The database needs no build — it is the official Postgres image.

docker build -t fernwood-backend:m1 ./backend
docker build -t fernwood-frontend:m1 ./frontend

Expected output (last lines of the second build)

#11 naming to docker.io/library/fernwood-frontend:m1 done
#11 unpacking to docker.io/library/fernwood-frontend:m1 done
#11 DONE 0.1s

Confirm both images exist:

docker images | grep fernwood

Expected output

fernwood-backend:m1                           ecb2c5ce776d   251MB   55.1MB
fernwood-frontend:m1                          9bf34a82d220   209MB   51.4MB
note

Image IDs, sizes, and even the column layout differ by Docker distribution — the capture above is from Rancher Desktop (which shows REPOSITORY:TAG · ID · size · compressed size); Docker Desktop shows REPOSITORY · TAG · IMAGE ID · CREATED · SIZE. You are only checking that both the fernwood-frontend:m1 and fernwood-backend:m1 rows are present.

Step 2 — Look at the networks Docker already gave you​

Before creating anything, see the three default networks and their drivers.

docker network ls

Expected output

NETWORK ID     NAME      DRIVER    SCOPE
7e8c59ca408c   bridge    bridge    local
5b2b0b560a14   host      host      local
37d312854bc4   none      null      local
note

If you have run other Docker projects on this machine you will also see their networks listed here (names like kind, <project>_default, and so on). The three that Docker always creates for you and that matter for this step are bridge, host, and none.

These are the bridge, host, and none networks from the lesson. The default bridge works, but containers on it can only reach each other by IP address — not by name. That is the limitation you fix in the next step.

Step 3 — Create a user-defined bridge network​

Create your own bridge network. The only visible difference from the default bridge is the one that matters: Docker runs an embedded DNS server on it, so containers resolve each other by --name.

docker network create appnet

Expected output

50d8325d9c7af3e6b6b4dc28d054409b18af21961b10924921e34cb5787d78b9

The long string is the new network's ID. Inspect it and note the bridge driver and the subnet Docker allocated:

docker network inspect appnet --format '{{.Name}} driver={{.Driver}} subnet={{range .IPAM.Config}}{{.Subnet}}{{end}}'

Expected output

appnet driver=bridge subnet=172.27.0.0/16
note

Your subnet (e.g. 172.27.0.0/16) is assigned by Docker and will likely differ. The point is that appnet exists with the bridge driver.

Step 4 — Run all three tiers on appnet​

Start the database first, then the backend, then the frontend. Every container is attached to appnet with --network appnet and given a stable --name — the name is the address the others use. Note that the backend's default DB_* values already point at a host called db, and the frontend's default BACKEND_URL already points at http://backend:8080, so the names below are not arbitrary — they are the names the app is expecting.

Start Postgres as db:

docker run -d --name db --network appnet \
  -e POSTGRES_USER=fernwood \
  -e POSTGRES_PASSWORD=fernwood \
  -e POSTGRES_DB=fernwood \
  postgres:16

Expected output

9f44edac3ea51c5bbe5e82266cdbd37ba1f71220ccb6c8aee375f3e76f33da78

Start the backend as backend, publishing its port so you can hit the API directly too:

docker run -d --name backend --network appnet -p 8080:8080 fernwood-backend:m1

Expected output

eb4298aa00ba3ae613c5bd632ce87f6965e9b2c46cb40c4ab0c83a8d8ccf7da2

Start the frontend as frontend, publishing port 3000:

docker run -d --name frontend --network appnet -p 3000:3000 fernwood-frontend:m1

Expected output

c40ab60610726f94d20f52601072ac0113692ebcc1226cba274fcd336fb3dec1

Confirm all three are running:

docker ps --format 'table {{.Names}}\t{{.Image}}\t{{.Status}}'

Expected output

NAMES      IMAGE                  STATUS
frontend   fernwood-frontend:m1   Up 15 seconds
backend    fernwood-backend:m1    Up 15 seconds
db         postgres:16            Up 16 seconds
note

The Up ... durations will differ. All three names must be present and in an Up state. If any shows Exited, jump to Troubleshooting.

Step 5 — Prove name-based discovery and reachability​

This is the whole point of the lab. Nothing below uses an IP address.

The frontend resolves and reaches the backend. Connect to the frontend shell once, then run the commands from inside it:

docker exec -it frontend -- sh

Inside that shell:

wget -qO- http://backend:8080/api/health
ping -c 1 backend
exit

Expected output

{"db":"connected","hostname":"eb4298aa00ba","service":"backend","status":"ok"}

PING backend (172.27.0.3): 56 data bytes
64 bytes from 172.27.0.3: seq=0 ttl=64 time=5.821 ms

--- backend ping statistics ---
1 packets transmitted, 1 packets received, 0% packet loss
round-trip min/avg/max = 5.821/5.821/5.821 ms

Two facts are proven at once: the name backend resolved to the backend container, and the backend itself resolved db and connected to Postgres ("db":"connected"). The hostname is the backend container's own ID.

note

The resolved IP (172.27.0.3 here) comes from appnet's subnet and will differ on your machine. What matters is that the name backend resolves at all and the ping succeeds — on the default bridge network it would not (you confirm that in Step 6).

The full path works from the outside. Hit the frontend from your host and confirm it fetched the catalogue from the backend:

curl -s http://localhost:3000 | grep -oE 'Backend reachable.*<code>[a-f0-9]*'

Expected output

Backend reachable · served by <code>eb4298aa00ba

Open http://localhost:3000 in a browser to see the full page: the frontend's container ID, the green "Backend reachable" banner, and the product catalogue grid.

Step 6 — See why the default bridge cannot do this​

To make the contrast concrete, run a throwaway container on the default bridge network (no --network appnet) and try to resolve backend by name. It fails, because the default bridge has no embedded DNS.

docker run --rm alpine nslookup backend

Expected output

Server:		192.168.5.3
Address:	192.168.5.3:53

Non-authoritative answer:

** server can't find backend: NXDOMAIN
note

The Server here is your host's own DNS resolver (its address will differ on your machine) — that is exactly the tell: a container on the default bridge has no embedded resolver, so nslookup falls back to the host's DNS, which has never heard of backend. On appnet the server would instead be 127.0.0.11, Docker's embedded DNS (you see this in the Deep Dive). The command also exits non-zero.

The NXDOMAIN is the point: name resolution for backend does not exist off appnet. Name-based service discovery is a property of the user-defined network, not of Docker in general. This is the single reason you always create a network for an application instead of using the default bridge.

Step 7 — See host and none in action​

The lesson's network-driver table listed three built-in networks — bridge, host, and none. You have now used a user-defined bridge network end to end. The other two are the ones you reach for at the extremes: host when you want no isolation, none when you want no network at all. Here you prove both, and see exactly what the network namespace does — using nicolaka/netshoot, a throwaway diagnostics image. Nothing below touches your three running containers; each command is a --rm container that exits on its own.

host — the container shares the host's network stack directly. Run a netshoot container on the host network and list its interfaces:

docker run --rm --network host nicolaka/netshoot ip -br addr

Expected output (abridged)

lo               UNKNOWN        127.0.0.1/8 ::1/128
eth0             UP             192.168.5.15/24 fe80::5055:55ff:fe3d:ad84/64
docker0          DOWN           172.17.0.1/16 fe80::84e6:6ff:fe91:ab63/64
br-c45ec7ee020a  UP             172.27.0.1/16 fe80::48c7:eeff:fea3:ee9c/64
# …plus veth* and other br-* interfaces for every Docker network on this host…

Look at what this container can see. There is no private eth0@ifNN on a 172.x container subnet — instead eth0 is the host's own LAN interface (192.168.5.15/24 here, your machine's real address on your network), and the list includes docker0 and the br-… bridge for appnet (172.27.0.1, the gateway you saw in Step 3). This container is not in a separate network namespace at all; it is looking at the host's interfaces directly.

note

Your output will look different, and probably shorter. The eth0 address is your host's real IP on your network (it will not be 192.168.5.15), and the interface name may not be eth0. The long tail of br-… and veth… entries above is specific to this authoring machine, which has several other Docker networks; a clean machine shows only lo, the host's real NIC, and docker0. What matters is the pattern: you see the host's interfaces, not an isolated private one.

Compare that with the same command on appnet (the network your app runs on):

docker run --rm --network appnet nicolaka/netshoot ip -br addr

Expected output

lo               UNKNOWN        127.0.0.1/8 ::1/128
eth0@if143       UP             172.27.0.5/16

Now the container has its own isolated eth0@if143 with a private appnet address (172.27.0.5/16, from the same subnet as db/backend/frontend) — and it sees nothing else. That is the normal bridge case: a namespace of its own. The host container above had no such private interface because it was sharing the host's stack.

Reach for --network host when the isolation is the problem, not the feature — a latency-sensitive proxy that must bind the host's ports with no NAT hop, or a host-level monitoring agent that has to observe the host's real interfaces. The trade-off is real: you lose the network isolation, and because the container is literally on the host's ports you cannot run two of them wanting the same port.

none — the container gets no network at all. Run netshoot on the none network and list its interfaces:

docker run --rm --network none nicolaka/netshoot ip -br addr

Expected output

lo               UNKNOWN        127.0.0.1/8 ::1/128

Just loopback. No eth0, no address, no route off the container. Prove it really cannot reach anything by trying to fetch a public URL — it fails because there is not even a DNS resolver or a route to use:

docker run --rm --network none nicolaka/netshoot curl -m 3 -sS https://example.com

Expected output

curl: (6) Could not resolve host: example.com (Could not contact DNS servers)

The command exits non-zero (curl exit code 6, "couldn't resolve host"). With no interface but loopback, the container has no way to resolve a name or open a connection — exactly as designed.

note

The precise wording of the failure can differ by tool and version (a ping instead of curl would say Try again or Network is unreachable), and the exit code may vary. The point that holds on every machine is that it fails: a none-network container genuinely cannot reach the network.

Reach for --network none when "no network" is the guardrail, not a bug — a batch job that only processes a mounted file and must not be able to phone home, or a security-sensitive step where you want it provably unable to make an outbound connection. none turns "this container cannot reach anything" from a hope into an enforced property.

Step 8 — Troubleshoot a shell-less container by sharing a namespace with netshoot​

--network container:<name> puts a new container into the target container’s existing network namespace. This is the same model used inside one Kubernetes pod, where every container in the pod shares one network namespace.

Use this when the workload container has no shell (for example, distroless images), but you still need live network checks.

Start a small shell-less workload and verify there is no shell in it:

docker run -d --name shellless-worker --network appnet registry.k8s.io/pause:3.12
docker exec -it shellless-worker -- sh

Expected output

4d2e1c3a7f8a
OCI runtime exec failed: exec failed: container_linux.go: ... no such file or directory

Share that namespace with netshoot and keep one shared shell open for all checks:

docker run -d --name shellless-netshoot --network container:shellless-worker nicolaka/netshoot sleep 3600
docker exec -it shellless-netshoot -- sh

Expected output

cb0d4f1a9e7b

Inside that shell:

ip -br addr
cat /etc/resolv.conf
ip route
nslookup backend
exit

Expected output

nameserver 127.0.0.11
search appnet

default via 172.27.0.1 dev eth0
172.27.0.0/16 dev eth0 scope link src 172.27.0.6
lo               UNKNOWN        127.0.0.1/8 ::1/128
eth0@if143       UP             172.27.0.6/16

Server:    127.0.0.11
Address:   127.0.0.11:53

Name:      backend
Address:   172.27.0.4

Clean up the shellless helper and the debug container:

docker rm -f shellless-netshoot shellless-worker

Expected output

shellless-netshoot
shellless-worker

This pattern is the operational version of a pod-sidecar troubleshooting workflow: if a container is too small to include debug tools, you do not rebuild the application just to debug networking; you attach a temporary peer diagnostic container to that same namespace instead.

Troubleshooting​

backend container shows Exited right after start

Check its logs with docker logs backend. The backend is designed to start even when Postgres is unreachable, so an exit here usually means a port clash on 8080 or a bad image build. Re-run Step 1 and confirm docker images | grep fernwood shows the backend image.

frontend shell returns bad address for backend

The frontend container is not on appnet. Confirm with docker inspect -f '{{json .NetworkSettings.Networks}}' frontend — you should see appnet listed. If it shows bridge instead, you started it without --network appnet; docker rm -f frontend and re-run its command from Step 4.

Health shows "db":"unavailable" even though db is running

The backend connects to Postgres with the fernwood user, database, and password. If you started db without the three -e POSTGRES_* variables from Step 4, the credentials will not match. Remove it (docker rm -f db) and re-run the db command exactly as written. Note this is graceful degradation working as designed — the backend still answered with HTTP 200, it just reports the DB is not reachable.

port is already allocated on 3000 or 8080

Another process is using that host port. Either stop it, or change the left side of the -p mapping (e.g. -p 3001:3000) and use the new port in your curl/browser. The right side (the container port) must stay the same.

Teardown​

Remove the three containers and the network. Nothing here persists data yet, so this is a clean reset.

docker rm -f frontend backend db
docker network rm appnet

Expected output

frontend
backend
db
appnet

The images (fernwood-frontend:m1, fernwood-backend:m1) remain in your local cache — you reuse them in the next session, so there is no need to delete them.

What you proved​

  • Containers on a user-defined bridge network discover each other by name via Docker's embedded DNS — no IP addresses anywhere in the app's configuration.
  • The 3-tier app runs as three independent, separately-scheduled containers that coordinate over the network — a real distributed system on a single host.
  • Name-based discovery is a property of the network you created, not of the default bridge — which is why you always create one for an application.

Next session you will declare this exact topology in a single Docker Compose file instead of typing five docker run commands, and then start pushing on the limits of running it all on one machine.
