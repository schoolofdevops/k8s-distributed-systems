Docker Networking — How Containers Find Each Other

▶ M1 · Docker Networking — How Containers Find Each OtherOpen fullscreen ↗

Part 1 ended on a simple demand. If a distributed application is independent pieces that coordinate over a network, the pieces first have to find and reach each other. On a single machine, that is Docker's job. This part is the "why and what" behind it: how a container gets a network at all, the three networks Docker ships with, why the default one quietly breaks real applications, and the fix you will use for the rest of your career. The lab right after turns this into running containers. Read this first, so the commands there are confirmations, not surprises.

How a container gets a network at all​

Before we compare networks, it helps to know what "being on a network" even means for a container. The mechanism explains everything that follows.

Analogy

Think of the Linux kernel as an apartment building, and the host's real network card as the building's single mailroom. A network namespace is a private mailroom Docker builds for one flat. It has its own interfaces, its own IP, its own routing table, and its own view of "the network." The flat behaves as if it has the whole mailroom to itself, even though dozens of other flats in the same building have their own private mailrooms too, all sharing the one real card downstairs.

When Docker starts a container, it does not hand it a slice of the host's network directly. It creates a network namespace, that is, a kernel-level isolated copy of the whole networking stack, and puts the container inside it. That is why a container has its own IP address, its own set of interfaces, and its own idea of which ports are in use, all separate from the host and from every other container. This isolation is the whole reason two containers can both listen on port 8080 without clashing. Each one is listening inside its own namespace. Everything else in this part, bridges, DNS, the choice of network, is really one question: how does Docker connect these isolated namespaces to each other and to the outside world?

The three built-in networks​

When Docker starts, it creates three networks, which you can see with docker network ls. Each one is backed by a network driver, that is, the piece of software that decides what "being on this network" actually means for the namespace above.

NetworkDriverWhat the container getsReach for it when
bridgebridgeA private IP on Docker's default virtual switch; reaches the outside via NAT (address translation at the host's edge)The default for a container you did not place anywhere specific
hosthostNo separate namespace; it shares the host's network stack directlyYou need the host's exact ports with no NAT hop, say a latency-sensitive proxy or a monitoring agent that must see the host's real interfaces, and you accept losing isolation
nonenullA loopback interface and nothing elseYou want a container deliberately cut off from the network, say a batch job that only crunches a mounted file, or a security-sensitive step that must not phone home

The host and none rows are not just trivia. host is what you reach for when the namespace isolation itself is the problem: a reverse proxy that must bind the host's port 443 with no address translation in the way, or an agent that needs to watch the host's real network. none is what you reach for when a container should have no way to reach anything. You are removing the network on purpose, as a guardrail. Both are the exception. For an application whose parts must talk to each other, you want the default driver's behaviour, a private network they share, but, as the next section shows, not the default network itself. You will prove both extremes hands-on in this module's lab (Step 7). You will watch a host container see the machine's real interfaces, and a none container fail to reach anything at all.

Why the default bridge is an operational trap​

The default bridge network works, and that is exactly what makes it dangerous. It works in the demo and fails in the real application. Its limit is specific. Containers on it can reach each other only by IP address, not by name. There is no name resolution on the default bridge.

That sounds like a footnote until you trace what happens in practice. Docker gives a container its IP from the bridge subnet at start time, and it can change every time the container restarts. So the moment one container needs to reach another, someone has to find the target's current IP and put it somewhere: an environment variable, a config file, a hardcoded value. Then a container restarts after a crash, comes back with a different IP, and every place that hardcoded the old one now points at nothing (or worse, at whatever container inherited that address). The frontend cannot reach the backend. The failure looks like a network outage, but it is really a stale address. Nobody changed the code, nothing is "down," and yet the app is broken. This is the classic 2-tier connection failure that a learner meets on day one and an operator meets during an incident. Hardcoding IPs is not a small shortcut. It is a design that guarantees breakage the first time a container restarts.

User-defined bridge networks and DNS by name​

The fix is a user-defined bridge network, one you create yourself with docker network create.

Analogy

A user-defined bridge is like an office floor with its own internal phone directory. Plug a container into that floor and it gets an extension and a name in the directory. So colleagues on the same floor can call it by name and reach it, no matter which extension it happens to have today. Plug a container into a different floor and it is in a different directory. Same building, but no listing, so the call does not connect. Which floor you plug into decides who can reach whom, and the directory means nobody has to remember extension numbers.

A user-defined bridge behaves like the default bridge with one big addition. Docker runs an embedded DNS server on it (a small name lookup service built in), so every container can resolve every other container by its --name. Start the backend as backend, and the frontend can call http://backend:8080 and it just works. No IP addresses, and no config to update when a container restarts with a new IP. The name stays fixed. Docker's DNS resolves it to whatever the current IP is, every time. That is why our app's BACKEND_URL defaults to http://backend:8080 and its database connection points at the host db. The names are the contract, and the IPs underneath are free to change.

This is not a Docker-only trick you will leave behind. It is the direct ancestor of how Kubernetes works. In Session 4 you will create a Kubernetes Service, and the payoff of learning name-based discovery now is simple. A Service gives every set of Pods a stable DNS name for exactly the same reason. Pods come and go and their IPs keep churning, so nothing addresses them by IP. Everything addresses the Service name, and Kubernetes' cluster DNS resolves it. The office-floor directory you learn today is the same idea, and Kubernetes scales it across a whole cluster. Learn the habit here on one machine, and the Kubernetes version will feel familiar, not new.

The one habit to keep

For any set of containers that need to talk to each other, create a user-defined bridge network and attach them all to it. You get name-based discovery for free, and you never wire IP addresses by hand. The default bridge is for throwaway single containers, not for an application.

What the lab is about to prove​

The lab that follows is where this stops being theory. You will build the frontend and backend images, put all three tiers on one user-defined network, and watch them find each other by name. The frontend fetches the catalogue from backend, and the backend reports whether it can reach db. You will also see the contrast directly. Containers on the default bridge fail to resolve each other by name, so the reason for the "one habit" above is something you observe, not something you take on faith. Start the lab with one expectation: names should work, and IPs should be something you never had to type.
