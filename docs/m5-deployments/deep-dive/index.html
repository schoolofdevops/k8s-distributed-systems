Deep Dive — under the hood of autoscaling, and the wall Deployments hit

The lab gave you the everyday mechanics: convert to Deployments, roll out, roll back, autoscale. This Part 2 goes past the buttons. Two things a practitioner running this in production actually needs: how the HPA decides, so you can tune it instead of cargo-culting numbers; and the precise point where the Deployment model stops being the right tool — the reason M6 exists.

This assumes you did the lab. The backend HPA, its scaling history, and kubectl top are all still live from there.

Part A — how the HPA actually decides, and how to tune it​

The formula is one line​

The HorizontalPodAutoscaler is not clever. Each cycle (every 15 seconds by default) it computes:

desiredReplicas = ceil( currentReplicas × ( currentMetricValue / desiredMetricValue ) )

That is the whole algorithm. In the lab, backend CPU hit 656% of the 50% target across the running Pods. Plug it in: the ratio is far above 1, so desiredReplicas jumps to the maxReplicas cap of 6 in a single step. When load vanished and utilization fell to ~19%, the ratio dropped below 1 and the desired count fell back toward the floor of 2. No magic — just ceil of a ratio, clamped to [min, max].

Two subtleties that bite people:

  • The ratio has a tolerance (10% by default). If current/target is within 0.9–1.1, the HPA does nothing — this is what stops it thrashing one Pod up and down around the target.
  • It scales on the average across ready Pods. A single hot Pod is diluted by its quiet peers, which is why a badly-sharded workload can be busy and still not scale.

Reading the HPA's own diagnosis​

The HPA publishes why it is doing what it does, in its conditions and events. This is the first thing to look at when an HPA "won't scale". From the lab's backend HPA:

kubectl describe hpa backend -n fernwood | sed -n '/Conditions:/,/Events:/p'

Expected output

Conditions:
  Type            Status  Reason               Message
  ----            ------  ------               -------
  AbleToScale     True    ScaleDownStabilized  recent recommendations were higher than current one, applying the highest recent recommendation
  ScalingActive   True    ValidMetricFound     the HPA was able to successfully calculate a replica count from cpu resource utilization (percentage of request)
  ScalingLimited  False   DesiredWithinRange   the desired count is within the acceptable range

Read those three lines like a status panel. ScalingActive: True / ValidMetricFound means metrics are flowing — if this said False / FailedGetResourceMetric, your problem is the metrics-server, not the HPA. AbleToScale: True / ScaleDownStabilized is the HPA telling you out loud that it is deliberately holding replicas up because of the stabilization window. ScalingLimited: False / DesiredWithinRange means it is neither pinned at min nor max. The events are the timeline:

kubectl describe hpa backend -n fernwood | grep -A10 "Events:"

Expected output

Events:
  Type     Reason                        Age    Message
  Normal   SuccessfulRescale             16m    New size: 3; reason: cpu resource utilization (percentage of request) above target
  Normal   SuccessfulRescale             15m    New size: 6; reason: cpu resource utilization (percentage of request) above target
  Warning  FailedGetResourceMetric       14m    failed to get cpu utilization: unable to get metrics ... no metrics returned from resource metrics API
  Normal   SuccessfulRescale             7m17s  New size: 5; reason: All metrics below target
  Normal   SuccessfulRescale             7m2s   New size: 4; reason: All metrics below target
  Normal   SuccessfulRescale             4m1s   New size: 3; reason: All metrics below target

Notice the honest FailedGetResourceMetric warning in the middle: during rapid scaling, a just-created Pod exists but has not been scraped yet, so for one cycle the HPA cannot compute a value for it. It recovers on the next scrape. Do not panic at a single one of these; a sustained run of them is the real signal that metrics are broken.

The stabilization window, and why scale-down felt slow​

In the lab, utilization fell in seconds but the replica count sat at 6 for about five minutes before dropping. That gap is the downscale stabilization window (--horizontal-pod-autoscaler-downscale-stabilization, default 5m). Each cycle the HPA looks back over that window and applies the highest recommendation it saw — exactly what the ScaleDownStabilized condition above reported. The effect: it will not shed capacity it might need again a moment later.

Analogy: it is the reflex of an experienced kitchen manager who does not send three cooks home the instant one table pays and leaves — a lull is not the end of the rush. They wait until the room has stayed quiet before releasing staff. Scale-up, by contrast, has a zero-second default window: the room filling is an emergency, so cooks are called in immediately.

You tune both sides with a behavior block. This is the tuned HPA from the deep-dive validation:

spec:
  behavior:
    scaleDown:
      stabilizationWindowSeconds: 60      # shrink 5× sooner than the 300s default
      policies:
        - { type: Percent, value: 50, periodSeconds: 30 }   # remove at most 50% of Pods per 30s
    scaleUp:
      stabilizationWindowSeconds: 0       # react to spikes immediately
      policies:
        - { type: Pods, value: 2, periodSeconds: 15 }       # add at most 2 Pods per 15s
      selectPolicy: Max

Applying it and reading it back confirms the API honours every field:

kubectl apply -f k8s/backend-hpa-tuned.yaml
kubectl get hpa backend -n fernwood -o jsonpath='{.spec.behavior}{"\n"}'

Expected output

{"scaleDown":{"policies":[{"periodSeconds":30,"type":"Percent","value":50}],"selectPolicy":"Max","stabilizationWindowSeconds":60},"scaleUp":{"policies":[{"periodSeconds":15,"type":"Pods","value":2}],"selectPolicy":"Max","stabilizationWindowSeconds":0}}

The tuning judgement, stated plainly: a short scale-down window saves money; a long one protects latency. A service with spiky, latency-sensitive traffic wants a long window (keep capacity ready). A batch or dev workload wants a short one (release Pods fast, stop paying). The default of 5 minutes is a safe middle. There is no universally correct number — there is only the trade you are choosing.

Part B — where Deployments stop being the right tool​

Everything above rests on one assumption baked into a Deployment: its Pods are interchangeable. A Deployment's replicas share one template, have no individual identity, and are addressed only as an anonymous pool behind a Service. For a stateless frontend that is exactly right. For a database it is quietly disastrous — and seeing why is the concrete motivation for M6.

Try to run the sample app's Postgres tier the way you ran the frontend: as a Deployment with two replicas. The k8s/pg-antipattern.yaml manifest does exactly that — postgres:16, replicas: 2, no persistence and no replication, on purpose. Apply it:

kubectl apply -f k8s/pg-antipattern.yaml
kubectl rollout status deployment/pg-antipattern -n fernwood

Expected output

deployment.apps/pg-antipattern created
Waiting for deployment "pg-antipattern" rollout to finish: 0 of 2 updated replicas are available...
deployment "pg-antipattern" successfully rolled out

On the surface it comes up fine.

kubectl get pods -n fernwood -l app=pg-antipattern

Expected output

NAME                             READY   STATUS    RESTARTS   AGE
pg-antipattern-578f8dff4-9kxnc   1/1     Running   0          39s
pg-antipattern-578f8dff4-tjj8w   1/1     Running   0          39s

Two Running Pods — and already three things are wrong.

1. The replicas are not a cluster — they are two unrelated databases. Capture the two Pod names first, then write to one and read from the other — it knows nothing about the write:

POD_A=$(kubectl get pods -n fernwood -l app=pg-antipattern -o jsonpath='{.items[0].metadata.name}')
POD_B=$(kubectl get pods -n fernwood -l app=pg-antipattern -o jsonpath='{.items[1].metadata.name}')
kubectl exec -n fernwood "$POD_A" -- psql -U postgres -c "CREATE TABLE t(x int); INSERT INTO t VALUES (1); SELECT count(*) FROM t;"
kubectl exec -n fernwood "$POD_B" -- psql -U postgres -c "SELECT count(*) FROM t;"

Expected output

CREATE TABLE
INSERT 0 1
 count
-------
     1
(1 row)

ERROR:  relation "t" does not exist
LINE 1: SELECT count(*) FROM t;
                             ^

A Deployment stamped out two copies of the same template; it did nothing to make them replicate to each other. Behind one Service they would answer queries at random, from two divergent datasets. For a stateless app that is load-balancing; for a database it is data corruption.

2. Identity is not stable. Delete the Pod that holds the data ($POD_A, still set from above) and its replacement comes back under a new random name:

kubectl delete pod "$POD_A" -n fernwood
kubectl get pods -n fernwood -l app=pg-antipattern -o name

Expected output

pod/pg-antipattern-578f8dff4-mq2xc
pod/pg-antipattern-578f8dff4-tjj8w

...-9kxnc is gone; ...-mq2xc is new. There is no stable name a peer or a client could rely on to say "connect to the primary". A replication topology needs members it can address by fixed identity — db-0 is the primary, db-1 follows it — and a Deployment cannot give you that.

3. Storage is ephemeral and shared-by-template. The replacement Pod started with an empty database — the row written to the deleted Pod is gone, because the storage lived and died with that Pod. And if you had pointed the template at a single PersistentVolumeClaim, both replicas would mount the same volume and fight over the same files (a ReadWriteOnce volume will not even attach to a second node, stalling the Pod). A Deployment has no way to give each replica its own durable volume.

The three failures map to the three guarantees a StatefulSet adds, which is the whole of M6:

A database needsA Deployment givesA StatefulSet gives
Stable network identityrandom Pod namesordinal names db-0, db-1, stable across restarts
Its own durable storage per memberephemeral, or one shared volumeone PVC per Pod, reattached to the same ordinal
Ordered start/stopall replicas at once, interchangeabledb-0 before db-1; reverse on scale-down

This is why the Fernwood spine has kept Postgres out of Kubernetes until now. Sessions 1–4 ran it in Docker; M4 and M5 only ever put the stateless frontend and backend tiers on the cluster. There is no db Pod in the distsys cluster yet, on purpose — a database is not a thing you run as a Deployment, and M6 is where it gets the object built for it.

Clean up the anti-pattern demo

The pg-antipattern Deployment was only to make the failure visible. Delete it so M6 starts from a clean cluster with no stray Postgres:

kubectl delete deployment pg-antipattern -n fernwood

Where you will use this​

  • An HPA "won't scale" during an incident. Go straight to kubectl describe hpa and read the three conditions before touching anything — they tell you whether it is a metrics problem (ScalingActive: False), a deliberate hold (ScaleDownStabilized), or a cap (ScalingLimited: True).
  • Tuning autoscaling for a real service. You now choose the scale-down window as an explicit latency-vs-cost trade in a behavior block, instead of living with the 5-minute default and wondering why capacity lingers.
  • Someone proposes running a database, queue, or cache as a Deployment "for now". You can show, in three commands, exactly how it loses data and identity — and point at the StatefulSet as the right tool instead of arguing from principle.
