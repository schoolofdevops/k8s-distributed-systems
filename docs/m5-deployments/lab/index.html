Lab — Release Fernwood Goods safely with Deployments

This lab picks up the distsys cluster you left running at the end of M4 — the fernwood namespace with a bare frontend ReplicaSet (3 Pods) and a bare backend ReplicaSet (2 Pods) behind their Services. You will turn those two ReplicaSets into Deployments, ship a new frontend version with zero downtime, ship a deliberately broken version and roll it back, put the backend under a HorizontalPodAutoscaler and watch it scale under real load, and finish by deploying a stock Spring Boot service with the exact same pattern.

What you will end up with

Two Deployments (frontend on a new release 2.0 image, backend), each owning a hash-named ReplicaSet; a proven zero-downtime rollout and a proven rollback; a metrics-server feeding kubectl top; a backend HPA that scaled 2 → 6 → 2 under load; and a separate Spring Boot Deployment serving through its own Service. The cluster stays up — M6 turns Postgres into a StatefulSet next.

Point-in-time output

Every Expected-output block below is captured from one real run. Pod name suffixes, ReplicaSet hashes, IP addresses, timestamps and exact CPU numbers will differ on your machine — match the shape (a Running status, a ready count, a version string), not the literal values.

Before you start​

Point kubectl at the cluster and work from the labs repo. Confirm you are starting from M4's state — two bare ReplicaSets, no Deployments yet:

kubectl config use-context kind-distsys
cd labs/distributed-app
kubectl get rs,deploy -n fernwood

Expected output

Switched to context "kind-distsys".
NAME                       DESIRED   CURRENT   READY   AGE
replicaset.apps/backend    2         2         2       59m
replicaset.apps/frontend   3         3         3       59m
No resources found in deployment.apps.

Two ReplicaSets, zero Deployments. If your default namespace is not already fernwood, add -n fernwood to the commands below (M4 set it as the context default).

Step 1 — Convert the ReplicaSets into Deployments​

The Deployment manifests wrap the same Pod templates you already ran in M4 — same fernwood-frontend:m2 / fernwood-backend:m2 images, same labels, same probes — and add a rollout strategy and CPU resources.requests (the requests matter for the HPA later). Look at the frontend one:

cat k8s/frontend-deployment.yaml

Expected output

apiVersion: apps/v1
kind: Deployment
metadata:
  name: frontend
  namespace: fernwood
  labels:
    app: fernwood
    tier: frontend
spec:
  replicas: 3
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxUnavailable: 0
      maxSurge: 1
  selector:
    matchLabels:
      app: fernwood
      tier: frontend
  template:
    metadata:
      labels:
        app: fernwood
        tier: frontend
    spec:
      containers:
        - name: frontend
          image: fernwood-frontend:m2
          imagePullPolicy: IfNotPresent
          ports:
            - containerPort: 3000
          env:
            - name: BACKEND_URL
              value: "http://backend:8080"
          resources:
            requests:
              cpu: 25m
              memory: 32Mi
          readinessProbe:
            httpGet:
              path: /healthz
              port: 3000
            initialDelaySeconds: 2
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /healthz
              port: 3000
            initialDelaySeconds: 5
            periodSeconds: 10

A Deployment's selector matches the same tier labels as the bare ReplicaSet, so you cannot have both managing the same Pods at once. Delete the bare ReplicaSets first, then apply the Deployments:

kubectl delete rs frontend backend -n fernwood
kubectl apply -f k8s/frontend-deployment.yaml -f k8s/backend-deployment.yaml

Expected output

replicaset.apps "frontend" deleted
replicaset.apps "backend" deleted
deployment.apps/frontend created
deployment.apps/backend created
A brief blip is expected here, once

Deleting the bare ReplicaSets removes their Pods, and the new Deployment Pods take a few seconds to come up — so the app has a short gap during this one conversion step. That is the last time: from here on, every change goes through the Deployment's rolling update, which has no gap.

Wait for both to finish rolling out:

kubectl rollout status deployment/frontend -n fernwood
kubectl rollout status deployment/backend -n fernwood

Expected output

Waiting for deployment "frontend" rollout to finish: 0 of 3 updated replicas are available...
Waiting for deployment "frontend" rollout to finish: 1 of 3 updated replicas are available...
Waiting for deployment "frontend" rollout to finish: 2 of 3 updated replicas are available...
deployment "frontend" successfully rolled out
deployment "backend" successfully rolled out

Step 2 — See that a Deployment creates a ReplicaSet it owns​

This is the key mental model from the lesson, made concrete. List the ReplicaSets now:

kubectl get rs -n fernwood -o wide

Expected output

NAME                  DESIRED   CURRENT   READY   AGE   CONTAINERS   IMAGES                 SELECTOR
backend-7c5db8b648    2         2         2       30s   backend      fernwood-backend:m2    app=fernwood,pod-template-hash=7c5db8b648,tier=backend
frontend-5556758bfd   3         3         3       30s   frontend     fernwood-frontend:m2   app=fernwood,pod-template-hash=5556758bfd,tier=frontend

You did not create these ReplicaSets — the Deployments did. Two things to notice: each ReplicaSet's name carries a hash (frontend-5556758bfd), and its selector gained a pod-template-hash label. That hash is how a Deployment tells one version's Pods apart from another's. The Services from M4 are untouched and already steer to the new Pods, because they select on tier, which never changed:

kubectl get deploy -n fernwood
kubectl get endpoints frontend backend -n fernwood

Expected output

NAME       READY   UP-TO-DATE   AVAILABLE   AGE
backend    2/2     2            2           45s
frontend   3/3     3            3           45s
NAME       ENDPOINTS                                                    AGE
frontend   192.168.40.95:3000,192.168.40.97:3000,192.168.40.98:3000    58m
backend    192.168.40.94:8080,192.168.40.96:8080                       58m

Step 3 — Roll out a new version with zero downtime​

You need an actual new version to ship. The frontend source now renders a release badge in its header (driven by an APP_VERSION env var that defaults to 2.0). Build it as :m5 and load it into the cluster, the same build → kind load flow you used in M2/M3:

docker build -t fernwood-frontend:m5 frontend
kind load docker-image fernwood-frontend:m5 --name distsys

Expected output

[+] Building 1.2s (10/10) FINISHED
 => => naming to docker.io/library/fernwood-frontend:m5
Image: "fernwood-frontend:m5" with ID "sha256:8d4629d6..." not yet present on node "distsys-control-plane", loading...
Image: "fernwood-frontend:m5" with ID "sha256:8d4629d6..." not yet present on node "distsys-worker", loading...

To prove zero downtime you need to hit the app continuously while it rolls. Open a small load loop from inside the cluster (a busybox Pod), then trigger the rollout in another terminal. First create the sampler Pod:

kubectl run curler --image=busybox:1.36 -n fernwood --restart=Never -- sleep 3600
kubectl wait --for=condition=Ready pod/curler -n fernwood --timeout=60s

The frontend's /healthz returns JSON with the serving Pod's hostname, and the new :m5 image adds a version field the old :m2 image does not have — so each sample tells you which version answered. Start a tight sampling loop in the background, writing timestamped lines to a file:

kubectl exec -n fernwood curler -- sh -c \
  'end=$(($(date +%s)+55)); while [ $(date +%s) -lt $end ]; do \
     ts=$(date +%T); \
     body=$(wget -T 2 -qO- http://frontend/healthz 2>/dev/null || echo REQUEST_FAILED); \
     echo "$ts $body"; done' > /tmp/rollout-samples.txt 2>&1 &

Immediately trigger the rollout by changing the image, and watch it:

kubectl set image deployment/frontend frontend=fernwood-frontend:m5 -n fernwood
kubectl rollout status deployment/frontend -n fernwood

Expected output

deployment.apps/frontend image updated
Waiting for deployment "frontend" rollout to finish: 1 out of 3 new replicas have been updated...
Waiting for deployment "frontend" rollout to finish: 2 out of 3 new replicas have been updated...
Waiting for deployment "frontend" rollout to finish: 2 old replicas are pending termination...
Waiting for deployment "frontend" rollout to finish: 1 old replicas are pending termination...
deployment "frontend" successfully rolled out

Now read the samples the loop captured. Two questions matter: were any requests dropped, and did old and new Pods serve at the same time?

grep -c REQUEST_FAILED /tmp/rollout-samples.txt   # dropped requests — want 0
grep -c '"version"'    /tmp/rollout-samples.txt   # samples served by the NEW (:m5) Pods
sed -n '/version/,+0p' /tmp/rollout-samples.txt | head -1   # first new-version response

Expected output

0
4853
19:35:16 {"service":"frontend","status":"ok","hostname":"frontend-68cf68cbbc-4rh6n","version":"2.0"}

Zero dropped requests across the whole rollout (this run captured 7012 samples, 0 failures). Look at the transition window — old and new Pods answering in the same second:

grep '19:35:16' /tmp/rollout-samples.txt | head -6

Expected output

19:35:16 {"service":"frontend","status":"ok","hostname":"frontend-5556758bfd-97tct"}
19:35:16 {"service":"frontend","status":"ok","hostname":"frontend-5556758bfd-97tct"}
19:35:16 {"service":"frontend","status":"ok","hostname":"frontend-68cf68cbbc-4rh6n","version":"2.0"}
19:35:16 {"service":"frontend","status":"ok","hostname":"frontend-5556758bfd-97tct"}
19:35:16 {"service":"frontend","status":"ok","hostname":"frontend-68cf68cbbc-4rh6n","version":"2.0"}
19:35:16 {"service":"frontend","status":"ok","hostname":"frontend-5556758bfd-97tct"}

The Pods whose response has no version field are the old :m2 Pods (frontend-5556758bfd-*); the ones reporting "version":"2.0" are the new :m5 Pods (frontend-68cf68cbbc-*). Both are serving the Service at the same instant — that is the rolling update overlap, and it is why nobody saw an error.

The old ReplicaSet is retained, scaled to zero — this is what makes the next step (rollback) instant:

kubectl get rs -n fernwood -l tier=frontend
kubectl rollout history deployment/frontend -n fernwood

Expected output

NAME                  DESIRED   CURRENT   READY   AGE
frontend-5556758bfd   0         0         0       3m
frontend-68cf68cbbc   3         3         3       90s
REVISION  CHANGE-CAUSE
1         <none>
2         <none>
Give history a useful CHANGE-CAUSE

<none> in the history is not helpful during an incident. Annotate each release so the history reads like a changelog:

kubectl annotate deployment/frontend \
  kubernetes.io/change-cause="frontend to release 2.0 (m5)" -n fernwood --overwrite

Step 4 — Ship a broken release and roll it back​

Now the scenario you actually train for: a bad release. The frontend/broken/ directory holds a variant whose readiness probe always fails (/healthz returns HTTP 500). Build it as :m5-bad and load it:

docker build -t fernwood-frontend:m5-bad frontend/broken
kind load docker-image fernwood-frontend:m5-bad --name distsys

Ship it, and watch the rollout — this time it will not complete:

kubectl set image deployment/frontend frontend=fernwood-frontend:m5-bad -n fernwood
kubectl annotate deployment/frontend \
  kubernetes.io/change-cause="frontend to m5-bad (broken readiness)" -n fernwood --overwrite
kubectl rollout status deployment/frontend -n fernwood --timeout=45s

Expected output

deployment.apps/frontend image updated
deployment.apps/frontend annotated
Waiting for deployment "frontend" rollout to finish: 1 out of 3 new replicas have been updated...
error: timed out waiting for the condition

The rollout is stuck on purpose. Because maxUnavailable: 0, the Deployment will not retire a single old Pod until a new one becomes ready — and the new one never will. Look at the state:

kubectl get deploy frontend -n fernwood
kubectl get pods -n fernwood -l tier=frontend

Expected output

NAME       READY   UP-TO-DATE   AVAILABLE   AGE
frontend   3/3     1            3           5m
NAME                        READY   STATUS    RESTARTS   AGE
frontend-68cf68cbbc-2ffc6   1/1     Running   0          3m
frontend-68cf68cbbc-4rh6n   1/1     Running   0          3m
frontend-68cf68cbbc-n76tt   1/1     Running   0          3m
frontend-7dd7fd55f7-77dv9   0/1     Running   0          60s

READY 3/3 — all three good :m5 Pods are still up and serving. UP-TO-DATE 1 — one bad Pod was created but it is 0/1 (never ready). The bad Pod's events show why, and confirm it is receiving no traffic (its IP is absent from the Service endpoints):

BAD=$(kubectl get pods -n fernwood -l tier=frontend \
  -o jsonpath='{range .items[*]}{.metadata.name} {.spec.containers[0].image}{"\n"}{end}' \
  | grep m5-bad | awk '{print $1}')
kubectl describe pod "$BAD" -n fernwood | grep "Readiness probe failed"
kubectl get endpoints frontend -n fernwood

Expected output

  Warning  Unhealthy  5s (x13 over 57s)  kubelet  Readiness probe failed: HTTP probe failed with statuscode: 500
NAME       ENDPOINTS                                                     AGE
frontend   192.168.40.100:3000,192.168.40.101:3000,192.168.40.102:3000  63m

Three endpoint IPs — the three healthy Pods. The bad Pod is not among them, so users never hit it. A readiness probe turned a broken deploy into a non-event. Now put the good version back:

kubectl rollout undo deployment/frontend -n fernwood
kubectl rollout status deployment/frontend -n fernwood

Expected output

deployment.apps/frontend rolled back
Waiting for deployment "frontend" rollout to finish: 1 old replicas are pending termination...
deployment "frontend" successfully rolled out

Rollback is fast because it is just the retained :m5 ReplicaSet being scaled back up — no rebuild, no re-pull. Confirm you are back to three good Pods on the :m5 image:

kubectl get rs -n fernwood -l tier=frontend
kubectl get deploy frontend -n fernwood -o jsonpath='{.spec.template.spec.containers[0].image}{"\n"}'

Expected output

NAME                  DESIRED   CURRENT   READY   AGE
frontend-5556758bfd   0         0         0       5m
frontend-68cf68cbbc   3         3         3       3m
frontend-7dd7fd55f7   0         0         0       97s
fernwood-frontend:m5

The :m5-bad ReplicaSet (frontend-7dd7fd55f7) is now scaled to 0 but retained — the drawer keeps every menu, good or bad.

Step 5 — Install metrics-server so the cluster can measure load​

Autoscaling needs a source of Pod-level CPU numbers. That source is the metrics-server, which is not installed in KIND by default. The manifest in the labs repo is the upstream one with one KIND-specific change: the --kubelet-insecure-tls flag, because KIND's kubelets serve metrics with a self-signed certificate the metrics-server would otherwise reject.

kubectl apply -f k8s/metrics-server.yaml
kubectl rollout status deployment/metrics-server -n kube-system --timeout=120s

Expected output

serviceaccount/metrics-server created
...
deployment.apps/metrics-server created
apiservice.apiregistration.k8s.io/v1beta1.metrics.k8s.io created
Waiting for deployment "metrics-server" rollout to finish: 0 of 1 updated replicas are available...
deployment "metrics-server" successfully rolled out

Give it a few seconds for the first scrape, then confirm kubectl top returns numbers:

kubectl top nodes
kubectl top pods -n fernwood -l tier=backend

Expected output

NAME                    CPU(cores)   CPU(%)   MEMORY(bytes)   MEMORY(%)
distsys-control-plane   599m         11%      1398Mi          17%
distsys-worker          317m         6%       988Mi           12%
NAME                       CPU(cores)   MEMORY(bytes)
backend-7c5db8b648-6w8xp   13m          46Mi
backend-7c5db8b648-gpl8d   13m          47Mi
No numbers?

If kubectl top says error: Metrics API not available for more than a minute, the metrics-server is almost certainly rejecting the kubelet certificate — check that --kubelet-insecure-tls is present in its args (kubectl get deploy metrics-server -n kube-system -o yaml | grep insecure). This is the single most common metrics-server-on-KIND failure.

Step 6 — Autoscale the backend with an HPA under real load​

Create a HorizontalPodAutoscaler for the backend: keep average CPU near 50% of each Pod's request, between 2 and 6 replicas.

cat k8s/backend-hpa.yaml
kubectl apply -f k8s/backend-hpa.yaml
kubectl get hpa backend -n fernwood

Expected output

apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: backend
  namespace: fernwood
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: backend
  minReplicas: 2
  maxReplicas: 6
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50
NAME      REFERENCE            TARGETS         MINPODS   MAXPODS   REPLICAS   AGE
backend   Deployment/backend   cpu: 26%/50%    2         6         2          60s

At idle the backend sits around 26%/50% — comfortably under target, so it stays at 2 replicas. Now generate real load. The load-generator manifest runs four Pods, each hammering the backend in a tight loop:

kubectl apply -f k8s/load-generator.yaml
kubectl rollout status deployment/load-generator -n fernwood

Watch the HPA respond (re-run this every 15–20 seconds, or use -w):

kubectl get hpa backend -n fernwood
kubectl get pods -n fernwood -l tier=backend

Expected output (over ~90 seconds as load ramps)

NAME      REFERENCE            TARGETS         MINPODS   MAXPODS   REPLICAS
backend   Deployment/backend   cpu: 72%/50%    2         6         3
...
NAME      REFERENCE            TARGETS         MINPODS   MAXPODS   REPLICAS
backend   Deployment/backend   cpu: 656%/50%   2         6         6

The HPA crossed the target and scaled the backend 2 → 3 → 6 (its max) within about a minute, with no kubectl scale from you. At peak all six Pods share the load:

kubectl top pods -n fernwood -l tier=backend

Expected output

NAME                       CPU(cores)   MEMORY(bytes)
backend-7c5db8b648-6w8xp   101m         47Mi
backend-7c5db8b648-cmxld   108m         46Mi
backend-7c5db8b648-csztj   87m          47Mi
backend-7c5db8b648-gpl8d   106m         48Mi
backend-7c5db8b648-scbn8   74m          48Mi
backend-7c5db8b648-wzjc2   101m         47Mi

Now remove the load and watch it scale back down:

kubectl delete -f k8s/load-generator.yaml

Scale-down is deliberately slow. The HPA applies a 5-minute stabilization window by default: it will not shrink until the demand has stayed low for that whole window, so a brief dip in traffic does not cause it to drop Pods it is about to need again. Keep an eye on it:

kubectl get hpa backend -n fernwood

Expected output (utilization drops immediately; replicas hold, then fall ~5 min later)

NAME      REFERENCE            TARGETS        MINPODS   MAXPODS   REPLICAS
backend   Deployment/backend   cpu: 19%/50%   2         6         6
...
NAME      REFERENCE            TARGETS        MINPODS   MAXPODS   REPLICAS
backend   Deployment/backend   cpu: 22%/50%   2         6         2

CPU falls back under target within seconds, but the replica count holds at 6 for about five minutes before returning to the floor of 2. That patience is a feature — the deep-dive shows how to tune the window.

Step 7 — Case study: deploy a Spring Boot service the same way​

Everything so far applied the Deployment + Service pattern to a Node frontend and a Python backend. The pattern does not care about the language. To prove it, deploy a stock Spring Boot (Java) service with the same two objects. openeuler/spring-boot is a small public Spring Boot 4 app on Docker Hub that serves Hello World! on port 8080 — and unlike the fernwood-* images (built locally, kind loaded), this one is public, so Kubernetes just pulls it. It is a standalone case study; it does not talk to the Fernwood tiers.

cat k8s/springboot-casestudy.yaml
kubectl apply -f k8s/springboot-casestudy.yaml
kubectl rollout status deployment/springboot-demo -n fernwood --timeout=300s

Expected output

deployment.apps/springboot-demo created
service/springboot-demo created
Waiting for deployment "springboot-demo" rollout to finish: 1 of 2 updated replicas are available...
deployment "springboot-demo" successfully rolled out
First pull is large

The image is ~1.1 GB, so the first rollout waits on a real pull — give it a couple of minutes. It is multi-arch, so it runs on both Intel and Apple-Silicon nodes.

Prove it is reachable through its Service, and confirm from the logs it really is Spring Boot:

kubectl exec -n fernwood curler -- wget -qO- http://springboot-demo:8080/
echo
POD=$(kubectl get pods -n fernwood -l app=springboot-demo -o jsonpath='{.items[0].metadata.name}')
kubectl logs "$POD" -n fernwood | grep -E "Spring Boot|Started Application"

Expected output

Hello World!
 :: Spring Boot ::                (v4.0.2)
2026-08-03T19:45:56.986Z  INFO 1 --- ... : Started Application in 5.779 seconds (process running for 6.634)

That is the whole point: the same kind: Deployment + kind: Service you wrote for JavaScript and Python, applied unchanged to Java. Deploy → expose → reachable. The pattern is language-agnostic. To open it in a browser on your laptop, port-forward it:

kubectl port-forward -n fernwood service/springboot-demo 8080:8080
# then visit http://localhost:8080/  (Ctrl-C to stop)

Teardown​

Leave the cluster and the Fernwood Deployments running — M6 builds on them. Remove only the throwaway pieces from this lab: the case-study Spring Boot service and the sampler Pod. (The load-generator was already deleted in Step 6.)

kubectl delete -f k8s/springboot-casestudy.yaml
kubectl delete pod curler -n fernwood

Expected output

deployment.apps "springboot-demo" deleted
service "springboot-demo" deleted
pod "curler" deleted

What stays running for M6: the frontend Deployment (on :m5), the backend Deployment with its HPA, both Services, and the metrics-server. Confirm the steady state:

kubectl get deploy,hpa,svc -n fernwood

Expected output

NAME                       READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/backend    2/2     2            2           40m
deployment.apps/frontend   3/3     3            3           40m
NAME                                          REFERENCE            TARGETS        MINPODS   MAXPODS   REPLICAS
horizontalpodautoscaler.apps/backend          Deployment/backend   cpu: 26%/50%   2         6         2
NAME               TYPE        CLUSTER-IP      EXTERNAL-IP   PORT(S)        AGE
service/backend    ClusterIP   10.96.171.26    <none>        8080/TCP       98m
service/frontend   NodePort    10.96.78.254    <none>        80:30080/TCP   98m

You have released a version safely, survived a bad release without an outage, and put a service under an autoscaler — the everyday mechanics of running an app on Kubernetes.
