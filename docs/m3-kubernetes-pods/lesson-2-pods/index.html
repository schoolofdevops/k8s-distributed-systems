Working with Pods

▶ M3 · Working with PodsOpen fullscreen ↗

In the last lesson you learned that you hand Kubernetes a declaration and the control plane makes it real. Now you meet the thing you actually declare to run a workload: the Pod. It is the smallest unit Kubernetes will schedule. You never ask Kubernetes to "run a container". You ask it to run a Pod, and the Pod holds the container. Everything you build later (ReplicaSets, Deployments, StatefulSets) is a machine for making and managing Pods. So the whole rest of the course sits on this one object.

The analogy: a shared studio flat, not a single bedroom​

A container, on its own, is like one person with their own room: their own bed, their own stuff, sealed off from everyone else. That is the isolation you have used since M1. Each container gets its own filesystem and its own process space.

A Pod is a shared studio flat that one or more roommates live in. Each roommate still has their own bed and their own belongings, separate filesystems, separate processes. But they share the things that make it one home: one street address, one internal phone line so they can talk to each other just by shouting across the room, and one shared cupboard they can both reach. And crucially, they move house together. The landlord never relocates one roommate and leaves the other behind.

In Kubernetes terms:

  • One street address. Every container in a Pod shares one network namespace, so they share one IP address. You saw the frontend Pod get 192.168.x.x in the lab; if it had two containers, both would answer on that same IP.
  • One internal phone line. Because they share the network namespace, containers in a Pod reach each other on localhost. No DNS, no Service, no network hop. This is the single most important reason Pods exist, and you prove it in the deep dive.
  • One shared cupboard. Containers in a Pod can mount the same volume and pass files through it.
  • They move together. A Pod is scheduled onto one node as a unit. All its containers land on the same node, start together, and are torn down together. Kubernetes never splits a Pod across two nodes.

That is the definition worth memorizing: a Pod is a co-scheduled group of containers that share a network namespace and can share storage. Most Pods hold exactly one container. The shared-flat machinery still matters, because when you do need a second container next to your app, a helper, the Pod is what lets them behave as one unit.

Why not just a container? The problem Pods solve​

You might ask why Kubernetes did not just schedule bare containers. The answer is that real workloads often need a tightly-coupled helper that must live right next to the main process (same address, same disk, same lifecycle), not one network hop away. A log shipper that reads the app's files. A proxy that the app talks to on localhost. A one-time setup step that must finish before the app starts. If those were separate schedulable units, Kubernetes might place them on different nodes, start them in the wrong order, or keep one alive after the other died. The Pod is the guarantee that a group of containers is treated as one: placed together, networked together, and managed together.

The object model: the shape every manifest shares​

In the last lesson you saw the four-part shape. Now that you are about to write real Pods, here is what each part is for. Every Kubernetes object, Pod, Service, Deployment, everything, uses these same four fields, so learning it once pays off everywhere.

apiVersion: v1        # which version of the API this object speaks
kind: Pod             # what kind of object this is
metadata:             # identity: name, labels, namespace
  name: frontend
  labels:
    app: fernwood
    tier: frontend
spec:                 # the desired state — what you want to be true
  containers:
    - name: frontend
      image: fernwood-frontend:m2
  • apiVersion is the API group and version. A Pod is core and stable, so it is just v1. Later objects look like apps/v1.
  • kind is the type of object. This tells the API server which controller cares about it.
  • metadata is how the object is identified: its name, its namespace (you use the default one until M4), and its labels. Labels are simple key-value tags, and they look unimportant right up until M4, where selectors use them to group Pods. Get in the habit of labelling now.
  • spec is the desired state. Everything about what you want goes here. When you later read that a controller "reconciles the spec," this is the spec it means.

There is a fifth field you do not write but will read constantly: status. Kubernetes fills it in. spec is what you asked for; status is what is actually true right now. The whole system is the gap between those two being watched and closed.

Multi-container Pods: sidecar and init (recognize them now)​

Most of your Pods hold one container. Two patterns add a second, and you only need to recognize them here. The deep dive runs both against Fernwood Goods.

  • init container is a container that runs to completion before the main container starts, and must succeed first. Use it for setup that has to happen first: wait for a dependency to be reachable, run a migration, fetch a file. If it fails, the Pod does not proceed. It runs, finishes, and gets out of the way.
  • sidecar is a helper that runs alongside the main container for the whole life of the Pod. A log shipper, a proxy, a metrics exporter. It shares the Pod's network and can share its volumes, which is exactly why it belongs in the Pod and not in a separate one.

That is enough to spot them in a manifest. Both come alive in the deep dive.

Health checks: three questions Kubernetes keeps asking​

A container being "up" does not mean it is working. A process can be running but wedged, or running but not finished starting. Kubernetes does not guess. It asks, over and over, using probes. There are three, and each answers a different question. Getting them right is the difference between an outage that self-heals and one that pages you.

  • livenessProbe: "is it still alive, or should I restart it?" If the liveness probe fails, Kubernetes kills the container and restarts it. Use it to recover from a process that has hung, alive as far as the OS is concerned, but not actually serving. Point it at something cheap that only passes when the app is genuinely functioning. Get this wrong and you get needless restarts, so it must be a true signal of health, not just "the port is open."
  • readinessProbe: "is it ready for traffic yet?" If the readiness probe fails, Kubernetes does not restart anything. It just takes the Pod out of Service load-balancing until it passes again. This is how a Pod that is briefly busy, warming a cache, or waiting on a dependency stops receiving requests without being killed. It is the probe that makes rolling updates safe (M5), because traffic only goes to Pods that say they are ready.
  • startupProbe: "is it done booting yet?" Some apps start slowly, a JVM warming up, a large cache loading. The startup probe holds off the liveness and readiness probes until the app first reports healthy, so a slow boot is not mistaken for a hang and killed before it ever gets going. You reach for it when start time is long and variable.
Which does a real workload need?

Almost every serving workload wants a readiness probe. Without it, a Service will send traffic to a Pod that is not ready. A liveness probe is worth adding when the app can wedge in a way a restart fixes; skip it or keep it gentle if a false failure would cause restart storms. A startup probe earns its place only when boot time is long enough that liveness would otherwise fire during startup. The Fernwood Goods frontend starts fast and serves a cheap /healthz, so in the lab you give it liveness and readiness and leave startup out, which is the honest choice for this app.

Here is what a probe looks like in a spec. This is the exact pair you apply in the lab:

readinessProbe:
  httpGet:
    path: /healthz
    port: 3000
  initialDelaySeconds: 2
  periodSeconds: 5
livenessProbe:
  httpGet:
    path: /healthz
    port: 3000
  initialDelaySeconds: 5
  periodSeconds: 10

The frontend already exposes /healthz, its own liveness, independent of the backend. That independence matters: the frontend degrades gracefully when the backend is down (you built that in M1), so its health endpoint must report the frontend's health, not the backend's. If you pointed liveness at something that also checked the backend, a backend outage would restart every healthy frontend, a self-inflicted outage. Probes must answer for the container they guard and nothing else.

Into the lab​

You now have the object (the Pod), its shape (apiVersion/kind/metadata/spec), and the three probes. In the lab you write a Pod for the Fernwood Goods frontend, apply it to the cluster you stood up, exec into it, read its logs, and watch its probes work. Then you deliberately break three Pods: one that cannot be scheduled, one whose image cannot be pulled, one that crashes on start. You learn to read what Kubernetes tells you, because most of the job is diagnosing the Pod that did not come up.
