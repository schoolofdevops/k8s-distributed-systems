Deep Dive — Multi-container Pods: init containers and sidecars

The lab ran a Pod with one container, which is what most Pods are. Part 2 uses the part of a Pod you have not needed yet: the ability to hold more than one container and treat them as a single unit. You already know why the machinery exists — shared network namespace, shared volumes, co-scheduling. Here you make it do real work for Fernwood Goods, and you watch the two multi-container patterns that cover almost every real case: the init container and the sidecar.

This is not a rerun of the lesson. The lesson taught you to recognize the patterns; this runs both, live, against the app, and folds in exactly what the cluster printed.

Before you start

You need the running distsys cluster and the frontend Pod from the lab still in place. Work from labs/distributed-app. You also load the backend image this time, because the init container demo waits for a real backend.

The analogy: opening a shop for the day​

The lab's single-container Pod was a stall with one person in it. A multi-container Pod is a shop with a small crew who all work the same floor. Before the shop opens, someone has to unlock, check the stock delivery arrived, and flip the sign to OPEN — that job runs once, first, and if the delivery never turns up the shop does not open. That is the init container. Then, while the shop is open, someone stands at the till taking customers (the main app), and someone else keeps restocking shelves and noting what is low the whole day (the sidecar) — a continuous helper, sharing the same floor, for as long as the shop is open. Same floor is the point: they share the Pod's network and can share its storage, which is why they belong in one Pod and not in separate ones.

Two containers you are about to add​

  • An init container named wait-for-backend — it blocks until the backend answers /api/health, then exits. The main frontend container does not start until it succeeds. This encodes a real dependency: do not start the frontend until the thing it talks to is up.
  • A native sidecar named healthz-logger — it runs for the whole life of the Pod, polling the frontend on localhost:3000/healthz every few seconds and logging the result. It is a native sidecar because it is declared as an init container with restartPolicy: Always — the modern, stable way to run a sidecar (Kubernetes 1.29+), which guarantees it starts before the main container and is torn down after it.

Why does the sidecar reach the app on localhost while the backend is a separate Pod reached by IP? Because the sidecar is in the same Pod as the frontend — same network namespace, so localhost — but the backend is its own Pod with its own IP. That contrast is the whole shared-namespace idea made concrete.

Step 1 — Run a backend Pod for the init container to wait on​

The init container waits for a real backend, so put one on the cluster. There are no Services yet (that is M4), so a bare Pod is exactly right here. Load the backend image and run it:

kind load docker-image fernwood-backend:m2 --name distsys
kubectl run backend --image=fernwood-backend:m2 --image-pull-policy=IfNotPresent --port=8080
kubectl wait --for=condition=Ready pod/backend --timeout=60s

Expected output

pod/backend created
pod/backend condition met

Grab the backend Pod's IP — without a Service, its IP is how you reach it. Notice you have to look it up and it is not stable across restarts; that pain is exactly what Services fix in M4, so feel it now:

kubectl get pod backend -o jsonpath='{.status.podIP}{"\n"}'

Expected output

192.168.40.70

Step 2 — Look at the multi-container spec​

The manifest is at labs/distributed-app/k8s/frontend-multicontainer.yaml. The key parts:

spec:
  initContainers:
    - name: wait-for-backend        # runs to completion first
      image: fernwood-frontend:m2
      command:
        - sh
        - -c
        - |
          until wget -q -O- http://BACKEND_IP:8080/api/health >/dev/null 2>&1; do
            echo "backend not ready yet, retrying in 2s"; sleep 2
          done
          echo "backend is up — releasing the frontend"
    - name: healthz-logger          # a sidecar: init container + restartPolicy Always
      image: fernwood-frontend:m2
      restartPolicy: Always
      command:
        - sh
        - -c
        - |
          while true; do
            echo "[healthz-logger] $(wget -q -O- http://localhost:3000/healthz || echo 'app not answering yet')"
            sleep 10
          done
  containers:
    - name: frontend                # the main app
      image: fernwood-frontend:m2
      env:
        - name: BACKEND_URL
          value: "http://BACKEND_IP:8080"

The one line that turns an init container into a sidecar is restartPolicy: Always on healthz-logger. Without it, Kubernetes would wait for that container to finish before starting the main container — and it never finishes, so the Pod would hang. With it, Kubernetes knows this is a long-lived helper: start it, then start the main container alongside.

Step 3 — Apply it with the backend IP substituted in​

The spec has BACKEND_IP as a placeholder because a Pod IP is only known at runtime. Substitute the IP you looked up and apply:

BACKEND_IP=$(kubectl get pod backend -o jsonpath='{.status.podIP}')
sed "s/BACKEND_IP/$BACKEND_IP/g" k8s/frontend-multicontainer.yaml | kubectl apply -f -
kubectl wait --for=condition=Ready pod/frontend-mc --timeout=90s
kubectl get pod frontend-mc

Expected output

pod/frontend-mc created
pod/frontend-mc condition met
NAME          READY   STATUS    RESTARTS   AGE
frontend-mc   2/2     Running   0          20s

Read the READY column: 2/2. That is the main container and the sidecar, both up. The init container is not counted here because it has already done its job and exited — you see it separately next.

Step 4 — Watch the init container gate the startup​

Read the init container's own logs. It waited for the backend, then released the frontend:

kubectl logs frontend-mc -c wait-for-backend

Expected output

waiting for backend at http://192.168.40.70:8080 ...
backend is up — releasing the frontend

That single line — backend is up — releasing the frontend — is the ordering guarantee working. The main frontend container did not start until this container succeeded. If you had never started the backend in Step 1, this init container would loop on backend not ready yet forever and the Pod would sit in Init:0/1, never reaching the main container. That is the point of an init container: a hard precondition, enforced by the Pod.

See it hold, if you want to prove it

Delete the backend (kubectl delete pod backend), re-apply frontend-mc, and kubectl get pod frontend-mc will show Init:0/1 — stuck, because the precondition is not met. Re-create the backend and it proceeds. Remember to restore the backend afterward, because the next step needs the Pod running.

Step 5 — Watch the sidecar reach the app over localhost​

Now the sidecar. It has been polling the frontend on localhost:3000 since the Pod started. Read its logs:

kubectl logs frontend-mc -c healthz-logger

Expected output

wget: can't connect to remote host: Connection refused
[healthz-logger] app not answering yet
[healthz-logger] {"service":"frontend","status":"ok","hostname":"frontend-mc"}
[healthz-logger] {"service":"frontend","status":"ok","hostname":"frontend-mc"}

There are two things worth seeing in that output. First, the early Connection refused / app not answering yet — the sidecar started a moment before the main container was listening, tried anyway, and recovered on the next loop. That is normal and honest: containers in a Pod start close together but not in a guaranteed instant-ready order (that is what probes are for). Second, and this is the payoff: the sidecar reached the app at localhost:3000 and got a healthy answer. It did not use a Service, a DNS name, or the Pod's IP — it used localhost, because it shares the frontend's network namespace. That is the shared-namespace property from the lesson, proven with real output.

Confirm the shape of the Pod — which containers are init (and which of those is the sidecar) versus main:

kubectl get pod frontend-mc -o jsonpath='{range .spec.initContainers[*]}init: {.name} restartPolicy={.restartPolicy}{"\n"}{end}{range .spec.containers[*]}main: {.name}{"\n"}{end}'

Expected output

init: wait-for-backend restartPolicy=
init: healthz-logger restartPolicy=Always
main: frontend

Both helpers live under initContainers, but only healthz-logger carries restartPolicy=Always — that is the flag that makes it a long-lived sidecar rather than a run-once init step. wait-for-backend has no restart policy, so it runs once and exits. One list, two very different lifecycles, told apart by one field.

Step 6 — Clean up the deep-dive Pods​

These Pods were for the demo. Remove them and leave the cluster in the same state the lab left it — just the working frontend Pod running:

kubectl delete pod frontend-mc backend
kubectl get pods

Expected output

pod "frontend-mc" deleted
pod "backend" deleted
NAME       READY   STATUS    RESTARTS   AGE     IP              NODE             NOMINATED NODE   READINESS GATES
frontend   1/1     Running   0          8m10s   192.168.40.66   distsys-worker   <none>           <none>

Where you will use this​

  • An init container that waits for a dependency is how you stop a service from starting before the thing it needs is reachable — a database, a config service, a migration that must run first. You just did it for the frontend/backend pair. In production it is the difference between a clean startup and a crash loop while a dependency comes up.
  • A sidecar is how you add a capability to a Pod without changing the app's code: a log shipper that reads the app's files, a proxy the app talks to on localhost, a metrics exporter. Because it shares the Pod's namespace and volumes, it can see what the app sees. When you meet a service mesh, its data plane is a sidecar in every Pod — this is the mechanism underneath it.
  • The localhost reach between containers is worth remembering the next time you are tempted to put two tightly-coupled processes in separate Pods. If they must share an address or a disk and live and die together, they belong in one Pod. If they scale independently, they do not — and that judgement is one you will make constantly from M4 on.

You have now used every part of a Pod: one container, health probes, and multiple containers with two lifecycles. From here the course stops asking you to place Pods by hand — M4 hands that to a controller.
