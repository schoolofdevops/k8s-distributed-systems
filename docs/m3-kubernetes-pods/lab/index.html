Lab — Stand up the cluster and run your first Pod

This lab is the biggest infrastructure step in the course. You build one Kubernetes cluster with KIND and use it from here all the way to Module 8 — it is not torn down at the end like the M1 and M2 containers were. You then put the Fernwood Goods frontend on it as a Pod, inspect it from every angle, and finish by deliberately breaking three Pods so you learn to read what Kubernetes tells you when a workload does not come up.

What you will end up with

A running two-node cluster named distsys (context kind-distsys), with Calico as its network plugin, and the Fernwood Goods frontend running as a Pod with liveness and readiness probes. The cluster stays up after this lab. Every later module does kubectl config use-context kind-distsys and keeps building on it.

Before you start​

You need Docker running, plus kubectl, kind, and helm on your path (the Setup page covers installing them). Work from the labs repo so the cluster config and manifests are on hand.

docker version --format '{{.Server.Version}}'
kubectl version --client -o json | jq -r '.clientVersion.gitVersion'
kind version
helm version --short
cd labs/distributed-app

Expected output

29.5.2
v1.32.2
kind v0.27.0 go1.23.6 darwin/arm64
v4.2.1+gd591a19
note

Your versions will differ. Any recent Docker (24+), a kubectl within one minor of your cluster, KIND 0.20+, and Helm 3.12+ are fine. What matters is that all four commands return a version and none error.

Step 1 — Create the cluster (with the default network plugin disabled)​

The cluster is defined by a config file so you can recreate it identically if you ever need to. It lives at labs/clusters/kind-distsys.yaml. Two things in it are deliberate: the name distsys (so it does not collide with any other KIND cluster on your machine), and disableDefaultCNI: true — this turns off KIND's built-in network plugin (kindnet) so you can install Calico instead. You do this because kindnet does not enforce NetworkPolicy, and Module 8 depends on that.

cat ../clusters/kind-distsys.yaml

Expected output (the parts that matter)

kind: Cluster
apiVersion: kind.x-k8s.io/v1alpha4
name: distsys
networking:
  disableDefaultCNI: true
  podSubnet: "192.168.0.0/16"
nodes:
  - role: control-plane
  - role: worker

Create the cluster from that config:

kind create cluster --config ../clusters/kind-distsys.yaml

Expected output

Creating cluster "distsys" ...
 ✓ Ensuring node image (kindest/node:v1.32.2) 🖼
 ✓ Preparing nodes 📦 📦
 ✓ Writing configuration 📜
 ✓ Starting control-plane 🕹️
 ✓ Installing StorageClass 💾
 ✓ Joining worker nodes 🚜
Set kubectl context to "kind-distsys"
You can now use your cluster with:

kubectl cluster-info --context kind-distsys

KIND set your kubectl context to kind-distsys for you. Confirm the nodes exist — they will report NotReady, and that is expected, because there is no network plugin yet:

kubectl get nodes

Expected output

NAME                    STATUS     ROLES           AGE   VERSION
distsys-control-plane   NotReady   control-plane   22s   v1.32.2
distsys-worker          NotReady   <none>          10s   v1.32.2
note

NotReady here is correct, not a failure. A node is only Ready once a CNI network plugin is running on it. You install that next, and then they flip to Ready.

Step 2 — Install Calico as the network plugin​

Install Calico's operator, then tell it to install Calico with its default settings. The operator's default pod network is 192.168.0.0/16, which is exactly the podSubnet in your cluster config, so the two already agree.

kubectl apply -f https://raw.githubusercontent.com/projectcalico/calico/v3.29.1/manifests/tigera-operator.yaml

Expected output (last lines)

serviceaccount/tigera-operator created
clusterrole.rbac.authorization.k8s.io/tigera-operator created
clusterrolebinding.rbac.authorization.k8s.io/tigera-operator created
deployment.apps/tigera-operator created
kubectl apply -f https://raw.githubusercontent.com/projectcalico/calico/v3.29.1/manifests/custom-resources.yaml

Expected output

installation.operator.tigera.io/default created
apiserver.operator.tigera.io/default created

Calico now installs itself across the cluster. This takes a couple of minutes — it pulls images and starts a pod on every node. Wait for the nodes to go Ready:

kubectl wait --for=condition=Ready nodes --all --timeout=180s

Expected output

node/distsys-control-plane condition met
node/distsys-worker condition met
note

If kubectl wait times out the first time, it usually just means Calico is still pulling images. Re-run the same kubectl wait command, or watch progress with kubectl get pods -n calico-system -w until the pods are Running, then press Ctrl-C.

Confirm the whole cluster is healthy before you put anything on it. First the nodes — both Ready, each on the same Kubernetes version:

kubectl get nodes -o wide

Every control-plane component from the lesson is right there in kube-system: etcd, kube-apiserver, kube-scheduler, kube-controller-manager, and a kube-proxy on each node. The calico-node pods — one per node — are the network plugin that flipped your nodes to Ready.

Finally, confirm which context you are pointed at. Every later module assumes this:

kubectl config current-context

Expected output

note

The exact Pod name suffixes (-9dh8w, -622cz, and so on) are generated and will differ on your machine, as will the AGE values. What must be true is that every Pod shows Running (or Completed) and the READY column shows all containers up (1/1, 2/2).

Step 4 — Load the frontend image into the cluster​

KIND nodes do not share your host's Docker image cache. If you reference fernwood-frontend:m2 in a Pod right now, the kubelet will try to pull it from a registry and fail, because it only exists locally. kind load copies your local image into the cluster's nodes.

kind load docker-image fernwood-frontend:m2 --name distsys

Expected output

Image: "fernwood-frontend:m2" with ID "sha256:b614262e0581..." not yet present on node "distsys-control-plane", loading...
Image: "fernwood-frontend:m2" with ID "sha256:b614262e0581..." not yet present on node "distsys-worker", loading...
note

This is the M2 image you already built. If you do not have it, build it first with docker build -t fernwood-frontend:m2 ./frontend from labs/distributed-app, then re-run the kind load command. The image ID will differ from the one above.

Step 5 — Write and run the frontend Pod​

The Pod spec is at labs/distributed-app/k8s/frontend-pod.yaml. It declares one container, pins imagePullPolicy: IfNotPresent so the kubelet uses the image you just loaded instead of reaching for a registry, and adds the liveness and readiness probes from the lesson, both pointed at the frontend's own /healthz.

cat k8s/frontend-pod.yaml

Expected output

apiVersion: v1
kind: Pod
metadata:
  name: frontend
  labels:
    app: fernwood
    tier: frontend
spec:
  containers:
    - name: frontend
      image: fernwood-frontend:m2
      # KIND nodes do not share your host's Docker image cache, so we load the
      # image with `kind load` and tell Kubernetes never to pull it from a
      # registry. Without this the Pod would try Docker Hub and fail.
      imagePullPolicy: IfNotPresent
      ports:
        - containerPort: 3000
      # Readiness: is this container ready to receive traffic yet? Until /healthz
      # answers 200, Kubernetes keeps the Pod out of any Service load-balancing.
      readinessProbe:
        httpGet:
          path: /healthz
          port: 3000
        initialDelaySeconds: 2
        periodSeconds: 5
      # Liveness: is the container still healthy? If /healthz stops answering,
      # the kubelet restarts the container in place.
      livenessProbe:
        httpGet:
          path: /healthz
          port: 3000
        initialDelaySeconds: 5
        periodSeconds: 10

Apply it, then wait for it to pass its readiness probe:

kubectl apply -f k8s/frontend-pod.yaml
kubectl wait --for=condition=Ready pod/frontend --timeout=60s

Expected output

pod/frontend created
pod/frontend condition met

See where it landed:

kubectl get pod frontend -o wide

Expected output

NAME       READY   STATUS    RESTARTS   AGE   IP              NODE             NOMINATED NODE   READINESS GATES
frontend   1/1     Running   0          4s    192.168.40.66   distsys-worker   <none>           <none>

Two things to read here. READY is 1/1 — the one container is up and passing its readiness probe. The IP is 192.168.40.66, from Calico's 192.168.0.0/16 pool, and the scheduler placed the Pod on distsys-worker — you declared what, the control plane decided where.

note

Your Pod's IP, NODE, and AGE will differ. The IP comes from Calico's pool so it will start 192.168.; the node may be either one. What matters is 1/1 and Running.

Step 6 — Inspect the Pod: logs, exec, describe​

This is the daily work of operating Pods. First, read the container's logs — the frontend logs a line on startup:

kubectl logs frontend

Expected output

frontend listening on :3000, backend at http://backend:8080

Now exec into the running container and ask the app about itself. The frontend answers its own health endpoint on localhost from inside the Pod:

kubectl exec frontend -- wget -qO- http://localhost:3000/healthz

Expected output

{"service":"frontend","status":"ok","hostname":"frontend"}

The hostname the app reports is the Pod's name — inside a Pod, the container's hostname is the Pod name. Finally, describe the Pod to see the events the kubelet recorded while starting it:

kubectl describe pod frontend

Expected output (the Events section at the end)

Events:
  Type    Reason     Age   From               Message
  ----    ------     ----  ----               -------
  Normal  Scheduled  13s   default-scheduler  Successfully assigned default/frontend to distsys-worker
  Normal  Pulled     11s   kubelet            Container image "fernwood-frontend:m2" already present on machine
  Normal  Created    11s   kubelet            Created container: frontend
  Normal  Started    11s   kubelet            Started container frontend

Read that sequence top to bottom — it is the lesson's architecture happening in order. The scheduler assigned the Pod to a node. The kubelet on that node saw the image was already present (because you loaded it), created the container, and started it. kubectl describe is the first command you reach for whenever a Pod is not doing what you expect, because these events tell you how far it got.

Step 7 — Reach the app from your machine​

There is no Service yet — that is M4 — so to open the app from your laptop you forward a local port straight to the Pod. Run this in one terminal:

kubectl port-forward pod/frontend 3000:3000

Expected output

Forwarding from 127.0.0.1:3000 -> 3000
Forwarding from [::1]:3000 -> 3000

In another terminal, hit it:

curl -s http://localhost:3000/healthz

Expected output

{"service":"frontend","status":"ok","hostname":"frontend"}

Open http://localhost:3000 in a browser and you will see the Fernwood Goods page, served by the Pod, showing its hostname. The backend is not on the cluster yet, so the page renders in its degraded state — that is M1's graceful degradation working exactly as designed. When you are done, press Ctrl-C in the port-forward terminal to stop it.

Step 8 — Troubleshoot a Pod stuck in Pending​

Most of operating Kubernetes is diagnosing the Pod that did not come up. The next three steps each break a Pod in a different way. Work through them — reading these signals is the skill.

The first broken Pod asks for 100 CPUs, which no node has, so the scheduler can never place it. Apply it:

kubectl apply -f k8s/broken/frontend-pending.yaml
kubectl get pod frontend-pending

Expected output

pod/frontend-pending created
NAME               READY   STATUS    RESTARTS   AGE
frontend-pending   0/1     Pending   0          10s

Pending means the Pod exists in the cluster but has not been placed on a node. To find out why, the events are authoritative — describe it and read the bottom:

kubectl describe pod frontend-pending

Expected output (Events section)

Events:
  Type     Reason            Age   From               Message
  ----     ------            ----  ----               -------
  Warning  FailedScheduling  46s   default-scheduler  0/2 nodes are available: 1 Insufficient cpu, 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }. preemption: 0/2 nodes are available: 1 No preemption victims found for incoming pod, 1 Preemption is not helpful for scheduling.

The message is precise: 0/2 nodes are available: 1 Insufficient cpu — the worker cannot satisfy the CPU request — and the control-plane node is excluded by a taint (a marker that keeps ordinary workloads off the control plane). The fix is to ask for a sane amount of CPU. Delete the broken Pod and re-apply it with a realistic request:

kubectl delete pod frontend-pending
sed 's/cpu: "100"/cpu: "100m"/' k8s/broken/frontend-pending.yaml | kubectl apply -f -
kubectl wait --for=condition=Ready pod/frontend-pending --timeout=30s
kubectl get pod frontend-pending -o wide

Expected output

pod "frontend-pending" deleted
pod/frontend-pending created
pod/frontend-pending condition met
NAME               READY   STATUS    RESTARTS   AGE   IP              NODE             NOMINATED NODE   READINESS GATES
frontend-pending   1/1     Running   0          2s    192.168.40.69   distsys-worker   <none>           <none>

100m is 100 millicpu — a tenth of one core — which the worker has to spare, so the scheduler places it immediately. Lesson: a Pending Pod is almost always a scheduling problem — not enough resources, a nodeSelector nothing matches, or a taint — and kubectl describe tells you which. Clean this one up before moving on:

kubectl delete pod frontend-pending

Expected output

pod "frontend-pending" deleted

Step 9 — Troubleshoot ImagePullBackOff​

The next Pod references fernwood-frontend:m9, a tag that was never built or loaded. Apply it and give the kubelet a few seconds to try pulling:

kubectl apply -f k8s/broken/frontend-imagepull.yaml
sleep 15
kubectl get pod frontend-badimage

Expected output

pod/frontend-badimage created
NAME                READY   STATUS             RESTARTS   AGE
frontend-badimage   0/1     ImagePullBackOff   0          15s
note

The kubelet cycles between ErrImagePull (actively retrying) and ImagePullBackOff (waiting out the backoff before the next retry). Depending on exactly when you run get, you may see either one — both mean the same thing. Re-run the command a couple of times if you land on ErrImagePull and want to see ImagePullBackOff too.

ImagePullBackOff means the kubelet could not pull the image and is waiting, with a growing delay, before trying again. The events say exactly why:

kubectl describe pod frontend-badimage

Expected output (Events section)

Events:
  Type     Reason     Age                From               Message
  ----     ------     ----               ----               -------
  Normal   Scheduled  46s                default-scheduler  Successfully assigned default/frontend-badimage to distsys-worker
  Normal   Pulling    1s (x3 over 45s)   kubelet            Pulling image "fernwood-frontend:m9"
  Warning  Failed     0s (x3 over 43s)   kubelet            Failed to pull image "fernwood-frontend:m9": failed to resolve reference "docker.io/library/fernwood-frontend:m9": pull access denied, repository does not exist or may require authorization: server message: insufficient_scope: authorization failed
  Warning  Failed     0s (x3 over 43s)   kubelet            Error: ErrImagePull
  Warning  Failed     12s (x2 over 43s)  kubelet            Error: ImagePullBackOff

Notice the Pod was scheduled — this is not a placement problem, it is a pull problem, which happens after placement. The kubelet tried docker.io/library/fernwood-frontend:m9 and got "repository does not exist." The fix is the correct tag; there is nothing to repair on the cluster. Delete it:

kubectl delete pod frontend-badimage

Expected output

pod "frontend-badimage" deleted
note

On a real registry, ImagePullBackOff most often means one of three things: a typo in the image name or tag, a private registry you have not given the cluster credentials for, or — on KIND specifically — an image you forgot to kind load. The events tell you which; read them before changing anything.

Step 10 — Troubleshoot CrashLoopBackOff​

The last Pod starts fine but its container exits immediately with an error, so Kubernetes restarts it, it exits again, and the kubelet backs off between restarts. Apply it and watch the restart count climb:

kubectl apply -f k8s/broken/frontend-crashloop.yaml
sleep 20
kubectl get pod frontend-crash

Expected output

pod/frontend-crash created
NAME             READY   STATUS             RESTARTS      AGE
frontend-crash   0/1     CrashLoopBackOff   2 (5s ago)    20s
note

STATUS cycles between Error (right after a crash) and CrashLoopBackOff (waiting out the backoff before the next restart) — both mean the same thing, and the exact RESTARTS/AGE numbers depend on when you happen to run get. What matters is that RESTARTS keeps climbing.

CrashLoopBackOff is different from the previous two: the image pulled and the container ran — it just died. When a container has run, the answer is in its logs, not its events:

kubectl logs frontend-crash

Expected output

starting up...
fatal: config missing, exiting

There it is — the container printed a fatal error and exited. (This one is a deliberately broken command in the spec; a real crash loop is usually a missing config value, a bad environment variable, or a failed connection the app treats as fatal.) The events confirm the restart pattern:

kubectl describe pod frontend-crash

Expected output (Events section)

Events:
  Type     Reason     Age                From               Message
  ----     ------     ----               ----               -------
  Normal   Scheduled  56s                default-scheduler  Successfully assigned default/frontend-crash to distsys-worker
  Normal   Pulled     14s (x4 over 55s)  kubelet            Container image "fernwood-frontend:m2" already present on machine
  Normal   Created    14s (x4 over 55s)  kubelet            Created container: frontend
  Normal   Started    14s (x4 over 55s)  kubelet            Started container frontend
  Warning  BackOff    1s (x6 over 53s)   kubelet            Back-off restarting failed container frontend in pod frontend-crash_default(...)

The x4 on Created/Started is Kubernetes restarting the container over and over; the BackOff warning is it waiting longer between each attempt. Lesson: CrashLoopBackOff means "it ran and died" — go straight to kubectl logs. If the current logs are empty because it died too fast, add --previous to read the logs of the last failed attempt. Delete it:

kubectl delete pod frontend-crash

Expected output

pod "frontend-crash" deleted
The three-signal habit

You just used the whole diagnostic kit. Reach for them in this order: kubectl get pod tells you the state; kubectl describe pod tells you the events (best for Pending and ImagePullBackOff, which fail before or during startup); kubectl logs tells you what the app said (best for CrashLoopBackOff, which fails after startup). Almost every Pod problem is diagnosed by these three.

Teardown — leave the cluster running​

This teardown is different from every module before it: do not delete the cluster. You reuse it through Module 8. All you clean up are the broken troubleshooting Pods from the last three steps — Steps 8, 9, and 10 each deleted their own as you went. Confirm only the working frontend Pod remains:

kubectl get pods

Expected output

NAME       READY   STATUS    RESTARTS   AGE     IP              NODE             NOMINATED NODE   READINESS GATES
frontend   1/1     Running   0          8m10s   192.168.40.66   distsys-worker   <none>           <none>

Leave that Pod running — Module 4 picks it up from here and turns it into a self-healing, scalable ReplicaSet. The cluster, Calico, and this one Pod are the state you carry forward.

Do not run kind delete cluster

If you ever do need to rebuild the cluster from scratch, the command is kind delete cluster --name distsys followed by re-running this lab from Step 1 — but you should not need to. The whole point is that this cluster is long-lived. Deleting it means redoing every later module's setup.

What you proved​

  • A Kubernetes cluster is a control plane plus nodes, and you saw every component from the lesson running for real — etcd, kube-apiserver, kube-scheduler, kube-controller-manager, kubelet (via node readiness), and kube-proxy.
  • Networking is pluggable: you disabled KIND's default plugin and installed Calico through the CNI, and the cluster came up Ready with Pod IPs from Calico's pool.
  • A Pod is how you run a workload. You declared one, the scheduler placed it, the kubelet ran it, and its readiness probe gated it to 1/1.
  • You can diagnose the three Pod failures you will hit most — Pending, ImagePullBackOff, CrashLoopBackOff — using get, describe, and logs.

In the next module you stop managing this Pod by hand. You give the cluster a desired count and let a controller keep that many frontends alive and reschedule them when a node dies — the reconciliation loop from the lesson, doing your job for you.
