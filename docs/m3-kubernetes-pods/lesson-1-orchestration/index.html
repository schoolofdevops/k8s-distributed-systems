Orchestration with Kubernetes

▶ M3 · Orchestration with KubernetesOpen fullscreen ↗

In M1 and M2 you ran Fernwood Goods on one machine. First with docker run, then with a Compose file that wrote the whole topology down. At the end of M2 you saw the ceiling: one host. If that host reboots, the app is down until someone notices and runs docker compose up again. If the frontend gets busy, you cannot add a second copy because both would want host port 3000. And if the backend container crashes, Compose does not move it somewhere healthy. It just restarts it on the same host, and if the host itself is gone, nothing restarts at all.

That gap is the reason this module exists. Everything you built so far is correct and useful, and none of it goes away. What changes is who is in charge of keeping it running. Up to now, that was you. From here on, it is Kubernetes.

Where Docker's job ends and Kubernetes' begins​

You already drew this line once, in M1's first lesson, so this is a reminder, not a re-teach. Docker's job is one container on one host: build the image, start the process, give it a network namespace, mount its volumes. Docker does that job well and Kubernetes still relies on it (or a runtime like it) to actually run containers. What Docker does not do is decide where a container should run across many machines, notice when one has died and start a replacement elsewhere, or keep the number of running copies matching a number you asked for. That set of jobs is orchestration: placement, healing, scaling, rollout. And it is exactly the part that hurts when you try to do it by hand on more than one host.

So the seam is clean: Docker (or containerd) runs a container; Kubernetes decides which containers run, how many, where, and what to do when reality drifts from what you asked for.

The analogy: an airport, not a single gate​

Think about a busy airport. Docker, in this picture, is one gate: a plane pulls in, the jet bridge connects, passengers board, the plane leaves. One gate handles one aircraft at a time and does it reliably. That is a container on a host.

Now zoom out to the whole airport running hundreds of flights a day. No single gate agent can run that. There is a control tower and an operations office that runs the airfield. And separately, there are the gates, runways, and ground crews that do the physical work. The tower does not carry luggage or drive a tug. The ground crews do not decide which flights land or which gate a plane parks at. Two different jobs, deliberately kept apart.

Kubernetes is built the same way, and the split has names:

  • The control plane is the tower and the ops office. It makes decisions and holds the plan.
  • The nodes are the gates and ground crews. They run the actual containers and report back.

You talk to the tower. You file a plan, "I want three copies of the frontend running", and the tower figures out which gates have room and tells the ground crews to make it happen. You never walk onto the tarmac and park a plane yourself. That is the whole shift from M2: you stop starting containers by hand and start declaring what you want, then let the control plane place and maintain it.

Keep this in mind: the value is not that Kubernetes is fancier than Compose. The value is that the airport keeps running when a gate breaks, a ground crew goes home, or twice as many flights show up, because something is always watching the difference between the plan and reality, and closing the gap.

Declarative, not imperative: the one idea behind everything​

There are two ways to get what you want from a system. You can give imperative orders: "start this container, now start that one, now open this port." That is what docker run and even docker compose up mostly are, steps you execute. Or you can declare the end state you want: "there should be three frontend Pods, using this image, answering on port 3000." Then you hand that to a system whose whole job is to make the world match your declaration and keep it matching.

Kubernetes is declarative to its core. You do not tell it how to get from zero frontends to three. You tell it there should be three, and a controller works out the steps, does them, and then keeps checking forever. If one dies, the count is now two, which does not match three, so it starts another. You did not ask for that repair. It happens because the declaration still says three and something is always comparing three against what is actually running.

The word to remember: reconciliation

The loop of "compare desired state to actual state, then act to close the gap, forever" is called reconciliation. It is the single most important idea in Kubernetes. Almost every part of the control plane is some flavor of a reconciliation loop. Once you see it, the rest of the system stops looking like magic and starts looking like the same pattern repeated.

Inside the control tower: the control-plane components​

The control plane is not one program. It is a handful of components, each with one job, talking to each other. Here is what actually runs in the tower.

  • API server is the tower radio. Every request, from you (kubectl) or from any other component, goes through the API server. Nothing touches the cluster's state except through it. It validates what you send, and it is the only thing that reads and writes the source of truth. If the API server is down, the airport does not stop flying (planes already in the air keep going), but no new instructions can be filed.
  • etcd is the records. A consistent key-value store that holds the entire desired and observed state of the cluster: every object you have declared, and the last known status of each. When people say "the cluster state lives in etcd," this is what they mean. Lose etcd without a backup and you have lost the plan.
  • scheduler is gate assignment. When a new Pod needs to run and has not been placed on a node yet, the scheduler picks the node. It weighs what the Pod asks for (CPU, memory, any placement rules) against what each node has free, and writes its choice back through the API server. It decides where; it does not start anything itself.
  • controller managers are the controllers watching the radar. This is where reconciliation lives. A bundle of controllers each watch one kind of object and drive actual state toward desired state: the node controller notices a node has gone silent, other controllers keep replica counts correct, and so on. Each one is the same loop (observe, compare, act) pointed at a different concern.

On the airfield: the node components​

A node is a machine (a VM or physical box) that actually runs your containers. In your lab it is a container pretending to be a machine (that is what KIND does), but the components are the real ones. Each node runs three things.

  • kubelet is the ground crew chief on that node. It watches the API server for Pods assigned to its node, tells the container runtime to start them, checks they are alive, and reports their status back up. The kubelet is the one component that bridges the tower's plan and the physical work. When you see a Pod go Running, it is the kubelet that made it so and the kubelet that said so.
  • kube-proxy is the taxiway signage. It programs the node's networking so that traffic aimed at a Service reaches a healthy Pod behind it. You do not use Services until M4, but kube-proxy is already running on every node, waiting for that job.
  • container runtime is the tugs and jet bridges that do the physical moving. Kubernetes does not run containers itself; it asks a runtime to. On your cluster that runtime is containerd, and Kubernetes talks to it through a standard interface called the CRI (Container Runtime Interface). This is why "Kubernetes uses Docker" was always a loose statement. It uses a runtime through the CRI, and containerd is the common one.
Why the CRI matters to you

Because Kubernetes talks to the runtime through the CRI and to storage and networking through similar standard interfaces (CSI and CNI), the pieces are swappable. Your lab cluster proves it: you disabled KIND's default network plugin and dropped in Calico instead, and Kubernetes did not care. Calico speaks the CNI, so it just works. That pluggability is why one set of Kubernetes skills carries across clouds and distributions.

What you actually send: objects, described as YAML​

You interact with the API server by sending it objects: a Pod, later a Deployment, a Service. Every object is described the same way, and you will write hundreds of these, so the shape is worth learning once. In the next lesson you meet the first and most fundamental object, the Pod, and write one for Fernwood Goods' frontend. For now, know that when you write:

apiVersion: v1
kind: Pod
metadata:
  name: frontend
spec:
  # ...what you want...

you are not writing a script that runs top to bottom. You are handing the API server a declaration: "an object of this kind, named this, that should look like this spec." The server stores it in etcd as desired state, and the controllers and kubelet take it from there. apiVersion, kind, metadata, spec: that four-part shape is the same for every object in Kubernetes. Learn it here and you can read any manifest you meet for the rest of the course and the rest of your career.

Why this is worth your attention​

On call, the difference between M2 and M3 is the difference between being paged to restart a container and sleeping through it because the cluster already replaced it. In a review, "where does this run and what keeps it running?" stops being "on box-07, and cron, we think" and becomes "it is a declared object in the cluster; the control plane keeps N copies alive and reschedules them when a node dies." The architecture you just learned is what makes that true: a control plane that holds the plan and never stops reconciling it, and nodes that do the work and report back.

In the lab you stand up exactly this, a real control plane and a real worker node, and then, in the next lesson, you put the first Fernwood Goods workload on it as a Pod.
