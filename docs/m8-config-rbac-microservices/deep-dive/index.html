Deep Dive — Troubleshooting drills: break it, diagnose it, fix it

The core lab showed config, RBAC, and NetworkPolicy working. This page is about the other 90% of the job: the day something is broken, the symptom is vague, and you have to find the cause from real kubectl output. Each drill below actually breaks something in a throwaway namespace, shows you the real symptom, walks the diagnostic steps a QA or platform engineer would use, then fixes it for real and confirms recovery.

The skill that ties all four together is a triage reflex: let the symptom point you at the stage. A Pod that will not start is a config problem; a "no" from the authorizer is an RBAC problem; a connection that times out is a network problem. Wrong stage, wasted hour.

Everything here runs in a throwaway drills namespace, so nothing you break can touch the hardened fernwood app you left running from the lab.

kubectl create namespace drills

Drill 1 — a Pod stuck because a ConfigMap key does not exist​

The most common "my Pod won't start" ticket that is not an image problem. Apply a Deployment whose container pulls one env var from a ConfigMap — but names a key (DB_HOSTNAME) that the ConfigMap does not have (it has DB_HOST):

kubectl apply -f labs/distributed-app/k8s/broken/drill-configmap-badkey.yaml
kubectl get pods -n drills -l app=drill-web

Expected output — the Pod is created but never runs; after a few seconds it settles on CreateContainerConfigError:

configmap/web-config created
deployment.apps/drill-web created
NAME                         READY   STATUS                       RESTARTS   AGE
drill-web-757d8dfcd5-kdfxg   0/1     CreateContainerConfigError   0          63s

The status names the category; the events name the cause. Read them:

kubectl describe pod -n drills -l app=drill-web | sed -n '/Events:/,$p' | grep -E 'Warning|Failed'

Expected output — the exact missing key, spelled out:

  Warning  Failed     6s    kubelet   Error: couldn't find key DB_HOSTNAME in ConfigMap drills/web-config

There is the whole diagnosis. The kubelet scheduled the Pod, pulled the image, then could not build the container's environment because DB_HOSTNAME is not a key in web-config. The fix is to reference the key that does exist. In a manifest you would correct the configMapKeyRef.key; here, patch it live to DB_HOST:

kubectl patch deployment drill-web -n drills --type=json \
  -p='[{"op":"replace","path":"/spec/template/spec/containers/0/env/0/valueFrom/configMapKeyRef/key","value":"DB_HOST"}]'
kubectl rollout status deploy/drill-web -n drills --timeout=60s
kubectl get pods -n drills -l app=drill-web

Expected output — a new Pod rolls out and reaches Running:

deployment.apps/drill-web patched
deployment "drill-web" successfully rolled out
NAME                        READY   STATUS    RESTARTS   AGE
drill-web-8d69fcf96-86jmv   1/1     Running   0          8s

The tell for this whole class of bug: CreateContainerConfigError is always a config reference problem — a missing ConfigMap, a missing Secret, or a missing key inside one. It is never an application error, because the application never started. Go straight to the events.

Drill 2 — a RoleBinding that silently grants nothing​

RBAC's most confusing failure: everything looks configured, and the permission still is not there. Apply a Service Account, a Role named pod-viewer that grants pod reads, and a RoleBinding — whose roleRef points at pod-reader-role, a Role that does not exist:

kubectl apply -f labs/distributed-app/k8s/broken/drill-rbac-broken.yaml
kubectl auth can-i list pods -n drills --as=system:serviceaccount:drills:drills-viewer

Expected output — the objects all create cleanly, yet the Service Account cannot list Pods. Notice the authorizer even tells you why:

serviceaccount/drills-viewer created
role.rbac.authorization.k8s.io/pod-viewer created
rolebinding.rbac.authorization.k8s.io/drills-viewer created
no - RBAC: role.rbac.authorization.k8s.io "pod-reader-role" not found

RBAC does not reject a binding that points at a missing Role — it accepts it and grants nothing, because a roleRef is resolved at check time, not at create time. When the message is less helpful than this one, the diagnostic is to compare the binding's roleRef against the Roles that actually exist:

kubectl get rolebinding drills-viewer -n drills -o jsonpath='roleRef -> {.roleRef.name}{"\n"}'
kubectl get role -n drills -o name

Expected output — the binding references pod-reader-role; the only Role present is pod-viewer. The names do not match:

roleRef -> pod-reader-role
role.rbac.authorization.k8s.io/pod-viewer

A roleRef is immutable — you cannot edit it in place — so the fix is to replace the binding with one that names the real Role:

kubectl delete rolebinding drills-viewer -n drills
kubectl create rolebinding drills-viewer -n drills --role=pod-viewer --serviceaccount=drills:drills-viewer
kubectl auth can-i list pods -n drills --as=system:serviceaccount:drills:drills-viewer

Expected output — with the binding pointing at the Role that exists, the permission appears:

rolebinding.rbac.authorization.k8s.io "drills-viewer" deleted
rolebinding.rbac.authorization.k8s.io/drills-viewer created
yes

The lesson: when a permission is missing but nothing errored, the three names have to line up — the binding's roleRef must name a real Role, and its subjects must name the real Service Account. A typo in either grants nothing, silently. kubectl auth can-i --as=... is the fastest way to test it without deploying anything.

Drill 3 — a NetworkPolicy that blocks the traffic it should allow​

The NetworkPolicy failure that wastes the most time, because the policy looks right. Apply a small drill-api service behind a default-deny, plus an allow-policy meant to let Pods labelled role=client reach it — but the policy's from-selector is typo'd as role=clientt:

kubectl apply -f labs/distributed-app/k8s/broken/drill-netpol-broken.yaml
kubectl rollout status deploy/drill-api -n drills --timeout=60s

Expected output:

deployment.apps/drill-api created
service/drill-api created
networkpolicy.networking.k8s.io/drills-default-deny created
networkpolicy.networking.k8s.io/allow-client-to-drill-api created
deployment "drill-api" successfully rolled out

Now a legitimate client — labelled exactly role=client, as intended — tries to reach the service and hangs until it times out:

kubectl run drill-client --image=busybox:1.36 --labels='role=client' --restart=Never -n drills --command -- \
  sh -c 'wget -qO- --timeout=5 http://drill-api:8080/ || echo "BLOCKED exit=$?"'
sleep 10
kubectl logs drill-client -n drills
kubectl delete pod drill-client -n drills

Expected output — the connection is silently dropped, not refused. A timeout, not a Connection refused, is the signature of a NetworkPolicy drop:

wget: download timed out
BLOCKED exit=1

The service is up and the client's label is correct, so the suspect is the policy's selector. Read what the policy actually allows, and compare it against the client's real label:

kubectl get netpol allow-client-to-drill-api -n drills -o jsonpath='allows from role={.spec.ingress[0].from[0].podSelector.matchLabels.role}{"\n"}'

Expected output — the policy allows role=clientt; the client is role=client. One stray letter, and the selector matches nothing:

allows from role=clientt

That is the entire bug. NetworkPolicy selectors are literal label matches — a selector that matches no Pod allows no traffic, and the default-deny then drops everything. Fix the selector:

kubectl patch netpol allow-client-to-drill-api -n drills --type=json \
  -p='[{"op":"replace","path":"/spec/ingress/0/from/0/podSelector/matchLabels/role","value":"client"}]'

Confirm the legitimate client now gets through — and, to prove the policy is still enforcing and did not just fall open, that a Pod without the label is still blocked:

kubectl run drill-client --image=busybox:1.36 --labels='role=client' --restart=Never -n drills --command -- \
  sh -c 'wget -qO- --timeout=5 http://drill-api:8080/ || echo "STILL BLOCKED exit=$?"'
kubectl run drill-nolabel --image=busybox:1.36 --restart=Never -n drills --command -- \
  sh -c 'wget -qO- --timeout=5 http://drill-api:8080/ || echo "BLOCKED exit=$?"'
sleep 15
echo "role=client :"; kubectl logs drill-client  -n drills
echo "no label    :"; kubectl logs drill-nolabel -n drills
kubectl delete pod drill-client drill-nolabel -n drills

Expected output — the correctly-labelled client reaches the service (drill-api ok); the unlabelled Pod still times out. The fix opened exactly one path and no more:

role=client :
drill-api ok
no label    :
wget: download timed out
BLOCKED exit=1

The discipline: a NetworkPolicy problem is a label problem. When traffic that should flow does not, kubectl get netpol -o yaml the policy and read its selectors against the actual labels on the Pods (kubectl get pod --show-labels). The mismatch is almost always a typo or a label that was never applied.

Drill 4 — the Secret version of Drill 1​

Worth seeing on its own, because people mentally file "the Secret exists" as "the Secret is fine" and skip straight past it. Apply a Deployment that pulls its password from a Secret via secretKeyRef — asking for key DB_PASS when the Secret stores DB_PASSWORD:

kubectl apply -f labs/distributed-app/k8s/broken/drill-secret-badkey.yaml
kubectl get pod -n drills -l app=drill-secret-web -o jsonpath='{.items[0].status.containerStatuses[0].state.waiting.reason}: {.items[0].status.containerStatuses[0].state.waiting.message}{"\n"}'

Expected output — the same CreateContainerConfigError category as Drill 1, this time naming the Secret and the missing key:

CreateContainerConfigError: couldn't find key DB_PASS in Secret drills/web-secret

Same failure mode, same fix — reference the key that exists:

kubectl patch deployment drill-secret-web -n drills --type=json \
  -p='[{"op":"replace","path":"/spec/template/spec/containers/0/env/0/valueFrom/secretKeyRef/key","value":"DB_PASSWORD"}]'
kubectl rollout status deploy/drill-secret-web -n drills --timeout=60s
kubectl get pods -n drills -l app=drill-secret-web

Expected output — it rolls out to Running:

deployment.apps/drill-secret-web patched
deployment "drill-secret-web" successfully rolled out
NAME                                READY   STATUS    RESTARTS   AGE
drill-secret-web-77676c8df9-pq888   1/1     Running   0          8s

ConfigMap or Secret, the rule is one: CreateContainerConfigError means a reference is wrong — a missing object or, far more often, a mistyped key. The container never ran, so it is never the application's fault.

The diagnosis at a glance​

SymptomFirst commandRoot causeFix
Pod CreateContainerConfigErrorkubectl describe pod → EventsConfigMap/Secret key (or object) referenced but absentCorrect the key / create the object
auth can-i says no, nothing erroredkubectl auth can-i --as=... then check roleRefBinding points at a missing Role, or wrong subjectRecreate the binding with the real Role/SA (roleRef is immutable)
Connection times out (exit 28)kubectl get netpol -o yaml vs get pod --show-labelsPolicy selector does not match the real Pod labelsCorrect the selector to the actual label
Connection refused (fast)check the Service / target portNot a policy — nothing is listening thereFix the Service/targetPort or the app

That last row is the one worth internalizing: timeout means a policy dropped it; refused means the packet arrived and nothing was listening. They point at completely different layers, and telling them apart from the failure mode alone saves you the most time of anything in this module.

Where you will use this​

  • A Pod is stuck CreateContainerConfigError in CI or a fresh namespace. Do not read the app logs — the app never started. describe pod and read the event; it names the exact ConfigMap/Secret key that is wrong. Usually a typo, occasionally an object that was never applied.
  • Someone says "I gave the Service Account access and it still gets Forbidden." Run kubectl auth can-i --as=system:serviceaccount:<ns>:<name> and check the binding's roleRef and subjects names against reality. A dangling roleRef grants nothing and never errors.
  • "The app can't reach the database after we added NetworkPolicy." A timeout (not a refusal) points at the policy. Compare its selectors to the actual Pod labels — the mismatch is the bug, and it is almost always a label typo or a namespace selector that does not match the real namespace label.

Teardown​

Every drill lived in the throwaway drills namespace. Deleting it removes all four Deployments, their ConfigMaps/Secrets, the Service Account, Role, RoleBinding, and NetworkPolicies in one command — and touches nothing in fernwood:

kubectl delete namespace drills

Expected output:

namespace "drills" deleted

The hardened fernwood app from the lab — externalized config, scoped RBAC, default-deny NetworkPolicy, working Ingress — is untouched and remains the final state of the course.
