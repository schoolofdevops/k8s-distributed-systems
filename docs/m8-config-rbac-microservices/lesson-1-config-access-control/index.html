Configuration & Access Control

▶ M8 — Configuration & Access ControlOpen fullscreen ↗

By now Fernwood Goods runs fully on the cluster. A frontend Deployment, a backend Deployment, a Postgres StatefulSet, Services wiring them together, and an Envoy front door that lets the outside world in. It works. But two things are still wide open, and both would fail a production review.

First, the app's configuration sits in the wrong places. Back in M6, the backend's database host was typed straight into the Deployment manifest as a plain value. The database password sits in plain sight in the StatefulSet. To point the same image at a different database, you would edit YAML and redeploy. That is config welded to the workload, and it is the first thing an auditor flags.

Second, the cluster trusts everyone. Any Pod can open a connection to any other Pod. The frontend could talk straight to Postgres. A debug Pod could reach the database, and nothing stops it. And anyone holding a kubeconfig (the file that holds your cluster login) can do anything: read every Secret, delete any Deployment, in any namespace. A flat, fully-trusting cluster is fine on your laptop. It gets dangerous the moment more than one team shares it.

This lesson closes both gaps. You will pull configuration out of the workload into ConfigMaps and Secrets. Then you will learn the three checks Kubernetes uses to decide who may do what: authentication, authorization, and admission control. You will meet the RBAC model that spells out permissions, and NetworkPolicy, which finally limits which Pods may talk to which.

The analogy: a secured research campus​

Imagine a large research campus. Several buildings, hundreds of staff, and some of the work is highly sensitive. Nobody memorises how the whole campus runs. Two very different things are going on here, and it helps to keep them apart from the start.

The first is configuration. Every workstation has a printed standing-orders sheet taped beside it: which server to log into, which printer to use, which project code to bill. The truly sensitive values, like door codes and safe combinations, are not on that sheet. They sit in a sealed envelope in a locked drawer. Here is the important point: the worker and the instructions are separate. A new hire sits down, reads the sheet, and gets to work. Move them to another project and you swap the sheet, not the person.

The second is access control, and the campus runs it as three checks. A guard at the gate checks who you are against your ID card. That is authentication. Your badge's clearance level then decides which doors actually open for you. That is authorization. And a mailroom inspection looks at anything you try to bring in, and can reject it or stamp a correction on it before it goes further. That is admission control. Three separate checks, in order: who are you, what are you allowed to do, and is what you are asking for acceptable.

Two more campus facts matter. Automated equipment, say a delivery robot or a sensor rig, also needs a badge. It gets a machine credential, not a person's ID. And inside the buildings, not every corridor connects to every room. Sealed doors keep the isolation wing reachable only from the wards that should reach it. Keep this whole picture in mind. The rest of the lesson is just the Kubernetes name for each part of it.

Moving configuration out: ConfigMaps and Secrets​

Back in M6 you wired the backend to Postgres by typing the database's DNS name straight into the Deployment:

env:
  - name: DB_HOST
    value: "db-0.db.fernwood.svc.cluster.local"

That worked, and for one value it was fine. But think about what it means. The address of a backing service (a thing your app depends on, like the database) is now baked into the workload definition. The backend image already reads five settings from its environment: DB_HOST, DB_PORT, DB_NAME, DB_USER, DB_PASSWORD. If every one of those is a plain value in the manifest, then the manifest belongs to one environment only. Staging has a different database host. Production has a different password. You end up with three near-identical manifests that differ only in a few strings, and every difference is a chance to ship the wrong one.

The rule underneath this is worth stating plainly. Configuration that changes between environments does not belong in the image, and it does not belong hardcoded in the workload either. The image is built once and should run unchanged everywhere. What changes per environment is data the workload reads at startup. Kubernetes gives you two objects to hold that data.

A ConfigMap holds non-secret configuration as key/value pairs. This is the standing-orders sheet: the database host, port, name, and user, which are settings you would not mind someone reading. A Secret holds the values you would never print on a sheet, here the database password. It is the sealed envelope.

Now here is the honest truth about Secrets, and it catches people. A Secret is not encrypted by default. Its values are base64-encoded, which is encoding, not encryption. Anyone can decode it in one command. So what does a Secret actually buy you over a ConfigMap? Two real things. It is a separate object with its own RBAC, so you can let a team read the ConfigMap while denying them the Secret. And the platform handles it more carefully: kept out of most logs, mountable as an in-memory file, and encryptable at rest if the cluster turns that on. The separation is the point. Secrets and non-secrets get different permissions because they carry different risk.

The workload pulls both in with envFrom, which injects every key in the object as an environment variable of the same name. Because the backend already reads DB_HOST, DB_NAME and the rest from its environment, the keys line up and nothing in the application code changes. The Deployment's env block that used to hold a plain DB_HOST value becomes two references:

envFrom:
  - configMapRef:
      name: backend-config
  - secretRef:
      name: backend-secret

That is the whole move. The image is untouched. The behaviour is identical, and the app still reports db: connected. But the configuration now lives in objects you can review, diff, and permission separately from the workload, and the same image will run against any database by swapping the ConfigMap and Secret. When you need a single value in one specific place rather than the whole set, valueFrom pulls one key (configMapKeyRef or secretKeyRef) instead of the wholesale envFrom. You will use both.

Config drift is a real failure mode

When a Pod reads config through envFrom, it reads it once, at container start. Editing the ConfigMap later does not change a running Pod. You must roll the Deployment for the new values to take effect. That is not a bug. It is why a config change is a deploy, not a silent live edit. It also means a Pod that still references a key that no longer exists will fail to start at all, which is one of the drills in this module's deep dive.

Three gates: authentication, authorization, admission control​

Now to access control. Every request to the Kubernetes API server (every kubectl command, and every Pod using its token) passes through three stages, in a fixed order, before it is allowed to change anything. These are the guard, the badge reader, and the mailroom from the analogy, and keeping them apart is what lets you debug a "permission" problem correctly.

Authentication (authN) answers who are you? The API server checks the caller's identity from the credential they present: a client certificate, a bearer token, or, for a Pod, its Service Account token. Kubernetes has no built-in "user" object for humans. It trusts an outside identity source and reads the identity off the credential. If the credential is invalid, the request stops here with 401. Notice what authN does not do: it does not decide what you can do. The guard confirms your ID. It does not open any doors.

Authorization (authZ) answers are you allowed to do this? Now that the API server knows who you are, it checks whether that identity may perform this specific action (the verb) on this specific resource in this specific namespace: delete pods in fernwood, or get secrets in kube-system. In this course, and in almost every real cluster, the system doing that checking is RBAC. If no rule permits the action, the request stops here with 403 Forbidden. This is the badge reader: identity already known, now the question is clearance.

Admission control answers is what you are asking for acceptable, and should it be adjusted? Even a fully-authorized request can be rejected or changed at this last gate by admission controllers, the mailroom inspection. Mutating admission can change the request (inject a sidecar, set a default, add a label). Validating admission can reject it against a policy ("every Pod must set resource limits", "no privileged containers"). This is how a platform team enforces standards that RBAC cannot express. RBAC says who may act. Admission says what shape the result must have. Only after all three gates does the change land in etcd.

Here is why you keep these apart. When something is "denied," the stage tells you the cause. A 401 is an identity problem (bad or missing credential). A 403 is an RBAC problem (identity fine, permission missing). A rejection with a policy message is admission (permission fine, the object breaks a rule). Three different fixes.

Service Accounts: identity for Pods​

Humans authenticate with certificates or tokens from an outside identity provider. But a Pod also makes API calls: a controller reconciling objects, the ingress controller reading Ingress rules, your own app listing Pods. What identity does it use? That is the machine credential from the analogy: a Service Account.

A Service Account is an identity for workloads, native to Kubernetes and tied to one namespace. Every Pod runs as one. If you do not name it, the Pod uses the default Service Account in its namespace. Kubernetes mounts a token for that Service Account into the Pod, and when the Pod calls the API server, that token is its credential. The API server authenticates the call as system:serviceaccount:<namespace>:<name>. This is the same as a person's ID badge, except it is issued to a process, not a person, and it is confined to one namespace.

The security lesson here is the same as least privilege everywhere. The default Service Account should be able to do almost nothing, and any Pod that genuinely needs API access should run as a purpose-made Service Account granted exactly the permissions it needs, and no more. In the lab you create a Service Account that can only read Pods in fernwood, and prove it can do that and nothing else.

RBAC: Roles, ClusterRoles, and bindings​

Authorization needs a language for "who may do what, where." That language is Role-Based Access Control, and it is built from just two types of object: ones that define a set of permissions, and ones that grant that set to a subject. A subject is a user, a group, or a Service Account.

The permission-defining objects come in a namespaced form and a cluster-wide form, and this split maps straight onto the namespaces you learned in M4:

  • A Role is namespaced. Its rules apply only inside one namespace. "Read Pods in fernwood" is a Role. This is the wing-specific badge. It opens doors in one wing only.
  • A ClusterRole is cluster-scoped. The same type of rules, but they apply cluster-wide, and a ClusterRole can also grant access to cluster-scoped resources (Nodes, PersistentVolumes, and namespaces themselves) that a Role cannot even name. This is the facility-wide badge.

A Role or ClusterRole on its own grants nothing. It is a definition sitting on a shelf. The binding attaches it to a subject:

  • A RoleBinding grants a Role (or a ClusterRole) within one namespace. It says "this subject has these permissions, here."
  • A ClusterRoleBinding grants a ClusterRole across the whole cluster.

One combination is worth calling out because it is genuinely useful: a RoleBinding can reference a ClusterRole. That lets the platform team define a reusable permission set once as a ClusterRole (say, "read-only across common resources") and then grant it namespace by namespace with RoleBindings. The permission is scoped to wherever the binding lives, not cluster-wide. Define once, grant narrowly.

The discipline that makes RBAC safe is least privilege. Grant the narrowest actions (get, list) on the fewest resources (pods) in the smallest scope (one namespace) that does the job. It is far easier to add a permission when something genuinely needs it than to discover, during an incident, that a Service Account could delete production because someone bound cluster-admin to be safe. In the lab you will feel this directly: a Service Account that can list Pods but gets a hard Forbidden the moment it tries to delete one.

NetworkPolicy: closing the flat network​

The last gap is the network itself. Go all the way back to M1. Docker gave every container on a bridge a flat network where everyone could reach everyone. That default carried into Kubernetes. By default, every Pod can open a connection to every other Pod, across namespaces, with nothing in the way. The frontend could connect straight to Postgres. A debug Pod someone left running could reach the database. Nothing is stopping it, because nothing has been told to.

A NetworkPolicy changes the default from open to closed, then reopens only the paths you name. It is the sealed internal doors of the campus. The isolation wing is reachable only from the wards that should reach it, and every other corridor to it is walled off.

Two facts decide whether a NetworkPolicy does anything at all. First, policies are additive, and they default to deny once they select a Pod. The moment any policy selects a Pod for a direction (ingress, which is traffic coming in, or egress, which is traffic going out), that Pod denies all traffic in that direction except what some policy explicitly allows. A Pod that no policy selects stays wide open. So the standard pattern is a default-deny policy that selects every Pod and permits nothing, followed by narrow allow-policies that add back exactly the paths you want.

Second, and this is why the course's cluster is built the way it is, NetworkPolicy is enforced by the CNI plugin, not by Kubernetes core. (The CNI is the network plugin that wires up Pod networking.) The API server will happily accept a NetworkPolicy object under a CNI that ignores it, and you will believe you are protected while every packet still flows. This course's KIND cluster runs Calico precisely because the default kindnet CNI does not enforce NetworkPolicy. That decision, made back in M3, is what makes this lesson real instead of theatre.

For Fernwood the intended shape is a simple chain plus the ingress exception:

Default-deny everything, then allow: the frontend reachable from Envoy on 3000; the backend reachable from the frontend and Envoy on 8080; the database reachable from the backend and nothing else on 5432. Every other path is dropped: a stray Pod dialling the backend, or anyone at all dialling Postgres.

That ingress exception for Envoy is not optional. The whole front door you built in M7 depends on Envoy Pods in the projectcontour namespace reaching the frontend and backend. A default-deny that forgets to allow projectcontour would silently break Ingress routing. The app would look up and pass its health checks while every external request returned a 503. This is the most common way a well-meaning NetworkPolicy takes down a working app, and the lab makes you prove Ingress still routes after the policy is applied.

Where this leaves the app​

At the end of this module's lab, Fernwood is hardened without a single change to its application code. Its configuration lives in a ConfigMap and a Secret you can permission independently. A scoped Service Account proves the RBAC boundary works. And a default-deny NetworkPolicy, with named exceptions, means the only Pod that can reach Postgres is the backend, while the M7 front door keeps serving traffic. That is the shape of a service that could pass a review.

The next lesson steps back from the mechanics. You have spent eight modules building one small system into a set of independent, separately-deployed, network-isolated services. Lesson 2 names what you actually built, which is the microservices patterns hiding in plain sight across the whole course, and it is honest about what that architecture costs.
