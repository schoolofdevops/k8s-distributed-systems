Lab — Externalizing Config, Scoping Access, and Locking Down the Network

You will harden the Fernwood Goods app without touching a line of its code. First you move the backend's configuration out of the manifest into a ConfigMap and a Secret and prove the app behaves identically. Then you create a Service Account with one narrow permission and prove the boundary from both sides. Finally you apply a NetworkPolicy that turns the flat, open network into a default-closed one — and prove both that the M7 Ingress still routes and that a Pod off the allow-list is genuinely blocked.

Nothing here changes the app's Deployment images, the StatefulSet, or the Services. You are adding config objects, RBAC objects, and network rules in front of what M7 left running.

Before you start​

Point kubectl at the shared distsys cluster and confirm the app from M7 is up:

kubectl config use-context kind-distsys
kubectl get deploy,statefulset -n fernwood

Expected output — the app is running (your ages and replica counts will differ):

NAME                       READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/backend    6/6     6            6           3h
deployment.apps/frontend   3/3     3            3           3h

NAME                    READY   AGE
statefulset.apps/db     1/1     2h

If that app is not there, catch up with M6 and M7 first — this module assumes both.

Step 1 — Externalize the backend's configuration​

The backend image reads five settings from its environment: DB_HOST, DB_PORT, DB_NAME, DB_USER, and DB_PASSWORD. Until now only DB_HOST was set, as a literal in the Deployment (M6), and the rest fell back to defaults. You will move all five out of the workload: the four non-secret settings into a ConfigMap, the password into a Secret.

Apply both objects:

kubectl apply -f labs/distributed-app/k8s/backend-config.yaml
kubectl get configmap backend-config -n fernwood
kubectl get secret backend-secret -n fernwood

Expected output — a ConfigMap with four keys and a Secret with one:

configmap/backend-config created
secret/backend-secret created
NAME             DATA   AGE
backend-config   4      1s
NAME             TYPE     DATA   AGE
backend-secret   Opaque   1      1s

Now update the backend Deployment to consume both. The env: block that held a literal DB_HOST is replaced with an envFrom: that pulls in every key from the ConfigMap and the Secret as environment variables of the same name:

kubectl apply -f labs/distributed-app/k8s/backend-deployment.yaml
kubectl rollout status deploy/backend -n fernwood --timeout=120s

Expected output — a clean rolling update onto the externalized config:

deployment.apps/backend configured
Waiting for deployment "backend" rollout to finish: 1 old replicas are pending termination...
deployment "backend" successfully rolled out

Confirm the config is now sourced from the two objects, not from inline values:

kubectl get deploy backend -n fernwood -o jsonpath='{.spec.template.spec.containers[0].envFrom}'; echo

Expected output — both references, no inline DB_HOST anywhere:

[{"configMapRef":{"name":"backend-config"}},{"secretRef":{"name":"backend-secret"}}]

The proof that matters: the app behaves identically. Config moved, behavior unchanged. Hit the backend through a throwaway Pod and confirm it still reports the database as connected. Label it tier=frontend so it reads as legitimate traffic regardless of whether the NetworkPolicy from Step 4 is already in place on this cluster — testing what a stranger Pod can't reach is Step 4's job, not this one's:

kubectl run cfg-check --image=curlimages/curl:8.11.1 --restart=Never --rm -i --quiet -n fernwood \
  --labels="app=fernwood,tier=frontend" -- -s http://backend:8080/api/health; echo

Expected output — db: connected, served by one of the freshly-rolled backend Pods (your hostname will differ):

{"db":"connected","hostname":"backend-5f987968ff-9g6xj","service":"backend","status":"ok"}

Step 2 — See what a Secret actually protects​

A Secret is not encrypted — its values are base64-encoded, which anyone can reverse. Prove it to yourself so you never over-trust one:

kubectl get secret backend-secret -n fernwood -o jsonpath='{.data.DB_PASSWORD}'; echo
kubectl get secret backend-secret -n fernwood -o jsonpath='{.data.DB_PASSWORD}' | base64 -d; echo

Expected output — the stored value, then the same value trivially decoded:

ZmVybndvb2Q=
fernwood

So the win of a Secret over a ConfigMap is not secrecy-by-encryption — it is that the Secret is a separate object with its own RBAC. You can grant a team read access to backend-config while denying them backend-secret. That separation is exactly what the next step's RBAC makes real.

Step 3 — A narrowly-scoped Service Account, proven both ways​

Create a Service Account that can do exactly one thing in fernwood: read Pods. Nothing else — no write, no other resource, no other namespace. The manifest is a ServiceAccount, a Role granting get/list on pods, and a RoleBinding joining them.

kubectl apply -f labs/distributed-app/k8s/rbac-pod-reader.yaml

Expected output:

serviceaccount/pod-reader created
role.rbac.authorization.k8s.io/pod-reader created
rolebinding.rbac.authorization.k8s.io/pod-reader created

Now prove the boundary. kubectl auth can-i --as=<subject> asks the API server's authorizer whether a subject may perform an action — the same RBAC check a real request goes through. First, what it can do:

SA=system:serviceaccount:fernwood:pod-reader
kubectl auth can-i list pods -n fernwood --as=$SA
kubectl auth can-i get  pods -n fernwood --as=$SA

Expected output — both permitted:

yes
yes

Then what it cannot do — delete a Pod, read a Secret, or reach into another namespace:

kubectl auth can-i delete pods   -n fernwood    --as=$SA
kubectl auth can-i get    secrets -n fernwood    --as=$SA
kubectl auth can-i list   pods    -n kube-system --as=$SA

Expected output — every one denied. The last is denied because a Role is namespaced: read access in fernwood grants nothing in kube-system.

no
no
no

A boundary you only asserted is not proven — so trigger the real denial. Run an allowed action, then a forbidden one, as the Service Account:

kubectl get pods -n fernwood --as=$SA -o name | head -3
kubectl delete pod db-0 -n fernwood --as=$SA

Expected output — the list succeeds; the delete is rejected by the API server with a real Forbidden (and db-0 is untouched):

pod/backend-5f987968ff-9g6xj
pod/backend-5f987968ff-vrzvt
pod/backend-5f987968ff-z7qr7
Error from server (Forbidden): pods "db-0" is forbidden: User "system:serviceaccount:fernwood:pod-reader" cannot delete resource "pods" in API group "" in the namespace "fernwood"

That Forbidden is authorization working exactly as designed: identity known, permission absent, action stopped.

Step 4 — Lock down the network with NetworkPolicy​

Until now every Pod in fernwood could reach every other Pod, and any Pod anywhere could reach Postgres. You will change the default from open to closed, then reopen only the paths the app needs. The manifest has four policies: a default-deny on all ingress, then allow rules for frontend (from Envoy), backend (from the frontend and Envoy), and db (from the backend only).

The Envoy allow rule is not optional

M7's Ingress works because Envoy Pods in the projectcontour namespace reach the frontend and backend. A default-deny that forgets to allow projectcontour would silently break Ingress — the app would look healthy while every external request failed. The manifest allows projectcontour on purpose; you will verify Ingress still routes right after applying it.

kubectl apply -f labs/distributed-app/k8s/networkpolicy.yaml
kubectl get networkpolicy -n fernwood

Expected output — four policies, the default-deny selecting every Pod (<none> = empty selector):

networkpolicy.networking.k8s.io/default-deny-ingress created
networkpolicy.networking.k8s.io/allow-frontend-from-envoy created
networkpolicy.networking.k8s.io/allow-backend-from-frontend-and-envoy created
networkpolicy.networking.k8s.io/allow-db-from-backend created
NAME                                    POD-SELECTOR                 AGE
allow-backend-from-frontend-and-envoy   app=fernwood,tier=backend    1s
allow-db-from-backend                   app=fernwood,tier=db         1s
allow-frontend-from-envoy               app=fernwood,tier=frontend   1s
default-deny-ingress                    <none>                       1s

First, confirm the policy did not break the running app. All Pods should stay Ready — Calico does not block the kubelet's health probes — and the M7 Ingress should still route. Test Ingress with in-cluster Pods that carry the right Host: header to Envoy:

kubectl get pods -n fernwood -l app=fernwood --no-headers | awk '{print $1, $2, $3}' | grep -E 'frontend|backend|db-0'
kubectl run np-ingress --image=curlimages/curl:8.11.1 --restart=Never --rm -i --quiet -n fernwood -- \
  -s -o /dev/null -w 'fernwood.local -> %{http_code}\n' -H 'Host: fernwood.local' http://envoy.projectcontour.svc.cluster.local/
kubectl run np-ingress2 --image=curlimages/curl:8.11.1 --restart=Never --rm -i --quiet -n fernwood -- \
  -s -o /dev/null -w 'api.fernwood.local -> %{http_code}\n' -H 'Host: api.fernwood.local' http://envoy.projectcontour.svc.cluster.local/api/health

Expected output — Pods still Ready, both Ingress hostnames still 200. The front door survived the lockdown:

frontend-68cf68cbbc-dzbz4 1/1 Running
backend-5f987968ff-9g6xj 1/1 Running
db-0 1/1 Running
fernwood.local -> 200
api.fernwood.local -> 200

Now prove the allowed internal path still works. A Pod labelled tier=frontend is permitted to reach the backend on 8080:

kubectl run np-asfrontend --image=curlimages/curl:8.11.1 --labels='app=fernwood,tier=frontend' \
  --restart=Never --rm -i --quiet -n fernwood -- \
  -s -o /dev/null -w 'frontend->backend:8080 -> http=%{http_code}\n' --max-time 5 http://backend:8080/api/health

Expected output — allowed, 200:

frontend->backend:8080 -> http=200

Finally, prove the policy is actually enforcing — that a Pod off the allow-list is blocked, not merely un-mentioned. Run a throwaway Pod with no tier label and point it at the backend and the database. Its packets are dropped, so the connection times out (curl exit code 28) rather than being refused:

kubectl run np-intruder --image=curlimages/curl:8.11.1 --restart=Never -n fernwood --command -- \
  sh -c 'curl -s -o /dev/null -w "intruder->backend:8080 http=%{http_code} exit=%{exitcode}\n" --max-time 5 http://backend:8080/api/health'
kubectl run np-intruder-db --image=curlimages/curl:8.11.1 --restart=Never -n fernwood --command -- \
  sh -c 'curl -s -o /dev/null -w "intruder->db:5432 exit=%{exitcode}\n" --connect-timeout 5 --max-time 6 http://db:5432/'
sleep 12
kubectl logs np-intruder -n fernwood
kubectl logs np-intruder-db -n fernwood
kubectl delete pod np-intruder np-intruder-db -n fernwood

Expected output — both blocked. http=000 with exit=28 is the signature of a silently dropped packet: no response, timed out. The database is reachable by the backend and by nobody else:

intruder->backend:8080 http=000 exit=28
intruder->db:5432 exit=28
pod "np-intruder" deleted
pod "np-intruder-db" deleted

Allowed traffic flows, disallowed traffic is dropped, and the front door still routes. The network is now default-closed with named exceptions — the shape you want in production.

What you built​

  • Externalized configuration — the backend's DB settings in a ConfigMap, its password in a Secret, consumed with envFrom. Same image, same behavior (db: connected), config now reviewable and permissioned on its own.
  • A scoped Service Account — pod-reader can get/list Pods in fernwood and nothing else, proven with auth can-i and a real Forbidden on a delete attempt.
  • A default-deny NetworkPolicy with named allows — frontend from Envoy, backend from frontend and Envoy, db from backend only. Legitimate traffic and M7 Ingress still work; a Pod off the allow-list is dropped.

Teardown​

Leave everything running. This is the final state of the course — a hardened, fully-working Fernwood on the cluster. Do not delete the cluster, the app, the ingress layer, or any of the objects you created in this lab; they are the course's end state. The only things to remove are any throwaway probe Pods, and kubectl run --rm already deleted those for you.

If you did the deep dive, its drills live in a separate drills namespace with its own teardown; removing that namespace does not touch anything here.

To confirm the end state is intact:

kubectl get configmap,secret,serviceaccount,networkpolicy -n fernwood | grep -E 'backend-config|backend-secret|pod-reader|allow-|default-deny'

Expected output — the config, RBAC, and network objects all present (columns trimmed for width):

configmap/backend-config     4        ...
secret/backend-secret        Opaque   1     ...
serviceaccount/pod-reader    ...
networkpolicy.networking.k8s.io/allow-backend-from-frontend-and-envoy   app=fernwood,tier=backend    ...
networkpolicy.networking.k8s.io/allow-db-from-backend                   app=fernwood,tier=db         ...
networkpolicy.networking.k8s.io/allow-frontend-from-envoy               app=fernwood,tier=frontend   ...
networkpolicy.networking.k8s.io/default-deny-ingress                    <none>                       ...
