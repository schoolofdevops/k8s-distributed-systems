Exposing Services with Ingress & the Gateway API (Envoy)

▶ M7 — Exposing Services with Ingress & the Gateway API (Envoy)Open fullscreen ↗

By now the Fernwood Goods app runs entirely on the cluster: a frontend Deployment, a backend Deployment, and a Postgres StatefulSet, all wired together by Services. Inside the cluster everything can reach everything else by name. But step outside the cluster and the app is unreachable. A Service gives you a stable address for callers already inside the cluster. It does nothing to let a browser on someone's laptop reach the storefront.

In M4 you papered over this with a NodePort — you gave the frontend Service a high port on every node and hit it directly. That works for a demo and falls apart in production. NodePort gives you one numeric port per Service (30080, 31711, …), no hostnames, no paths, no TLS, and no single place to apply a rule to all incoming traffic. Real traffic arrives as https://shop.example.com/ and https://api.example.com/orders, on port 443, sorted by hostname and path. Nothing you have built so far can do that sorting. This module adds the layer that can: an Ingress, implemented by Envoy.

The analogy: the reception desk of an office building​

Think about a large office building with many companies inside it. Every company has its own internal phone switchboard — that is the Service you built in M4. Dial the switchboard and you reach whoever is on duty in that company, and you neither know nor care which desk they sit at. That part is solved.

But a visitor arriving from the street does not walk straight to a switchboard. They come through one main entrance into a single lobby, and they meet a receptionist. The receptionist reads who the visitor is there to see — "I'm here for Fernwood Sales" or "deliveries go to the loading dock" — and directs them to the right floor and the right internal number. One street address, one lobby, one desk reading the request and routing it onward.

That receptionist is the Ingress. The building's single street entrance is the one entry point all outside traffic comes through. The receptionist reads each arriving HTTP request — its hostname and its URL path — and forwards it to the correct Service, which then does its own internal switchboard job. You are not replacing the switchboards. You are putting a receptionist in front of them so the outside world has one door and one set of directions instead of a wall of numbered side entrances.

Service versus Ingress: two different jobs​

It is easy to blur these together because both "route traffic". They operate at different layers and solve different problems.

A Service works at layer 4 — TCP/UDP. It load-balances a connection across a set of Pods by IP and port. It does not read the HTTP request. It cannot tell GET /products from GET /health, and it has no idea what hostname the client asked for, because that information lives up in the HTTP request it never inspects.

An Ingress works at layer 7 — HTTP. It reads the request line and headers. That is what lets it route on hostname (shop.fernwood.local versus api.fernwood.local) and on path (/ versus /api), terminate TLS, and present many Services behind one external address. It sits in front of Services and hands each request to one of them.

The Ingress does not replace the Service — it feeds it. The request still lands on a Service, which still does the L4 load-balancing across healthy Pods you learned in M4. Ingress just adds the L7 sorting on top.

An Ingress object is only a rule set​

Here is the part that trips people up. When you kubectl apply an Ingress, nothing routes yet. An Ingress object is a rule set and nothing more — a piece of paper that says "requests for this hostname go to that Service". It has no process behind it, no listening socket, no traffic.

Something has to read those rules and actually implement them: open a real port, accept connections, read each request, and forward it. That something is the Ingress controller. The controller's whole job is to watch Ingress objects and program a real proxy to match. Without a controller running, an Ingress object is inert — you can create as many as you like and no packet will move.

Back to the building: the Ingress object is the printed directory posted at reception — "Fernwood Sales, 4th floor". The controller is the receptionist who actually reads that directory and walks visitors to the lift. A directory with no one at the desk routes nobody.

Kubernetes ships the Ingress object type in the core API, but deliberately ships no controller. You choose and install one. The common teaching default is the NGINX ingress controller. Fernwood's platform team runs Envoy instead — a high-performance L7 proxy that is the data plane behind most modern service meshes and API gateways. Raw Envoy on its own does not understand Kubernetes Ingress objects, so you run an Envoy-based controller that does the watching-and-programming for it. In this course that controller is Contour, a CNCF project that uses Envoy as its data plane and — usefully — speaks both the classic Ingress API and the newer Gateway API from a single install.

Two boxes, two jobs: Contour is the brain that reads Kubernetes objects and computes config; Envoy is the muscle that holds the open port and moves the bytes. Every Ingress and route you write becomes Envoy configuration that Contour pushes down.

How outside traffic actually reaches Envoy​

The controller programs Envoy, but something still has to get a packet from the outside world to Envoy in the first place. The Envoy Pods are exposed by a Service of their own — and this is where the layers stack up neatly. On a cloud provider that Service is type LoadBalancer: the cloud provisions a real external load balancer with a public IP, and every request to that IP lands on Envoy. That is the normal production entry point — one address for the whole cluster, in front of the one Envoy, in front of every app Service.

Your KIND cluster has no cloud behind it, so that LoadBalancer Service never gets an external IP — it sits <pending> forever, which is expected, not a fault. To reach Envoy from your laptop you use kubectl port-forward against the Envoy Service, which opens a local port straight to it. The routing you are testing is identical either way; only the last hop from your machine to Envoy differs. Keep the mental picture straight: LoadBalancer/NodePort gets you to Envoy; Ingress rules decide where Envoy sends you next.

When to use a Service, and when to use an Ingress​

A Service of type LoadBalancer can expose a single app to the outside world on its own — no Ingress needed. So when do you add one? Use a bare LoadBalancer Service when you have one thing to expose and it is not HTTP, or you genuinely want a dedicated external address per app. Reach for an Ingress the moment you have several HTTP Services to expose and want them behind one address, sorted by hostname and path, with TLS terminated in one place. One external IP, one certificate store, many apps — that consolidation is the reason Ingress exists. The cost of a LoadBalancer per Service (a real, billed cloud load balancer each) is the other half of the argument: one shared ingress is cheaper and easier to reason about than a dozen public IPs.

Name-based virtual hosting versus path-based routing​

An Ingress sorts traffic on two dimensions, and it is worth being precise about which is which because you will reach for them in different situations.

Name-based virtual hosting routes on the hostname in the request. Many hostnames, one entry point, each hostname sent to a different Service:

  • fernwood.local → the frontend Service
  • api.fernwood.local → the backend Service

This is what you want when the parts of your system are genuinely separate properties — a marketing site, an app, an API — that happen to share one ingress. Each gets its own clean hostname and its own certificate, and they do not collide.

Path-based routing keeps one hostname and routes on the URL path:

  • shop.fernwood.local/ → the frontend Service
  • shop.fernwood.local/api → the backend Service

This is what you want when it is really one property that a user thinks of as a single site, but different path prefixes are served by different backends. The user sees one domain; behind it, /api is a separate Service from /. When two rules could both match, the more specific (longer) prefix wins, so /api is chosen over the catch-all /.

You can mix both, and in a real system you usually do. The mental model stays simple: the receptionist can sort visitors by which company they name (host) or by which department they ask for (path), and often by both.

The Gateway API: the same job, split across roles​

Ingress has a design flaw that only shows up at organisational scale. It is a single flat object that crams three different concerns together — which controller implements it, what the entry point looks like, and the actual routing rules — into one YAML that one team must own. In a cluster shared by a platform team and several app teams, that is a fight waiting to happen. The app team wants to change a route; the object they must edit also holds infrastructure settings they should not touch.

The Gateway API is the newer, more expressive successor, and its core move is to split that one object into three, each owned by the team that should own it:

  • GatewayClass — which implementation backs this (here, Contour/Envoy). Cluster-scoped. The platform team registers it once, the way M6's StorageClass named a provisioner once.
  • Gateway — the actual listener / entry point: this port, this protocol, this address. The infra team owns the shared front door.
  • HTTPRoute — the routing rules: this hostname and path go to that Service. App teams own these and attach them to the Gateway without ever touching it.

That separation is the whole point. The infra team defines the Gateway once and never has to reopen it; each app team ships HTTPRoutes for its own hostnames and paths, on its own schedule, with permission to touch only its own routes. The same routing you can express with a classic Ingress you can express with a Gateway plus HTTPRoutes — same outcome, cleaner ownership. Contour serves both APIs on the same Envoy at once, which is exactly what the lab shows: the classic Ingress rules and the Gateway API routes running side by side through one data plane.

You will use classic Ingress for a long time yet — it is everywhere, and for a single team it is perfectly fine. Reach for the Gateway API when more than one team shares the front door, or when you need routing Ingress cannot cleanly express. Knowing both, and knowing they compile down to the same Envoy config, is what lets you read any cluster you are handed.

Where this leaves the app​

At the end of this module Fernwood has a real front door. Outside traffic arrives at one entry point, Envoy reads the hostname and path, and routes it to the frontend, the backend, or — as the case study shows — a completely unrelated Spring Boot service, all through the same controller. The next module locks that door down: NetworkPolicy decides which traffic is even allowed to move, and the ingress path you built here is one of the flows M8 has to keep open on purpose.
