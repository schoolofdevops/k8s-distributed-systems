Deep Dive — Reading Envoy's real config, and migrating Ingress to the Gateway API

The lab left you with a working front door and a claim: classic Ingress and the Gateway API are "two APIs, one Envoy". This page proves that claim by reading the config Envoy is actually running, and then uses the same view to do the thing you will really be paid to do — migrate an existing Ingress to the Gateway API without guessing whether the cutover worked.

Two questions drive this page, both the kind a senior engineer asks before trusting a routing change:

  1. When you write an Ingress or an HTTPRoute, what does Contour actually program into Envoy — and are the two really identical underneath, or does that just look true from the outside?
  2. How do you migrate a route from Ingress to the Gateway API and verify the cutover at the data plane, not just at the YAML?

How Contour turns objects into Envoy config: the xDS pipeline​

Contour never edits an Envoy config file. Envoy holds its config in memory and subscribes to a live feed; Contour publishes to that feed. The feed is xDS — a set of gRPC discovery services, one per config type:

  • LDS — Listeners: the open sockets (here, http-80).
  • RDS — Routes: the virtual hosts and their match-to-cluster rules.
  • CDS — Clusters: the upstreams (one per Service+port).
  • EDS — Endpoints: the live Pod IPs behind each cluster.

The analogy is a live subscription feed, not a document you save. Envoy subscribes once; every time you apply an Ingress or HTTPRoute, Contour recomputes the affected xDS resources and pushes them, and Envoy swaps them in without a restart. That is why your routes appeared seconds after kubectl apply with no Envoy bounce.

Notice both inputs feed the same Contour and the same Envoy. There is no separate Gateway-API data path. That is the structural reason the two APIs behave identically — they converge before they ever reach Envoy.

Read the actual rules Envoy is running​

In M1 you read the real iptables rules the Service abstraction compiled down to. This is the L7 version of that move: read the real Envoy config the Ingress and HTTPRoute abstractions compiled down to. Envoy exposes an admin interface; Contour binds it to 127.0.0.1:9001 inside the Envoy Pod. Port-forward to it (second terminal):

kubectl port-forward -n projectcontour pod/$(kubectl get pod -n projectcontour -l app=envoy -o jsonpath='{.items[0].metadata.name}') 9001:9001

Start with the listeners — the sockets Envoy actually holds open:

curl -s http://127.0.0.1:9001/listeners

Expected output — the admin socket, the stats/health socket, and the one that matters, http-80:

envoy-admin::127.0.0.1:9001
stats-health::0.0.0.0:8002
http-80::0.0.0.0:8080

Now the route table on that listener. This is the payoff. Dump the dynamic route config and pull out each virtual host and the cluster it routes to:

curl -s http://127.0.0.1:9001/config_dump \
  | jq -r '.configs[] | select(."@type"|endswith("RoutesConfigDump"))
      | .dynamic_route_configs[]?.route_config | select(.name=="http-80")
      | (.virtual_hosts // [])[] | "\(.name)  ->  \((.routes//[{}])[0].route.cluster)"'

Expected output — every hostname you created, in one Envoy route table, regardless of which API declared it (your set will match whatever you have applied):

api.fernwood.local  ->  fernwood/backend/8080/da39a3ee5e
fernwood.local  ->  fernwood/frontend/80/da39a3ee5e
legacy.fernwood.local  ->  fernwood/frontend/80/da39a3ee5e
shop.fernwood.local  ->  fernwood/backend/8080/da39a3ee5e
spring.fernwood.local  ->  fernwood/springboot-demo/8080/da39a3ee5e
store-api.fernwood.local  ->  fernwood/backend/8080/da39a3ee5e
store.fernwood.local  ->  fernwood/frontend/80/da39a3ee5e

Read that carefully. fernwood.local came from a classic Ingress; store.fernwood.local came from a Gateway API HTTPRoute. In Envoy they are neighbouring virtual hosts in the same route config, pointing at the same clusters, indistinguishable by origin. The abstraction you chose in Kubernetes is invisible by the time traffic is routed. That is what "two APIs, one Envoy" means concretely.

One layer down are the clusters and their endpoints. A cluster's endpoints (EDS) are the live Pod IPs — the same thing the Service's Endpoints held in M4, now inside Envoy:

curl -s http://127.0.0.1:9001/clusters | grep '^fernwood/frontend/80' | grep 'health_flags::healthy'

Expected output — three healthy endpoints, one per frontend Pod (your IPs will differ):

fernwood/frontend/80/da39a3ee5e::192.168.40.71:3000::health_flags::healthy
fernwood/frontend/80/da39a3ee5e::192.168.40.72:3000::health_flags::healthy
fernwood/frontend/80/da39a3ee5e::192.168.40.73:3000::health_flags::healthy

When a frontend Pod is rescheduled and its IP changes, Contour recomputes EDS and pushes the new IP; Envoy updates this list without dropping the listener. The full path is now visible end to end: listener → virtual host → cluster → endpoint, and you can read every hop.

Migrating a route from Ingress to the Gateway API​

Now use that same view to do a real migration. The mapping between the two APIs is mechanical — every field of a simple Ingress rule has a direct Gateway API home:

Classic IngressGateway APINotes
ingressClassName: contourGateway + GatewayClassImplementation is chosen once on the Gateway, not per route
rules[].hostHTTPRoute.spec.hostnames[]A route can list several hostnames
rules[].http.paths[].path + pathTyperules[].matches[].path (type, value)Same prefix semantics
backend.service.name / portrules[].backendRefs[].name / portSame Service target
(implicit — one object owns everything)parentRefs[]The route explicitly attaches to a Gateway

The migration files route legacy.fernwood.local to the frontend, first as an Ingress, then as an HTTPRoute. Apply the Ingress and confirm it is live:

kubectl apply -f labs/distributed-app/k8s/deep-dive/migrate-ingress.yaml

Read the vhost it produced straight from Envoy:

curl -s http://127.0.0.1:9001/config_dump \
  | jq -r '.configs[] | select(."@type"|endswith("RoutesConfigDump"))
      | .dynamic_route_configs[]?.route_config | select(.name=="http-80")
      | (.virtual_hosts // [])[] | select(.name|test("legacy"))
      | "vhost \(.name) domains=\(.domains|join(",")) -> \((.routes//[])[].route.cluster)"'

Expected output — the Ingress is now a virtual host in Envoy:

vhost legacy.fernwood.local domains=legacy.fernwood.local -> fernwood/frontend/80/da39a3ee5e

Now cut over. Delete the Ingress and apply the HTTPRoute for the same hostname:

kubectl delete -f labs/distributed-app/k8s/deep-dive/migrate-ingress.yaml
kubectl apply  -f labs/distributed-app/k8s/deep-dive/migrate-httproute.yaml

Expected output:

ingress.networking.k8s.io "legacy" deleted
httproute.gateway.networking.k8s.io/legacy created
Do not kubectl wait on an HTTPRoute condition

An HTTPRoute's Accepted/ResolvedRefs conditions live under status.parents[], one set per attached Gateway — not as a top-level condition. kubectl wait --for=condition=Accepted httproute/… therefore times out even when the route is perfectly healthy. Verify an HTTPRoute by reading its status with kubectl get -o jsonpath or, better, by reading Envoy — which is what you do next.

Confirm the cutover at the data plane. Re-read the same vhost — it is now sourced from the HTTPRoute, and it is identical:

curl -s http://127.0.0.1:9001/config_dump \
  | jq -r '.configs[] | select(."@type"|endswith("RoutesConfigDump"))
      | .dynamic_route_configs[]?.route_config | select(.name=="http-80")
      | (.virtual_hosts // [])[] | select(.name|test("legacy"))
      | "vhost \(.name) domains=\(.domains|join(",")) -> \((.routes//[])[].route.cluster)"'
kubectl get ingress legacy -n fernwood

Expected output — same domain, same cluster; the Ingress object is gone:

vhost legacy.fernwood.local domains=legacy.fernwood.local -> fernwood/frontend/80/da39a3ee5e
Error from server (NotFound): ingresses.networking.k8s.io "legacy" not found

The virtual host in Envoy did not change — same domain, same cluster, same endpoints — because both objects compile to the same xDS. That is what makes an Ingress-to-Gateway-API migration safe to do one route at a time: you can prove parity at the data plane before and after each cutover, and roll back by re-applying the Ingress if the vhost ever differs. In a real estate you would migrate route by route, reading Envoy after each, rather than flipping the whole cluster at once.

Where you will use this​

  • Auditing a cluster you inherited. The YAML claims one thing; Envoy's route table is the truth. When a request 404s and the Ingress "looks right", dump /config_dump and check whether the vhost is even in the table — usually it is a class mismatch or a Service with no endpoints, both visible here.
  • Migrating an Ingress estate to the Gateway API. Do it per route, per team, proving parity in Envoy at each step, exactly as above — not as a big-bang rewrite.
  • Debugging load balancing. When one Pod gets no traffic, /clusters shows its endpoint's health_flags; an unhealthy or missing endpoint there explains what kubectl get pods cannot.

Stop the port-forward with Ctrl-C when you are done. The migrated legacy HTTPRoute is harmless and can stay; if you want the cluster exactly as the lab left it, delete it with kubectl delete -f labs/distributed-app/k8s/deep-dive/migrate-httproute.yaml.
