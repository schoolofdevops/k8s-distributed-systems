Lab — Exposing Services with Ingress & the Gateway API (Envoy)

You will put a real L7 front door in front of Fernwood Goods. You install Contour (an Envoy-based ingress controller), route to the frontend and backend by hostname, then by path, expose an unrelated Spring Boot service through the same door, and finally express the same routing with the Gateway API. By the end the classic Ingress rules and the Gateway API routes run side by side through one Envoy.

Nothing here touches the app's Deployments, the StatefulSet, or the Services. You are adding a layer in front of what M6 left running.

Before you start​

You need the shared distsys cluster from M3 with the Fernwood app running (frontend, backend, db). Point kubectl at it:

kubectl config use-context kind-distsys
kubectl get deploy,statefulset -n fernwood

Expected output — the app M6 left behind is up (your ages and replica counts will differ):

NAME                       READY   UP-TO-DATE   AVAILABLE   AGE
deployment.apps/backend    2/2     2            2           134m
deployment.apps/frontend   3/3     3            3           134m

NAME                    READY   AGE
statefulset.apps/db     1/1     60m

If that app is not there, catch up with M6 first — this module assumes it.

Step 1 — Install Contour (the Envoy-based ingress controller)​

Contour is two things in one install: the Contour control plane that watches Kubernetes objects, and the Envoy data plane that holds the open ports. The rendered manifest, pinned to a version, creates both plus their RBAC in a projectcontour namespace.

kubectl apply -f https://raw.githubusercontent.com/projectcontour/contour/v1.33.5/examples/render/contour.yaml

Expected output (trimmed — many objects are created):

namespace/projectcontour created
serviceaccount/contour created
serviceaccount/envoy created
configmap/contour created
customresourcedefinition.apiextensions.k8s.io/contourconfigurations.projectcontour.io created
...
service/contour created
service/envoy created
deployment.apps/contour created
daemonset.apps/envoy created

Wait for the control plane and data plane to come up, then look at what is running:

kubectl wait --for=condition=ready pod -l app=contour -n projectcontour --timeout=90s
kubectl wait --for=condition=ready pod -l app=envoy   -n projectcontour --timeout=90s
kubectl get pods -n projectcontour

Expected output — two Contour replicas Running, the Envoy Pod Running (2/2), and a one-shot cert-generation Job Completed:

NAME                            READY   STATUS      RESTARTS   AGE
contour-6f49b487f-bpgrb         1/1     Running     0          38s
contour-6f49b487f-fgzx7         1/1     Running     0          38s
contour-certgen-v1-33-5-mbk4x   0/1     Completed   0          40s
envoy-pp5fk                     2/2     Running     0          38s

contour-certgen is a Job, not a crash — it generates the TLS certs Contour and Envoy use to talk to each other, then exits. Completed is success.

Step 2 — Find the entry point and open a path to it​

Envoy is exposed by its own Service. Look at it:

kubectl get svc envoy -n projectcontour

Expected output — a LoadBalancer Service whose EXTERNAL-IP is <pending>:

NAME    TYPE           CLUSTER-IP      EXTERNAL-IP   PORT(S)                      AGE
envoy   LoadBalancer   10.96.165.183   <pending>     80:32256/TCP,443:31711/TCP   10m

On a cloud provider that <pending> would become a real public IP within a minute. KIND has no cloud load balancer, so it stays <pending> forever — that is expected here, not a fault. To reach Envoy from your laptop, port-forward its Service. Run this in a second terminal and leave it running:

kubectl port-forward -n projectcontour svc/envoy 8888:80

That maps localhost:8888 straight to Envoy's port 80. Every curl below aims at 127.0.0.1:8888 and supplies the real hostname with --resolve, so you never have to edit /etc/hosts. A bare request with no matching host returns a 404 straight from Envoy — proof it is answering:

curl -s -o /dev/null -w "%{http_code}\n" http://127.0.0.1:8888/

Expected output — Envoy is up and correctly has no route for a hostless request yet:

404

Step 3 — Name-based virtual hosting​

Route two hostnames through the one entry point to two different Services. The manifest is one Ingress object with two host rules.

kubectl apply -f labs/distributed-app/k8s/ingress-namebased.yaml
kubectl get ingress -n fernwood

Expected output — the Ingress is accepted with class contour:

NAME       CLASS     HOSTS                               ADDRESS   PORTS   AGE
fernwood   contour   fernwood.local,api.fernwood.local             80      1s

kubectl describe shows the rules resolved to real Pod endpoints — the Ingress is wired to the same Services (and therefore the same Pods) the app already runs:

kubectl describe ingress fernwood -n fernwood

Expected output (trimmed to the rules — your Pod IPs will differ):

Rules:
  Host                Path  Backends
  ----                ----  --------
  fernwood.local      
                      /   frontend:80 (192.168.40.71:3000,192.168.40.72:3000,192.168.40.73:3000)
  api.fernwood.local  
                      /   backend:8080 (192.168.40.95:8080,192.168.40.126:8080,192.168.40.94:8080 + 3 more...)

Now prove the routing. Same entry point, two hostnames, two different Services:

curl -s --resolve fernwood.local:8888:127.0.0.1 http://fernwood.local:8888/ | grep -i '<title>'

Expected output — fernwood.local reaches the frontend, which returns the storefront HTML:

  <title>Fernwood Goods</title>
curl -s --resolve api.fernwood.local:8888:127.0.0.1 http://api.fernwood.local:8888/api/products

Expected output — api.fernwood.local reaches the backend, which returns JSON (your served_by Pod name and product order will differ; db should read connected):

{"count":6,"db":"connected","products":[{"id":1,"name":"Cedar Plant Stand","origin":"Oregon"},...],"served_by":"backend-ff65b9c87-kf6sq"}

One door, two hostnames, two Services. That is name-based virtual hosting.

Step 4 — Path-based routing​

Now the other dimension: one hostname, routed on the URL path. / goes to the frontend, /api to the backend. The backend already serves its endpoints under /api/..., so the path passes through unchanged.

kubectl apply -f labs/distributed-app/k8s/ingress-pathbased.yaml

Expected output:

ingress.networking.k8s.io/fernwood-paths created

Hit the same host on two paths:

curl -s -o /dev/null -w "path /     -> %{http_code}\n" --resolve shop.fernwood.local:8888:127.0.0.1 http://shop.fernwood.local:8888/
curl -s --resolve shop.fernwood.local:8888:127.0.0.1 http://shop.fernwood.local:8888/api/health

Expected output — / lands on the frontend (a 200), /api/health lands on the backend (its JSON):

path /     -> 200
{"db":"connected","hostname":"backend-ff65b9c87-kf6sq","service":"backend","status":"ok"}

The longer prefix wins: /api/health matches the /api rule, not the catch-all /. That precedence is what makes path-based routing predictable.

Step 5 — Case study: expose a Spring Boot service through the same door​

The controller does not care what language a Service is written in. To prove it, put a stock Spring Boot (Java) app behind the same Envoy, with the same kind of Ingress object. Deploy it (M5 introduced this image; redeploy it if it was torn down):

kubectl apply -f labs/distributed-app/k8s/springboot-casestudy.yaml
kubectl wait --for=condition=available deploy/springboot-demo -n fernwood --timeout=90s

Expected output:

deployment.apps/springboot-demo created
service/springboot-demo created
deployment.apps/springboot-demo condition met

Add an Ingress rule for it on its own hostname, then reach it:

kubectl apply -f labs/distributed-app/k8s/ingress-springboot.yaml
curl -s --resolve spring.fernwood.local:8888:127.0.0.1 http://spring.fernwood.local:8888/

Expected output — the Java service answers through the same Envoy front door:

Hello World!

Three different services — Node, Python, Java — now sit behind one ingress layer, each on its own hostname, none of them aware of the others.

Step 6 — The Gateway API: the same routing, split across roles​

Express the same kind of routing with the newer Gateway API. Contour speaks it, but you must enable it in three moves: install the Gateway API CRDs, tell Contour which Gateway to reconcile, then create the GatewayClass/Gateway/HTTPRoute objects.

First the CRDs. Contour needs the experimental channel (it watches route types like TCPRoute and BackendTLSPolicy that the standard channel does not ship):

kubectl apply -f https://github.com/kubernetes-sigs/gateway-api/releases/download/v1.3.0/experimental-install.yaml

Expected output (trimmed):

customresourcedefinition.apiextensions.k8s.io/gatewayclasses.gateway.networking.k8s.io created
customresourcedefinition.apiextensions.k8s.io/gateways.gateway.networking.k8s.io created
customresourcedefinition.apiextensions.k8s.io/httproutes.gateway.networking.k8s.io created
customresourcedefinition.apiextensions.k8s.io/tcproutes.gateway.networking.k8s.io created
...

Now point Contour at a specific Gateway by replacing its config with one that names it, and restart Contour so it reloads:

kubectl apply -f - <<'EOF'
apiVersion: v1
kind: ConfigMap
metadata:
  name: contour
  namespace: projectcontour
data:
  contour.yaml: |
    gateway:
      gatewayRef:
        name: contour
        namespace: projectcontour
EOF
kubectl rollout restart deploy/contour -n projectcontour
kubectl rollout status deploy/contour -n projectcontour --timeout=90s

Expected output — Contour rolls out cleanly with Gateway API enabled:

configmap/contour configured
deployment.apps/contour restarted
deployment "contour" successfully rolled out

Create the three objects — GatewayClass (which implementation), Gateway (the listener), and two HTTPRoutes (the rules) — and confirm the Gateway is programmed:

kubectl apply -f labs/distributed-app/k8s/gateway.yaml
kubectl apply -f labs/distributed-app/k8s/httproute.yaml
kubectl wait --for=condition=Programmed gateway/contour -n projectcontour --timeout=60s
kubectl get gateway -n projectcontour
kubectl get httproute -n fernwood

Expected output — the Gateway reports PROGRAMMED: True and both HTTPRoutes are attached:

gateway.gateway.networking.k8s.io/contour condition met
NAME      CLASS     ADDRESS   PROGRAMMED   AGE
contour   contour             True         0s
NAME       HOSTNAMES                      AGE
backend    ["store-api.fernwood.local"]   0s
frontend   ["store.fernwood.local"]       0s

The HTTPRoutes use different hostnames (store.*, store-api.*) so they run alongside the classic Ingress rules, not instead of them. Prove both APIs are live on the same Envoy at once:

echo "[Ingress]    fernwood.local     -> $(curl -s -o /dev/null -w '%{http_code}' --resolve fernwood.local:8888:127.0.0.1 http://fernwood.local:8888/)"
echo "[Ingress]    api.fernwood.local -> $(curl -s -o /dev/null -w '%{http_code}' --resolve api.fernwood.local:8888:127.0.0.1 http://api.fernwood.local:8888/api/health)"
echo "[GatewayAPI] store.fernwood     -> $(curl -s -o /dev/null -w '%{http_code}' --resolve store.fernwood.local:8888:127.0.0.1 http://store.fernwood.local:8888/)"
echo "[GatewayAPI] store-api.fernwood -> $(curl -s -o /dev/null -w '%{http_code}' --resolve store-api.fernwood.local:8888:127.0.0.1 http://store-api.fernwood.local:8888/api/health)"

Expected output — classic Ingress and Gateway API routing, side by side, one data plane:

[Ingress]    fernwood.local     -> 200
[Ingress]    api.fernwood.local -> 200
[GatewayAPI] store.fernwood     -> 200
[GatewayAPI] store-api.fernwood -> 200

Same Envoy, two control APIs, both routing real traffic. That is the whole comparison in one screen.

What you built​

  • Contour + Envoy as the ingress controller and data plane, installed from a pinned manifest.
  • Name-based virtual hosting — fernwood.local → frontend, api.fernwood.local → backend.
  • Path-based routing — shop.fernwood.local/ → frontend, /api → backend.
  • A Spring Boot case study exposed through the same front door on spring.fernwood.local.
  • The Gateway API — GatewayClass/Gateway/HTTPRoute serving store.* routes on the same Envoy, side by side with the Ingress objects.

Teardown​

Leave everything running. The next module (M8) adds NetworkPolicy in front of this exact ingress path, so Contour, Envoy, the Ingress objects, and the Gateway API objects all stay. The only thing to stop is the port-forward: return to its terminal and press Ctrl-C.

If you ever need to remove the whole ingress layer (you do not for this course), it is:

# Do NOT run this for the course — M8 needs the ingress layer.
# kubectl delete -f labs/distributed-app/k8s/httproute.yaml -f labs/distributed-app/k8s/gateway.yaml
# kubectl delete ingress fernwood fernwood-paths springboot-demo -n fernwood
# kubectl delete -f https://raw.githubusercontent.com/projectcontour/contour/v1.33.5/examples/render/contour.yaml

The cluster, the Fernwood app, and the ingress layer are the steady state M8 inherits.
